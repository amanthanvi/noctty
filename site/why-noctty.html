Why Noctty

Trust should be inspectable.

Noctty is an independent native Windows terminal built around Ghostty's terminal core. The source, release machinery, boundaries, and current trust limits are public so you can check the project before you run it.

Verify a release Plan a migration

Latest stable: v1.3.123. Twenty-two stable releases shipped between 2026-04-16 and 2026-08-06. No cadence is promised; the dated release history is the whole record. Version 1.3.123, latest release, for Windows 10 and 11 on x64 and ARM64, MIT licensed.

The project

A Windows product, not a repackaged build.

Ghostty supplies the shared terminal, font, renderer, input, configuration, shell-integration, and VT-library foundations. Noctty owns the Win32 runtime around them: native windows, tabs and splits, settings, session restoration, Windows shell profiles, packaging, and updates.

Other Windows ports of Ghostty exist. Noctty's claim is narrower: this repository publishes a maintained Windows application and its distribution path, rather than claiming to be the official Ghostty app. Noctty is not affiliated with the Ghostty non-profit.

The current project has one maintainer. What separates it from a personal build uploaded as a release is checkable rather than asserted: release history that is not rewritten or force-pushed, public build and release workflows, a verifier script you can run against any published release, and the standing boundaries below.

Source history, CI, packaging scripts, release notes, and issue tracking are all public. That visibility is useful evidence. It is not a substitute for checking a binary's origin yourself, which is what the next two sections are for.

Measured and unmeasured

What has actually been checked.

Two claims get made about terminals more than any others: that they are fast, and that they are accessible. Here is what this project can show for each, including the results that fall short.

Performance

Throughput, frame time, cold start, per-pane memory, idle cost, and ConPTY round trip are measured on one machine, a Ryzen 9 9900X with an RTX 5070 Ti on Windows build 26200, from ReleaseFast builds. The methodology doc carries each figure with the date, the run count, and the state the machine was in, because a benchmark taken under load is a different measurement.

Two results miss a budget stated in PRODUCT.md, and they are recorded as measured rather than adjusted: memory per additional pane, and the cold start tail, where the median fits the budget and the p95 does not. Both are currently marked provisional. They were taken under parallel build load, against a build that predates a round of performance work, so the figures are not repeated here until they have been re-measured on an idle machine. Key-to-pixel latency is not measured at all; the suite ships a software proxy that cannot certify it.

No comparison against another terminal is published, here or anywhere else in the project. Measuring another terminal at the same causal endpoint on the same machine has not been done, so no such claim is made.

Accessibility

Noctty ships UI Automation providers for terminal text and selection, the tab strip, docked search, the command palette, and the settings window. An interactive harness walks that tree on a real Windows desktop and asserts control types, names, patterns, and events.

No screen reader has been run against a release build. The published per-widget matrix records Narrator, NVDA, and JAWS as not yet measured in every row, and carries the per-release procedure that would change them. A UI Automation tree proves structure, not speech. Window chrome also cannot be reached from the terminal with the keyboard alone.

Release verification

Check the bytes. Then check the signer.

Download the installer or portable ZIP and the architecture-specific checksum file from the same GitHub Release. Do these checks before you install or extract anything. Each one answers a different question, and none of them substitutes for another.

  1. Match the published checksum

    Answers: did the bytes arrive intact and unchanged? Compare the hash with the matching line in SHA256SUMS-windows-<arch>.txt. Stop on any mismatch. 

    Get-FileHash `
  .\noctty-<version>-windows-<arch>-setup.exe `
  -Algorithm SHA256

  2. Inspect the embedded signature

    Answers: which key signed the executable code? The installer and the PE files inside the portable ZIP are Authenticode-signed. The ZIP container is not, so the container is covered only by its checksum. 

    Get-AuthenticodeSignature `
  .\noctty-<version>-windows-<arch>-setup.exe | `
  Format-List Status,StatusMessage,SignerCertificate

  3. Run the checksum and signature checks at once

    The repository verifier downloads the complete release, checks every GitHub digest and checksum entry, validates every embedded PE signature, and requires a single signer whose SPKI matches the key pinned into the updater. Releases do not currently publish build-provenance attestations, so this verifier does not claim to check one. The environment variable is what makes it accept today's self-signed certificate; without it, the script fails closed. 

    git clone https://github.com/amanthanvi/noctty.git
Set-Location .\noctty
$env:WINDOWS_CODESIGN_TRUST_SELF_SIGNED = "true"
pwsh .\scripts\verify-published-release.ps1 `
  -Version <version>

The present trust limit

There is no code-signing certificate from a public certificate authority. Releases are signed with a self-signed certificate, which gives an embedded cryptographic signature but no third-party Windows publisher identity and no SmartScreen reputation. SmartScreen will warn, and the warning will not fade with time. PowerShell may report the otherwise intact signature as UnknownError because Windows does not trust its root. The repository verifier accepts that case only when the signature is cryptographically valid and the signer matches the compiled key pin.

Certificate subject
CN=winghostty Local Dev Signing
SPKI SHA-256
671ec822c41f39b1d79c31d27169b37486333c008c7a038261b4fae53818ce2a

The subject name predates the Noctty rename and proves nothing by itself. A checksum published beside a binary proves consistency with that release page, not authorship. The pinned public key is the separate publisher constraint the updater and the verifier enforce; its rotation policy is ADR 0005.

Moving to a publicly trusted signer means either an accepted application to a free open-source signing program or a purchased certificate. Neither has happened. Until one does, the honest summary is that the published checksums, embedded signatures, and key pin constrain a release to this repository's publisher key, while Windows itself will keep telling you it does not recognize the publisher.

Standing boundaries

What Noctty will not become.

These eleven scope rules were ratified after studying how other terminal products and Windows forks failed. Each one is a thing this project has decided not to do, so scope pressure has an answer.

  1. No cloud coupling.

    No account, telemetry, analytics, or required hosted service.

  2. No product pivot that sidelines terminal fundamentals.

    Input, rendering, compatibility, and reliability keep priority over a new product category.

  3. No feature breadth before performance and reliability.

    New surface area comes after the published performance budgets, not before them.

  4. No re-platforming onto Electron or a fashionable UI stack.

    Zig and native Win32 remain the application boundary.

  5. No workspace or widget drift.

    No embedded browser, database client, or general file manager.

  6. No forced or background-applied updates.

    Applying an update stays user-initiated after checksum and signature verification.

  7. No in-process plugin runtime or hosted sync.

    Automation belongs outside the terminal process through documented interfaces.

  8. No DLL injection or undocumented hooks.

    Windows integration uses ConPTY and documented operating-system APIs.

  9. No daily-rebase soft fork.

    Upstream changes are adopted deliberately without force-pushed release history.

  10. No shell-editor interception or proprietary output protocol.

    PSReadLine, readline, prompts, and terminal applications keep ownership of their normal interfaces.

  11. No chrome-only differentiation.

    VT correctness, fluidity, sessions, native behavior, and trust have to justify the project.
