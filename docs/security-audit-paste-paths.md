# Win32 text-ingestion and PTY-write security audit

Audit date: 2026-08-21  
Base revision: `d031dc474efc4811e662a3e387e560fb760f0e19`

This audit covers the base revision plus the remediations landed in this change. Unless a row explicitly says "current tree," its historical `file:line` references are at base `d031dc474`; follow-up rows use the post-remediation current tree.

Remediation status: reconciled with the issue #123 / roadmap C32 change in this worktree.

## Result

Both Win32 drag-and-drop paths now use the same core paste encoder and unsafe-paste confirmation route as ordinary clipboard paste. For non-bracketed paste, or when `clipboard-paste-bracketed-safe=false`, the shared paste gate classifies both carriage return and line feed as unsafe. Trusted bracketed paste intentionally preserves CR and LF inside the fenceposts without confirmation because the framing prevents them from submitting input; a pasted closing fence remains unsafe. Live OSC 7 working directories reject all C0 and DEL bytes before reaching terminal pwd/title state and again before `PWD` or `CreateProcessW`. Win32 link opening permits the repository's built-in URL schemes and safe local files while rejecting arbitrary protocol handlers, UNC files, and executable/script files. Session JSON owns decoded strings and rejects control- or newline-bearing pane metadata on load; session snapshots drop only an offending live field so one hostile title cannot deny persistence for every window. The named-pipe server rejects remote clients, installs a protected current-user-only DACL with an explicit mandatory-integrity label, claims the pipe name with `FILE_FLAG_FIRST_PIPE_INSTANCE`, and never releases that name while it runs; clients refuse any server whose owner SID differs or whose integrity level is below their own. Forwarded new-window arguments are constrained by a deny-by-default key allowlist, so `--command`, `-e`, and `--input` no longer forward at all.

This audit is based on the code present at the revision above. It does not rely on unverified wording from an external CVE-2026-26982 advisory.

## Threat model / non-goals

In scope:

- attacker-controlled Windows `CF_UNICODETEXT` clipboard contents;
- OLE text, HTML, URL, and file-drop payloads, plus legacy `WM_DROPFILES` file names;
- requests from any client that Windows permits to open noctty's named pipe;
- cold, forwarded, and warm toast activation arguments;
- attacker-modified on-disk Win32 session-state JSON;
- terminal-controlled live OSC 7 working-directory reports and OSC 8 hyperlinks;
- terminal output that writes or reads the clipboard through OSC 52; and
- fork-only UI or automation routes that carry text to a PTY write or process launch.

Out of scope:

- an attacker who can already execute arbitrary code as the same Windows user;
- compromise of the child process that already owns the PTY;
- synthetic keyboard, IME, UI Automation, or `SendInput` attacks that require same-desktop code execution at a permitted Windows integrity level;
- arbitrary modification of the user's trusted noctty configuration or executable; and
- administrative compromise of the Windows account or host. The IPC pipe itself is in scope and now uses an explicit current-user-only DACL in addition to `PIPE_REJECT_REMOTE_CLIENTS`.

User gestures and configuration preconditions are stated per finding. Disabling `clipboard-paste-protection` intentionally disables confirmation, but `input.paste.encode` still runs on paths routed through `completeClipboardPaste`.

## Reference controls and terminal sink

`input.paste.encode` replaces NUL, BS, ENQ, EOT, ESC, DEL, VINTR, VQUIT, VKILL, VSUSP, VSTART, VSTOP, VWERASE, VLNEXT, VREPRINT, and VDISCARD with spaces. It adds bracketed-paste fenceposts when bracketed mode is active and otherwise converts LF to CR. `input.paste.isSafe` rejects CR, LF, and the exact bracketed-paste end marker. Win32 key encoding uses CR for Enter (`src/input/key_encode.zig:173-183`).

`Surface.completeClipboardPaste` applies `input.paste.isSafe` when paste protection is enabled and the paste is non-bracketed or `clipboard-paste-bracketed-safe=false` (`src/Surface.zig:6417-6460`). With the default trusted-bracketed setting, CR and LF remain inside the bracketed-paste fenceposts and do not require confirmation because they cannot submit input; a payload containing the closing fence is always unsafe. Every accepted paste still passes through `input.paste.encode` (`src/Surface.zig:6471-6481`) and the resulting write messages are queued (`src/Surface.zig:6488-6493`). Win32 converts `error.UnsafePaste` into the existing confirmation overlay (`src/apprt/win32.zig:24749-24788`, `src/apprt/win32.zig:27634-27680`); Accept retries with `allow_unsafe=true` (`src/apprt/win32.zig:17727-17752`).

All arbitrary-byte paths that reach `Surface.queueIo` pass its readonly gate (`src/Surface.zig:925-942`), then `termio.Thread` (`src/termio/Thread.zig:343-359`), `Termio.queueWrite` and the backend (`src/termio/Termio.zig:583-597`, `src/termio/backend.zig:76-85`), and finally `Exec.queueWrite` into the PTY stream (`src/termio/Exec.zig:463-526`). On Windows the write stream is connected to ConPTY input (`src/termio/Exec.zig:1147-1151`). This downstream path chunks or queues bytes; it is not a sanitizer.

## Findings

### High: live OSC 7 pwd can inject a Windows environment record

**Status: fixed in this follow-up.** One `windows_shell.isSafeWindowsPath` predicate rejects all C0 bytes and DEL. The final decoded Windows OSC 7 path must pass before `terminal.setPwd`, and both `shellPwd` and `safeCurrentDirectory` apply the same policy as the last gates before `PWD` and `CreateProcessW`.

- **Attacker control:** a child process can print an OSC 7 `file://localhost/...` URI whose path contains percent-encoded bytes.
- **Concrete injection:** `file://localhost/C:/evil%00INJ=1%0Ab` decoded to `C:\evil\x00INJ=1\nb`. The old drive-absolute check inspected only the first three bytes, and the embedded NUL became a second record in the Windows environment block (`src/Command.zig:644-677`).
- **Code path:** `reportPwd` -> `decodeOsc7PathForPwd` (`src/termio/stream_handler.zig:1166-1278`) -> terminal pwd/title -> split/tab cwd inheritance (`src/apprt/win32.zig:1872-1906`) -> `shellPwd` -> `env.put("PWD")`.
- **Resolution:** reject the final localized OSC 7 path before storing or reflecting it, and reject any later unsafe working-directory value at the two process-launch gates. The exact percent-encoded payload is pinned at `src/termio/stream_handler.zig:1760-1775`; raw decoded drive paths are pinned in `src/config/windows_shell.zig:1310-1342`.

### High: OSC 8 and regex links dispatch arbitrary Windows protocol handlers

**Status: fixed in this follow-up.** Win32 `openUrl` now enforces a scheme/local-file policy before `ShellExecuteW` and logs every rejection without logging attacker-controlled bytes.

- **Attacker control:** OSC 8 stores a terminal-provided URI verbatim; configured and built-in regex links pass matched terminal text, resolving an existing relative file path to an absolute path when possible (`src/Surface.zig:2275-2295`, `src/Surface.zig:4629-4652`).
- **Concrete execution route:** `file:///C:/.../x.exe`, UNC paths, `search-ms:`, `ms-*`, or another registered scheme previously reached `ShellExecuteW(null, "open", ...)` unchanged.
- **Legitimate behavior retained:** the built-in matcher schemes from `src/config/url.zig` remain allowed (`http`, `https`, `mailto`, `ftp`, `ssh`, `git`, `tel`, `magnet`, `ipfs`, `ipns`, `gemini`, `gopher`, and `news`). Raw drive-absolute files and local/`localhost` `file:` URIs remain supported for regex links, `write_screen_file:open`, and config editing.
- **Resolution:** reject all other schemes, UNC/device/remote-file paths, NTFS alternate streams, and executable/script/installer/shortcut/help extensions after percent-decoding file paths. This is deliberate fork hardening because upstream `src/os/open.zig` also has no allowlist. Allowed and rejected matrices plus a no-dispatch assertion are pinned at `src/apprt/win32.zig:33782-33866`.

### Medium: hostile live pane metadata can deny the entire session save

**Status: fixed in this follow-up.** Strict pane-text rejection remains on `parseAlloc`/load. Encode retains structural validation, while `buildSessionLayout` independently drops only an unsafe `cwd`, `profile`, `title_override`, or `tab_title_override` field before serialization.

- **Attacker control:** terminal output can influence live pwd/title metadata.
- **Failure before remediation:** `encodeAlloc` reused strict load validation, so one control-bearing field returned `InvalidPaneText`; `saveSessionState` logged only an encode failure and did not replace the state for any window.
- **Resolution:** one schema predicate is shared by load validation and snapshot filtering (`src/apprt/win32_session_state.zig:308-324`, `src/apprt/win32.zig:4294-4368`). A regression builds a pane with a hostile title, proves encode succeeds with that field omitted and safe siblings preserved, then proves the hostile file is still rejected on load (`src/apprt/win32.zig:34757-34802`).

### High: same-user named-pipe arguments can reach PTY input and process execution

**Status: fixed, jointly with PR #185.** This round's first-pass framing of "accepted, documented upstream parity" is superseded: the forwarded-argv channel now has a deny-by-default key allowlist and `--command`, `-e`, and `--input` are not on it. The measured Windows default pipe DACL granted full access to LocalSystem, Administrators, and the current user, plus read access to Everyone and Anonymous. The server supplies a protected DACL whose owner and only full-access ACE are the current token user's SID plus an explicit mandatory-integrity label, retains `PIPE_REJECT_REMOTE_CLIENTS`, and claims the pipe name with `FILE_FLAG_FIRST_PIPE_INSTANCE`.

- **Attacker control:** a process already executing as the same Windows user can send bounded but otherwise arbitrary argv. The decoder limits count, individual length, and aggregate allocation; lower-privilege unrelated local principals and remote SMB clients are rejected at the pipe boundary.
- **Concrete injection:** a new-window payload containing `--input=raw:calc.exe\r` is decoded, parsed as general configuration, Zig-unescaped, and written to the newly started PTY before ordinary input. `--input=path:<path>` does the same with readable file contents. `--command=calc.exe` reaches `cmd.exe /C` and process creation rather than a PTY write.
- **Code path:** `decodeNewWindowPayload` -> core `.new_window` mailbox (`src/apprt/win32.zig:2213-2227`, `src/App.zig:278-283`) -> general `config.loadIter` (`src/apprt/win32.zig:2044-2054`) -> surface creation (`src/apprt/win32.zig:4382-4409`) -> startup input or process launch.
- **Resolution:** `allocIpcPipeSecurityDescriptor` builds `O:<sid>G:<sid>D:P(A;;GA;;;<sid>)S:(ML;;NW;;;<integrity sid>)` from the process token and fails server startup closed if any token, SID, or descriptor step fails (`src/apprt/win32.zig:1936-1988`). `ipcPipeServerIsTrusted` re-reads the descriptor attached to the connected pipe object before the first write and refuses any server whose owner SID differs from ours or whose integrity level is below ours, failing closed on any query or parse error (`src/apprt/win32.zig:941-986`). `createIpcServerPipe` claims the name once with `FILE_FLAG_FIRST_PIPE_INSTANCE` and creates each replacement instance before closing the served one, so the server fails closed on a preclaimed name and never releases the name between requests (`src/apprt/win32.zig:1999-2104`). Forwarded argv is filtered by `forwarded_argv_allowed_keys` / `forwardedArgvRejection` (`src/apprt/win32.zig:1327-1560`), which admits no key that reaches PTY input or process creation.
- **Residual, deliberately not fixed:** a process running as the same user AT THE SAME INTEGRITY LEVEL can still pre-create `\\.\pipe\noctty.<class>` before noctty starts, in which case our first-instance claim fails and a subsequent client forwards to it. That is not a boundary this process can defend: an attacker with same-user, same-integrity code execution can already `OpenProcess` a running noctty and inject into it, so anything we could compare against -- a capability file, a launch nonce, our own image path -- is readable or forgeable by exactly that attacker. Binding the client to the server's PID is also unsound as authentication, since a duplicated server handle outlives its creating process and PIDs are recycled. The two boundaries that do exist (a different user, a lower integrity level) are enforced above; the argv allowlist bounds what a same-user squatter can obtain to the working directory and non-executing configuration keys.

### Medium: session parser returns dangling string slices

**Status: fixed in this change.** The full `SessionState` parse uses `.allocate = .alloc_always`; a regression test frees and overwrites the source allocation before reading restored strings.

- **Attacker control:** the on-disk session JSON controls unescaped cwd, profile, and title strings.
- **Concrete failure:** Zig 0.15.2 `parseFromSlice` defaults to `alloc_if_needed`, so an unescaped JSON string may remain a slice into the raw input. `loadAlloc` defers freeing that input before returning the parsed state (`src/apprt/win32_session_persistence.zig:24-36`), and restore later dereferences the fields (`src/apprt/win32.zig:3423-3445`). This establishes a use-after-free and possible crash/corrupted restore; reliable code execution was not established.
- **Code path:** `loadAlloc` -> `win32_session_state.parseAlloc` (`src/apprt/win32_session_state.zig:106-123`) -> raw buffer free -> `restoreSessionPane`.
- **Resolution:** set `.allocate = .alloc_always` on the full `SessionState` parse. Paste sanitization is not applicable to an ownership defect.

### Medium: restored cwd can inject another Windows environment entry through NUL

**Status: fixed in this change.** `win32_session_state.validateAlloc` rejects control- or newline-bearing `cwd`, `profile`, `title_override`, and `tab_title_override` values through the existing `win32_paste_protection.hasControlChars` and `hasNewline` predicates, causing load to use the existing corrupt-state quarantine path.

- **Attacker control:** session JSON accepts `cwd` as an unrestricted decoded string; JSON `\u0000` produces an embedded NUL.
- **Concrete injection:** a drive-absolute value such as `C:\\safe\\\u0000NOCTTY_SESSION_INJECTED=yes` passes the shell-visible cwd selection (`src/config/windows_shell.zig:174-187`), becomes the `PWD` value (`src/termio/Exec.zig:935-942`), and is copied verbatim into the double-NUL-terminated Windows environment block (`src/Command.zig:644-677`). The embedded NUL begins a second environment record. No privilege escalation beyond the session-file trust boundary was established.
- **Code path:** session `Pane.cwd` -> `restoreSessionPane` (`src/apprt/win32.zig:3424-3427`) -> `Surface.init` / `Exec` (`src/Surface.zig:713-722`) -> `EnvMap.put("PWD", ...)` -> `CreateProcessW` environment.
- **Resolution:** reject the hostile state centrally in the session schema validator before any restored value reaches process setup or title reflection.

### Medium: non-bracketed ordinary clipboard paste treats CR as safe

**Status: fixed for non-bracketed paste and bracketed paste with `clipboard-paste-bracketed-safe=false`.** The shared `input.paste.isSafe` predicate rejects CR as well as LF, so those clipboard paths reuse the existing confirmation flow. Default trusted bracketed paste intentionally skips this check because CR and LF are framed rather than submitted; the closing fence remains unsafe.

- **Attacker control:** standard `CF_UNICODETEXT`, including data previously written through OSC 52.
- **Concrete injection:** `attacker-command\r` in non-bracketed mode passes `input.paste.isSafe`, receives no confirmation, preserves the CR through `input.paste.encode`, and reaches the PTY as the same byte used for Enter. The user must invoke Paste in a foreground program that interprets CR as submission.
- **Code path:** any standard Win32 paste gesture -> `clipboardRequest` -> `completeClipboardRequest(.paste, confirmed=false)` -> `completeClipboardPaste` -> conditional non-bracketed safety gate -> common PTY sink.
- **Resolution:** changed the shared predicate; no Win32-specific sanitizer was added. The exported `ghostty_paste_is_safe` contract and C-wrapper test now pin this carriage-return rejection as a noctty fork delta from upstream libghostty-vt.

### Medium: legacy `WM_DROPFILES` bypasses the OLE drop sanitizer and confirmation

**Status: fixed in this change.** The fallback uses `win32_surface_drop.formatFilePayload` and hands the result to `surfaceDropPayloadCallback`, reusing the OLE classifier, sanitizer, and confirmation pipeline. The legacy `WM_DROPFILES` API carries no Shift/Ctrl modifier semantics, so it supplies default formatting modifiers rather than exactly matching every OLE formatting case.

- **Attacker control:** file-system names returned by `DragQueryFileW` for the dropped files.
- **Concrete injection:** a Windows-legal name containing `&`, such as `a& echo DROP_PROBE &`, is wrapped in POSIX single quotes. `cmd.exe` does not treat those quotes as protection, so the ampersands remain command separators when the user presses Enter after the drop.
- **Code path:** `DragAcceptFiles` -> `WM_DROPFILES` -> `handleDropFiles` -> ad hoc quoting -> synthetic `KeyEvent` -> `keyCallback` -> PTY. The path never calls `win32_paste_protection.inspect`, `completeClipboardRequest`, `input.paste.isSafe`, or `input.paste.encode`.
- **Resolution:** reused the existing OLE formatter and callback and removed the local ad hoc quoting and synthetic key event.

### Low: restored or IPC-set titles are reflected into title-report PTY responses

**Status: fork-only injection source fixed; core behavior accepted.** Session title controls, including CR and LF, are rejected by the central session validator. Core `Surface.zig` title reporting remains unchanged because it is upstream-owned, opt-in, disabled by default, and already documented as dangerous; IPC and perform-action title setters additionally require a permitted local pipe client under this threat model.

- **Attacker control:** session `title_override` / `tab_title_override`, IPC new-window `--title`, or allowed perform-action `set_surface_title:` / `set_tab_title:` text.
- **Concrete injection:** a title containing an OSC terminator followed by command text and CR is interpolated into `ESC ] l <title> ESC \\`. If `title-report=true` and the child issues CSI 21 t, the protocol frame can terminate early and the following bytes enter PTY input. Title reporting is disabled by default and its configuration documentation already warns of code-execution risk (`src/config/Config.zig:2331-2340`).
- **Code path:** restored or IPC-set title -> Win32 effective title (`src/apprt/win32.zig:25101-25118`) -> `Surface.handleMessage(.report_title)` (`src/Surface.zig:1049-1072`) -> common PTY sink.
- **Resolution:** no core title-report change. Removing control- or newline-bearing restored session titles closes the fork-only untrusted source; the remaining opt-in upstream behavior and permitted-local-client automation precondition are accepted.

## Clean or non-applicable paths

- All four OLE formats converge on `surfaceDropPayloadCallback`, the Win32 severity classifier, the core paste gate, the shared encoder, and the existing confirmation overlay.
- Explicit Win32 selection paste fails closed because Win32 advertises and accepts only the standard clipboard.
- `Surface.textCallback` currently has no Win32 caller. Actual key, authorized `WM_CHAR`, and IME-commit paths use key semantics and are intended user-input channels.
- `+perform-action` reparses server-side and rejects direct `.text`, `.csi`, `.esc`, paste, write-file, and crash actions.
- Toast activation has a typed focus-only grammar and no PTY-text or attacker-selected command sink. Warm activation ignores event-supplied arguments and uses the launch string stored when noctty created the toast (`src/apprt/win32_toast_winrt.zig:390-401`, `src/apprt/win32_toast_winrt.zig:445-453`).
- Session `profile` is an exact live-profile key selector. Session command, environment, scrollback, and terminal-content members do not exist and are rejected by strict current-schema parsing. The raw state file is capped at 1 MiB (`src/apprt/win32_session_persistence.zig:7`, `src/apprt/win32_session_persistence.zig:94-99`).
- OSC 52 clipboard read uses a separate allow/ask/deny policy and base64-encodes clipboard bytes into a fixed response rather than writing them as raw terminal input.

## Fuzzing

Six in-process `std.testing.fuzz` targets run their inline seed corpora during ordinary unit tests. Each target also has a deterministic 2,048-input bounded mutation campaign:

1. `src/input/paste.zig`: arbitrary bytes through mutable `encode` in both modes, asserting strip-set removal, payload fence-escape removal, exact bracket fenceposts, and the `isSafe` CR/LF invariant.
2. `src/apprt/win32_session_state.zig`: arbitrary JSON through the strict `parseAlloc` load parser and validator, with successful parses exercising owned allocation and leak-checked teardown through `std.testing.allocator`.
3. `src/apprt/win32_toast_activation.zig`: arbitrary bytes through toast parsing, round-tripping successful activation targets; inline seeds pin valid, malformed, and wrong-scheme inputs.
4. `src/App.zig`: arbitrary bytes through `input.Binding.Action.parse`, passing every parsed action through the private `isSafeAutomationAction`; inline seeds pin representative allowed and rejected actions.
5. `src/apprt/win32_ipc.zig` new-window payloads: arbitrary bounded bytes through the production pipe decoder itself, over a temp-file handle. Successful decodes survive source-buffer overwrite and round-trip through the canonical encoder; seeds pin zero arguments, multiple arguments, truncation, and an oversized argument count.
6. `src/apprt/win32_ipc.zig` perform-action payloads: arbitrary bounded bytes through the production pipe decoder itself, over a temp-file handle. Successful focused and surface-targeted payloads survive source-buffer overwrite and round-trip through the canonical encoder; seeds also pin truncation, an invalid target tag, and a zero-length action.

Zig 0.15.2 cannot safely register zero-length corpus seeds, and an input shrunk to zero during a long `--fuzz` run can still trigger the same upstream mutator assertion even though ordinary unit-test mode exercises the empty input separately. The bounded campaigns therefore never submit zero-length inputs, use fixed seeds and iteration counts, alternate structured-corpus mutation with random bytes, and complete without the continuous fuzzer or shrinker.

Seed-corpus pass: `zig build test -Dtest-filter=fuzz`.

Safe bounded extension pass: `zig build test "-Dtest-filter=bounded fuzz campaign"`. Continuous `--fuzz` remains available for toolchains where the upstream zero-length shrink assertion is fixed; it is not the evidence claimed by this audit.

The IPC targets write each input into a seekable temporary file and hand its handle to the production `decodeNewWindowPayload` / `decodePerformActionPayload`, so the grammar, allocation bounds, and `readExactUntil` transport loop under test are the ones the pipe server runs; one file is reused for a whole campaign rather than one per iteration. Strict-prefix tests reject every truncation of representative valid payloads. Real-handle tests cover named-pipe EOF, silent-client timeout, one-byte request fragmentation and round trip, a drip-feed that cannot extend one absolute deadline, and the effective current-user-only DACL and mandatory label. Server-mode regressions pin remote-client rejection and first-instance claiming (`src/apprt/win32.zig:33750-33766`). The fuzz targets do not claim to simulate Win32 pipe scheduling.

There is no equivalent pure ConPTY transport seam to fuzz without live OS handles. `WindowsPty.open` creates an `HPCON` and Win32 pipes, the Windows read thread blocks in `ReadFile` before calling `Termio.processOutput`, and writes terminate in `xev.Stream.queueWrite`. The first pure layer after the transport is the terminal parser/stream, which already has separate parser and full-stream fuzz targets under `test/fuzz-libghostty`; those are not ConPTY transport coverage.

`src/pty_transport_probe.zig` therefore includes an opt-in bounded real-transport test rather than a fake pure fuzzer. It reuses the fork's existing native self-executable probe shape: an early environment-gated test hook becomes the contained child, uses native console reads/writes, and never invokes a shell or parses a nested command string. With `NOCTTY_RUN_CONPTY_TRANSPORT_TEST=1`, the parent opens the production Windows PTY, starts that child through `Command.zig` on the real `HPCON`, waits for an explicit ready marker, sends 24 deterministic safe-ASCII payloads in randomized one-to-seven-byte overlapped fragments, and requires the child's exact response marker for every payload. Output is capped at 64 KiB, writes have two-second deadlines, startup has a five-second deadline, and the final marker/process-exit read has a 15-second deadline. A pending timed-out/erroring overlapped write is cancelled and drained to terminal completion before its buffer, event, or `OVERLAPPED` storage can be released. Exact-child cleanup is armed immediately after process start and targets only the recorded process handle; PTY cleanup uses the production handle-closing sequence. Ordinary test runs compile the harness and skip execution. This audit does not treat parser fuzzing, a skipped opt-in run, or the failed superseded shell-child diagnostics as ConPTY transport proof.

## Unresolved facts and validation limits

- Static source proves that `WM_DROPFILES` is enabled and has an independent handler. This run did not establish whether Explorer emits it when the OLE target is also active on the same HWND.
- Focused unit, seed-corpus fuzz, bounded mutation campaigns, and build validation cover the changed boundaries. No live clipboard, Explorer/OLE, toast, or session-restore UI test was run in this pass.
- IPC payload grammar, allocation bounds, truncation rejection, round-trip, decoded-data ownership, Win32 named-pipe fragmentation, absolute deadlines, and effective DACL are validated. Two serialized real-HPCON attempts against a now-removed inline-shell child reached only the ConPTY startup mode bytes (`ESC[?9001h ESC[?1004h`), never reached the child's ready marker, and one attempt required exact-PID termination after the experimental close-thread teardown exceeded its declared bound. All recorded test/build/child identities were verified absent afterward. The replacement native self-child harness then completed 24 deterministic one-to-seven-byte fragmented round trips with its two-second write, five-second startup, and 15-second final-read deadlines plus 64 KiB output cap; both execution sentinels were observed, and its recorded parent/test and child PIDs were absent afterward with no `ghostty-test` survivor. Parser fuzzing is not presented as transport coverage.
- The exact external CVE-2026-26982 advisory text was not available in the reviewed repository. The comparison baseline is the checked-in `src/input/paste.zig` behavior and its `Surface.completeClipboardPaste` caller.
