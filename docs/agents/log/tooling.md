- 2026-11-21: PS-PATH-LOOKUP-01. Two command-lookup traps the #740 round-5 council measured against the GUI selection's script walk (`scripts/ci-script-closure.ps1`). (1) A path with no extension looks like it runs the `.ps1` beside it, the first extension PowerShell tries. Not always: with `<path>.ps1` and `<path>.cmd` both present, `Get-Command <path> -CommandType ExternalScript` found the `.ps1` and `-CommandType Application` the `.cmd` (Sol, pwsh 7.6.10), and cmd's `/C`, `/K`, `/R` and `call` run `<path>.cmd` by PATHEXT, never a `.ps1` (Opus). Keeping every sibling as a member is no fix either: with only `<path>.exe` (a pwsh) there, the walk kept the exe and dropped the `-File` child its arguments named (Greptile). Rule: a path lookup, in any form and under any `-CommandType`, resolves only when its `.ps1` is the one sibling with `.ps1` or a PATHEXT extension, matched case-insensitively (`Get-CiScriptPathLookup`, `Find-CiScriptLookupFiles`, and the `Lister` note New-CiScriptFileReader's readers carry); a native or batch sibling, with or without a `.ps1`, or no sibling, leaves it unresolved, which fails the walk. cmd never runs a `.ps1`, and the walk now refuses every cmd and batch invocation outright (the 2026-11-20 GUI-HIDDEN-DEFAULT-01 entry in test-harnesses.md, rounds 6 to 8). (2) `Microsoft.PowerShell.Utility\Get-Date` reads as a module-qualified cmdlet by its shape, and a shipped module's name looked like enough. It is not: a name the module does not export is a relative path, so `Microsoft.PowerShell.Utility\Run-Child` and an invented `Microsoft.PowerShell.SolFixture\Run-Child` each ran that path's `.ps1` from the current location, through a bare word, `&`, `.` and `Get-Command`, while `Microsoft.PowerShell.Utility\Get-Date` stayed the cmdlet beside a same-name fixture (Sol, pwsh 7.6.10; the module part matches in any case, so `microsoft.powershell.x\Run-Child` is the same). Rule: such a name is a cmdlet only when this session's `Get-Command -Module <module> -Name <name> -CommandType Cmdlet,Function` returns exactly that command (`Test-CiScriptShippedCmdlet`); otherwise it is a relative path, unresolved.
- 2026-11-21: PS-SCRIPT-SCOPE-LAYOUT-01. Two PowerShell traps the #740 round-2 worker measured while modelling how a script reads a variable. (1) A script's top-level `$c` looks like its own script-scope variable, separate from `$global:c`. It is not under `pwsh -File`: a `-File` script runs in the global scope (it has no parent), so `$c = 'a'; $global:c = 'b'; $c` reads `b` there, while the same file run with `&` reads `a`, and dot-sourced inside a function reads yet another scope (pwsh 7.6.10 and Windows PowerShell 5.1). A static reader cannot tell which way a file runs, so `Get-ScriptClosure` takes the value of every layout and refuses a read where they disagree. (2) `InvokeMemberExpressionAst.Arguments` is `$null`, not empty, for a call with no arguments, so `@($node.Arguments).Count` is 1 (PS-EMPTY-ARRAY-COUNT-01's shape). Rule: test `$null -eq $node.Arguments` before counting.
- 2026-11-20: PS-ARGUMENT-BINDING-01. A static reader of PowerShell invocations (the GUI selection's script walk, `scripts/ci-script-closure.ps1`) looks safe matching parameter names exactly and skipping what it does not know. It is not: PowerShell binds a unique prefix of a parameter name or of an alias (`-OutVar` is `-OutVariable`, `-v` is `-Verbose`, `Start-Job -LP` is `-LiteralPath`), so an exact matcher misses the parameter and reads its value as the code or file argument; a module-qualified cmdlet (`Microsoft.PowerShell.Utility\Add-Type`) is the cmdlet, while a qualified alias (`Microsoft.PowerShell.Utility\iex`) is not a command at all; `pwsh -in child.ps1` reads `-in` as `-Interactive` and runs the file; and Windows PowerShell 5.1 has no `-ConfigurationFile`, `-CustomPipeName` or `-SettingsFile`, so it runs the rest of such a line as code. Measured on pwsh 7.6.10 and Windows PowerShell 5.1 by the #740 round-2 worker, each against the cmdlet's own metadata or the host's own command-line parser. Rule: bind arguments the way PowerShell does (exact name or alias, else the unique prefix; common parameters included; switches take no value; `--` ends parameters) from tables generated from the cmdlets' metadata, and report anything that does not bind as unresolved rather than skipping it (`Get-ScriptClosure`'s binder, with its controls in `test/windows/gui-hidden-scripts.ps1`).
- 2026-11-20: PS-EMPTY-ARRAY-COUNT-01. A mutation control that counts a validator's problems as `@(Get-Problems ...).Count` looks like it fails when the validator finds nothing. It does not when the validator returns its list with the unary comma (`return , $list.ToArray()`): an empty list then arrives as one object, an empty array, and `@(...)` wraps it, so the count is 1 and the control passes against a validator that accepted the mutation. Measured on pwsh 7.6.10 (the #740 round-1 worker): `@(<function returning , @()>).Count` is 1. Found by CodeRabbit on #740 in Contracts.99-GuiHiddenSelection.ps1's workflow and plan mutation controls. Rule: assign the result first and test that variable's `.Count` (`$found = Get-Problems ...; if ($found.Count -eq 0) { ... }`), as Contracts.99-GuiHiddenSelection.ps1 and Contracts.99-GuiHiddenLaunch.ps1 (9f) now do; wrap with `@()` only a call that emits its items one by one.
- 2026-11-20: PS-ORDERED-INT-INDEX-01. In PowerShell, `$map[$pid]` with an int argument on an `[ordered]@{}` (an `OrderedDictionary`) uses its positional `[int]` indexer, not a key lookup. A set past the count throws `ArgumentOutOfRangeException` ("Parameter 'index'"), and a get returns the entry at that position. `.Contains(4321)` and an `[object]`-cast key still go by key.
  - Found by Greptile on #738 (r4646862899). `Get-ProbeDescendants` in `test/windows/gui-hosted-probe.ps1` keyed an ordered map by PID, so its first descendant threw, and every Q0 arm's driver would have failed.
  - Shown in pwsh 7, with no noctty:
    - `$d = [ordered]@{}; $d[4321] = 1` throws.
    - After two string entries, `$d[1]` returns the second value.
    - `@{}` and `[System.Collections.Generic.Dictionary[int,object]]` key by the int.
    - The probe's extracted function, run on synthetic rows, throws before the fix and returns the right keys after it.
  - Rule: key a map by an int (a PID, a thread ID, a handle value) only with `@{}` or `Dictionary[int, ...]`, and test it with `ContainsKey`. Use `[ordered]@{}` only for string keys. Where a record needs ordered int keys, key it by their strings.
- 2026-11-18: PWSH-CEQ-ICU: in PowerShell 7, `-eq` and `-ceq` compare strings in the invariant culture, and under .NET's ICU globalization a control character has no weight there, so a comparison of terminal bytes can pass with the ESC missing. Measured on pwsh 7.6.10: `"$([char]27)A" -ceq "A"` is True, and so is the same with BEL (0x07); `[CultureInfo]::InvariantCulture.CompareInfo.Compare` gives 0; `[string]::Equals(..., [StringComparison]::Ordinal)` is False, `String.Contains` and `-cmatch` are ordinal, and Windows PowerShell 5.1 gives False. Found in the reply-path harness's round 1, whose verdicts used `-ceq`; re-checked from the recorded hex with ordinal equality, none of its 116 and 122 predicted rows changed (the 2026-11-18 REPLY-PATH-01 entry in conpty.md). The membership operators compare the same way: on 7.6.10 `"$([char]27)A" -in @('A')`, `@('A') -contains` and `-ccontains "$([char]27)A"` and a `Where-Object { $_ -ceq ... }` all match (the council's round 2 measured them, and round 3 again; 5.1 matches none). Rule: compare bytes, escape sequences or anything holding a control character with `[string]::Equals($a, $b, [StringComparison]::Ordinal)` or a regex, never `-eq`/`-ceq`/`-ne`/`-cne`, `-in`/`-notin`, `-contains`/`-ccontains`/`-notcontains`, `Where-Object` with any of them, `switch` or `Compare-Object`, which use the same culture comparison.
