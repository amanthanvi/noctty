- 2026-10-30: A directory name is untrusted text in the OSC 7 that Git Bash's `ghostty.bash` and zsh's `ghostty-integration` write (GHSA-2r63-vmw6-3m3c, upstream 6eb24a0f0f38, #14859, ported in the 2026-10 merge window's shell slice, #616). This qualifies the 2026-10-14 PKG-17 entry in launch-and-paths.md: `cygpath -m` now also runs for a drive-mount directory whose `$PWD` holds a control byte. Four traps. (1) NTFS refuses C0 in a name (`CreateDirectoryW` returned 123, `ERROR_INVALID_NAME`, for 0x01, 0x07, 0x1B and 0x1F, and accepted 0x7F), yet Git Bash's `$PWD` holds raw C0 bytes: MSYS and Cygwin keep a control byte in a Windows name as U+F000+c and show U+F001-U+F01F as the byte. Measured with Git Bash 5.3.15 (MSYS 3.6.9) on directories PowerShell created: `cd` into `x` U+F007 U+F01B `]52;c;SGVsbG8=` U+F007 `y` cut the OSC 7 short at `/x` and sent a complete OSC 52, and `z` U+F001 `q` put a raw 0x01 inside the OSC 7. `cygpath -m` maps the bytes back to U+F0xx, so the off-drive branch was safe only by accident. Rule: in `__ghostty_precmd` a drive-mount `$PWD` with a control byte goes through the cygpath branch, and the final printf strips `[[:cntrl:]]` from `$HOSTNAME` and the rewritten `$cwd`; stripping `$PWD` before the rewrite would change what cygpath resolves. That branch gives cygpath `$PWD` itself, not the `$cwd` that lost its `/cygdrive` prefix: on standalone Cygwin `/c/...` is not a drive and resolves under the Cygwin root (inferred, no Cygwin here; `test/windows/bash-shell-integration.ps1` models it with a stand-in `cygpath`, and with `$cwd` the report was `/C:/cygwin64/c/.../zq`). The report names the real directory only for C0 in a UTF-8 locale, or with no `LANG` (when none is set, Git Bash's login shell sets a UTF-8 one in `/etc/profile.d/lang.sh`). Measured with `__ghostty_precmd` on scratch directories: DEL (which NTFS accepts) and, under `LANG=C.UTF-8`, a C1 such as U+0092 are stripped, so `a` DEL `b` is reported as `.../ab`, a directory that does not exist (before the port those bytes went out, and noctty's `osc_string` state takes 0x20-0xFF as payload, `parse_table.zig`); under `LANG=C` `cygpath -m` ends its answer at the control byte, so `z` U+F001 `q` is reported as `.../z`, which may be another, existing directory. Upstream strips the same `[[:cntrl:]]` set. zsh takes upstream's `print -rnu` with both stripped (not run: no zsh here). The native emitters (cmd's `$P`, Clink's `os.getcwd()`, elvish's `$pwd`, PowerShell's ProviderPath, which it also percent-encodes) pass a native cwd, which cannot hold C0 on a local volume; a remote redirector that passes C0 names through is unmeasured. (2) `cat -v` shows a raw BEL and bash's caret text alike as `^G`. From bash 5.2 a prompt prints the control characters of a `\w` expansion as caret text, so the `title` feature's `\[\e]2;\w\a\]` wrote the literal characters `^G^[` (byte dump), and a reading of `cat -v` output had called it raw. Dump bytes (`od -c`, Python `repr`). Bash before 5.2 prints them raw; upstream left that line as it is too. (3) Git for Windows' own prompt is not safe and is not noctty's: `/etc/bash.bashrc` sources `/etc/profile.d/git-prompt.sh` for a non-login shell (`/etc/profile` does for a login one), and its `\[\033]0;$TITLEPREFIX:$PWD\007\]` expands `$PWD` raw at every prompt (it sent the same OSC 52). noctty's injection sources `/etc/bash.bashrc`, and `bash --rcfile` runs it as SYS_BASHRC too, so a Git Bash tab with Git's default prompt stays exposed through its title; `test/windows/bash-shell-integration.ps1` replaces `PS1` before it tests noctty's emitters. (4) Harness traps: Git Bash started in `%TEMP%` without `PWD` has `$PWD=/tmp/...` (Git mounts TEMP there), which takes the safe cygpath branch, so pass the Windows `-StartPwd` and check the start is `/c/...`; a `HOSTNAME` holding an ESC cuts every later OSC 7 body at that ESC and hides a control byte in the path, so change it after the path case; and `Get-Osc7` returns one flat host/path pair when a single report matches (PowerShell unrolls a function's output), so wrap the call in `@()`.

- 2026-09-14: OSC 133 D in `integration.ps1` cannot decide an exit code from `$?` plus `$LASTEXITCODE` alone — two native commands failing with the SAME code look exactly like a cmdlet failing after a native one, so `cmd /c exit 5` twice marked `D;5` then `D;1`. The tiebreaker is the HEAD of `$Error` by reference identity (`[object]::ReferenceEquals`), re-snapshotted at the very END of `prompt`; never `$Error.Count`, which freezes at `$MaximumErrorCount` (256 on 5.1) and drops to 0 on a user's `$Error.Clear()` while the head keeps changing. Four measured traps. (1) `$Error[0]` on an EMPTY `$Error` throws `ArgumentOutOfRangeException` on both hosts under StrictMode 3.0+ — the hazard is the out-of-range ARRAYLIST INDEX, not an unset-variable read, so `Set-StrictMode -Off` quietly yields `$null` for the same expression and casual testing without StrictMode will not see it — and the throw is itself recorded in `$Error`, so swallowing it still leaves a record where the user had none; guard on `.Count -gt 0`. Relatedly, `$Error` does not hold only ErrorRecords and the two other shapes want opposite answers: a parse error typed at the prompt is a bare `ParseException` (a PowerShell-level failure, on BOTH hosts), while `$ErrorActionPreference = 'Stop'` pushes an `ActionPreferenceStopException` AHEAD of the record it stopped on — so with `$PSNativeCommandUseErrorActionPreference` also true the head hides a perfectly good `ProgramExitedWithNonZeroCode`. Unwrap one level through `.ErrorRecord`, which both inherit from `RuntimeException`, rather than rejecting non-ErrorRecords outright. Classify natives by `FullyQualifiedErrorId`, never by exception type: `RemoteException` is the 5.1 redirected-stderr record's exception but also every failure deserialized out of a job or remote session, so `Start-Job { throw 'x' } | Receive-Job` after a native failure re-reported the native code.
