- 2026-10-31: Settings shows where each saved value comes from through `config.origin` (#631). Traps:
  1. The labels are owner-drawn (`SS_OWNERDRAW`, painted in the viewport's `WM_DRAWITEM`), not subclassed. Every Settings text `STATIC` with a UIA provider is subclassed by `settingsTextProc`, which forwards to one shared previous procedure (`text_uia_prev_proc`). A second subclass on the labels would make that procedure differ per window, and `attachTextUiaProvider` then refuses the provider.
  2. `origin.of` reads `_replay_steps`. A value written into a config in memory leaves no step: a Settings draft, `finalize`'s choices, or `useSavedValues`' file `default-profile`. So the origin of a value Settings shows has to go through `win32_settings_reference.savedOrigin`, not `origin.of` directly. The masked-save status is the exception: it names what is in effect after the reload, so it uses `origin.of`.
  3. `finalize` does not set `click-repeat-interval` under tests, so a test of a derived origin must pick its key from `resolved_when_unset` and check that one is derived, not name one.
  4. A test fixture that reloads from disk must not `errdefer` the reloaded config once it is assigned to `fixture.config`: returning `error.SavedButMasked` runs the errdefer, and `finish` frees it a second time.
  5. `zig build test -Doptimize=ReleaseFast` still builds the test executable in Debug (`build.zig` pins it); a ReleaseFast cost needs the test's optimize mode changed in a scratch tree.
  6. A diagnostic at a line does not always mean the line did not parse: `finalize` notes problems at a value's own line (`default-profile`, `profile-order`, `profile-hidden`) after it parsed.
  7. The replay log's order is not always the order that decides.
     - `finalize` puts the command line's `command`, `initial-command` and `default-profile` back over a file read after the command line.
     - Lines of the `Repeatable*` types, `Keybinds`, `Palette` and the profile maps *can* add up, but not always. An empty value resets by each field's own rule: `font-family =` clears the families, while `keybind =` and `command-palette-entry =` put the defaults back. `keybind = clear` clears every binding, a command-line `font-family` replaces earlier families, and a later entry for the same key replaces an earlier one. So the log alone does not show that an earlier line still contributes.
     - The `-e` marker is recorded before the loader checks that a command follows; an `-e` without one sets nothing.
     - `finalize` folds `gtk-single-instance` into `single-instance` and copies the result back: each key holds its last accepted assignment, a reset to `detect` included, and `single-instance` wins unless it holds `detect`. It also layers every `--elevated-profile-env=` it took over `env` after all files.
  8. The files `config-file` names are read after the command line, and only a replay (a theme, a new conditional state) puts `-e` last. So whatever the command line must win over an include has to be applied again in `finalize`: `finalizeCliLaunch` does it for `--command` and `--initial-command`, and `finalizeECommand` for `-e`.
  9. A line of a config file that names a key may not have set it: the loader may have refused the value, or the file may have changed since it was read. A line holds what the loader took only when its text, read through `cli.args.LineIterator`, is the argument the log recorded at that line number; matching the line number alone is not enough (`settings_reference.TargetLines`). What the loaded config holds (whether a key the app works out was set, in any layer) comes from the log, not the file as it is now, nor from whether that file can be read now. And asking `origin.of` about every key of a config with many refused lines needs `origin.Index`: the free functions scan every problem for each step. Only the winning step is classified as an included file (`Candidate`): `included` passes over every `config-file` name, which the list keeps however often it is given.
- 2026-10-30: D26 9.5 part 2 (opacity trackbar, number up-downs). Six traps.
  1. **A trackbar shortens its thumb in a short window** unless it has `TBS_FIXEDLENGTH`. Measured on comctl32 5 and 6: the thumb is anchored 2 px below the top, and its length is 4 px at 1 px tall, 10-12 px at 16 px, and 19 or 22 px from 24 px up.   5. **The stock UIA proxy gives an up-down no value.** It is a Spinner without RangeValue or Value; the buddy field carries the value. A trackbar is a Slider with RangeValue in its own units (0..100 here).
  6. **A Reset button an edit makes is shown before any layout.** `syncDefaultMarks` shows it straight from `takeResetButton`; only a page switch leaves it hidden for `layoutChildren` to place. Any change to a row's geometry has to reach `takeResetButton`'s placement too.

- 2026-10-29: SETTINGS-KEYBIND-LIST-NITS. Four traps.
  1. **A RuntimeId and availability have to agree.** `PaletteRowProvider` used the row id as its RuntimeId but checked it only at the index it was made at, so a held row died when its item moved, while a fresh provider for the same item answered with the same RuntimeId. `available()` now finds the id in the list and follows it; ids that are positions behave as before.
  2. **Check that a clip case can happen before asserting it.** At the Settings window's least height and furthest scroll, the Keybindings list lies wholly inside the viewport, so a test waiting for the viewport's top edge to cut a row would wait forever.   3. **A binding's text is not its identity.** `Trigger.format` prints only Super, Ctrl, Alt and Shift, while the binding set keeps `caps_lock+ctrl+f12` and `ctrl+f12` apart, and `Trigger.hash` drops the locks too (`Mods.binding`). An id, a `differs` mark or a followed selection keyed on the text, or on `Trigger.hash`, aliases two bindings. Compare with the set's own equality (`Trigger.foldedEqual`, `Action.equal`), use a hash only to find candidates, and hand an old id only to an equal binding.
  4. **A hash that finds candidates must agree with the equality that decides.** `Action.hash` hashes a float parameter's bits while `Action.equal` compares it with `==`, so `0` and `-0` are equal but never meet in a hash lookup; and NaN is not even itself under `==`. - 2026-10-26: Settings search (D26 9.3): a Ctrl+F field in the header narrows every page to the rows whose name, label, caption, help or keywords hold every word typed, and `@modified` to the rows 9.2 marks. Nine things worth knowing. (1) USER room. 9.2 left the worst case at 100 USER objects over the process baseline (every Windows-supported field changed, every section visited, a row menu open), the budget exactly, and the search field is one more window in every state. Lazy creation does not help there: the worst case is a state that shows the windows. Two windows that are never shown together can be one: the status line's window now also says the close prompt's question (`syncClosePromptText`, `restoreStatusLine` gives the line back with everything that changed meanwhile), and one "Discard changes" serves the action bar and the prompt. It moves in z-order, which is Tab order, after "Save and close" while the prompt is up and back after "Use disk" when it goes (`placeDiscardButton`). It must also take the prompt's own id (`BTN_CLOSE_DISCARD`) while the prompt is up: UIA Invoke posts `WM_COMMAND` with the id the button has when it is invoked (`postButtonClicked` in `widgets.zig`), so with one id two Invokes queued on the bar's Discard opened the prompt and then confirmed it, discarding the draft without a confirmation anyone heard (Greptile caught it; the test queues two Invokes, then pumps). Its enable rule follows the prompt (`updateClosePromptActions` enables it only while the prompt is visible; enabling it there in the normal state disabled the bar's button and failed twelve tests). Measured on a ReleaseFast portable copy: 99 with the menu open, also with `@modified` typed (main 100). (2) The search is a filter on `formItems()`: everything that lays out, shows, hides, marks or hit-tests a page's rows reads that list, so the found rows are laid out compactly and the others are hidden like another page's rows. Hidden windows are absent from the UIA raw tree (measured: 51 elements, 30 after a search that keeps three rows; their labels, fields and Reset buttons are what left) and from Tab. Reset buttons follow the shown rows through the 9.2 pool, so a search never adds windows. (3) The per-keystroke cost is O(all rows) matching plus showing, hiding and laying out the shown page's rows, and at about 200 rows the window manager's per-window work is nearly all of it. Measurement-only builds with 170 synthetic label/checkbox/Reset rows (201 in all) put the search pass at p95 21-30 ms spread over the pages and about 100 ms with 181 rows on one page, against a 16 ms budget: matching was 0.03 ms, and `ShowWindow` on one row window at a time cost about 0.2 ms a window with 450-600 sibling windows.
