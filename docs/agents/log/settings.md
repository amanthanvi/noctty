- 2026-10-11: Settings file safety (PKG-21: G004-G006, G008, F083), re-verified on d2a23196b before changing anything: G004's `-e` half had been fixed by #305, F083's wrong label survived #324, the rest held. (1) The save target scanner and the loader disagreed beyond `-e`, found by feeding the loader's own `loadIter` the same argv. `--config-file x` is NOT an option (the loader gets `ValueRequired` and an "invalid field" for `x`, and loads nothing), `--config-file=` clears the list, `--config-file=?x` and `="x y"` carry an optional marker and quotes that `Path.parse` strips, and a bare `--` ends nothing (`--config-file=b` after it is still read). `cliConfigFileOverrideArgs` now runs each value through `RepeatablePath.parseCLI`, stops at `-e` and at `-Embedding` like `Config.parseManuallyHook`, and a differential test asks the loader; this supersedes the separated-form statements in the 2026-04-17 `cliConfigFileOverride` entries. `win32_elevation.buildRelaunchParameters` still stops at `--` and reads the separated form; it was left alone. (2) A save writes where the configured name leads (`win32/save_target.zig`): `CreateFileW` with no access plus `GetFinalPathNameByHandleW`, stripping `\\?\` and `\\?\UNC\` (kept when the plain path would pass 230 characters, since `ReplaceFileW` and `MoveFileExW` take the path as written and no manifest here opts into long paths, and kept when a component ends in a dot or space or is a device name such as `nul` or `com1`, because Win32 normalization turns `config.` into `config`: stripped, a save through a link to `config.` replaced the sibling file; found by Greptile, tested on disk). A symlinked config keeps its link, a chain of links is followed, and a first save is the name itself. `nNumberOfLinks > 1` marks a hard-linked file, which is rewritten in place because a replacement would leave the other names on the old bytes. That rewrite opens without truncating (creating over a hidden or system file fails with access denied), is not atomic, and keeps the synced temp copy, with its path in the log, if it fails after the first byte. The open fails with not-found for both a first save and a dangling link, so `GetFileAttributesW` on the name (it does not follow links) tells them apart, and a dangling link is refused (`DanglingLink`, with its own status note) instead of replaced. Anything the final-path query cannot answer (some redirector and RAM-disk volumes, a name with a lone surrogate) leaves the name as it was, so a save that worked before still works (which also means a link on such a volume is still replaced). The hard-link rewrite writes before it truncates, so a disk-full failure in the middle of a longer text leaves new bytes followed by the old tail, with the complete copy kept and logged. Tests make links with `CreateSymbolicLinkW(.., SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE)` and skip on `ERROR_PRIVILEGE_NOT_HELD`; std's `Dir.symLink` was not tried (it creates the link through NT, which wants the privilege enabled). (3) Windows PowerShell 5.1 writes UTF-16LE with a BOM for `>` and Out-File. `Config.loadReader` parsed it as NUL-separated bytes (nothing set, nothing said) and a save appended UTF-8 lines to it. The loader now decodes a FF FE or FE FF file (a warning is logged; an odd trailing byte is dropped); a file that is not valid UTF-16 is skipped WITH A DIAGNOSTIC instead of returning an error, because `loadRecursiveFiles` does `try loadFsFile` and one bad included file would otherwise end the whole config load. A save refuses (`UnsupportedEncoding`, nothing written) any file that starts with a UTF-16 BOM or contains a NUL byte, which also catches UTF-32 and BOM-less UTF-16; ASCII-compatible text (UTF-8 with or without BOM, a legacy code page) is still patched line by line, byte for byte. When launched with `--config-file custom.conf`, `target_path` resolves to `custom.conf` (via `cliConfigFileOverride` → `absolutizePath`); loading the default search path would overwrite the custom file with defaults + GUI edits only, silently dropping every key that existed only in the custom file. `loadFile` tolerates a missing target (first-save case) via an `error.FileNotFound` catch → proceeds with the default-only baseline. `realpathAlloc` is banned for this specific path-resolution because it `CreateFileW`s the target — fails before the first save writes the file.
- 2026-04-17: Settings save writes to the **active** config file, not always the per-user default. `cliConfigFileOverride(alloc)` scans process argv for `--config-file <path>` (and `--config-file=<path>`); when set, the save path targets that file via `std.fs.realpathAlloc`. Falls back to `config_edit.openPath` for the no-override case. If a user launched `noctty --config-file custom.conf`, saving in the settings UI updates `custom.conf`; writing to the default would either edit the wrong file or get masked on reload by the CLI-provided config.
- 2026-04-17: `patchOrAppendEdits` replaces only the LAST matching key line per file, not every occurrence. `Config.loadRecursiveFiles` takes the last value when a key appears multiple times, so updating only the last occurrence preserves intentional earlier overrides (e.g. a user who had two `font-size = 12` entries deliberately — one in a theme block, one overriding — keeps the first line untouched). Pass 1 scans for last-match indices, pass 2 emits with replacements only at those indices, pass 3 appends keys that never appeared.
- 2026-04-17: Settings save is surgical — `patchOrAppendEdits` reads the raw target file text, replaces only the GUI-edited key lines, and preserves everything else byte-identical: comments, blank lines, relative `config-file` paths (not canonicalised), and fields we don't round-trip through the Config type (RepeatableString et al). Line match: trim-left → key before `=`, with `#` / `;` / empty-line comments skipped. Duplicate key lines in the source are all replaced. User-edited keys not in the source are appended at the end. This supersedes the old `FileFormatter`-based full-rewrite which canonicalised relative paths on every save.
- 2026-04-17: Settings save emit loop force-emits GUI-edited fields even when their value equals `Config.default()`. Without this, resetting a field that an included `config-file` sets to a non-default value (e.g. `window-theme = dark`) back to the stock default in the GUI would silently fail — `FileFormatter(.changed=true)` would drop the reset line and the include would re-apply its non-default value on reload. Implementation: track the GUI-edited set via `std.StaticBitSet` keyed on `Config.Key`, and in the per-field emit loop emit when `(is_user_edited or differs_from_default)`. The hand-rolled loop replaces the `FileFormatter` call for settings saves; the formatter is still used by the CLI's `+show-config` path and by doc generation.
- 2026-04-17: `settingsSaveAndReload` post-save validation: after `Config.load()` returns the refreshed config, walk the `user_edited` bitset and compare `pending.changed(&reloaded, key)` for each GUI-edited field. When any masked field is found, return `SaveError.SavedButMasked` — distinct from generic write failures. `SettingsWindow.save` catches this variant and emits a warning toast ("Settings saved — some values are masked by a later config-file layer") instead of a plain success, so users understand their edit IS on disk but the effective runtime value doesn't match.
- 2026-04-17: `cliConfigFileOverride` picks the LAST `--config-file` occurrence, NOT the first. `Config.loadRecursiveFiles` applies files in argv order and later files override earlier ones; writing to the first file when a later one also sets the same key would make the save masked-on-reload. The `while` loop advances past the path argument with `i += 1` after matching the separated form so a path that happens to start with `--config-file` doesn't get mistaken for a key.
- 2026-04-17: Settings save failure preserves the pending draft — only the success + SavedButMasked paths call `clearPending` + `adoptCurrentConfig`. Real errors (`TempCreateFailed`, `ReplaceFailed`, `ReloadFailed`, `PathResolveFailed`, `SerializeFailed`, `OutOfMemory`) log a warn and leave `pending` intact so the user can retry without losing their edits. This guards against losing edits on transient disk errors such as AV sharing violations or an external editor holding the file open.
- 2026-04-17: Settings save short-circuits when `user_edited` bitset is empty — no-op saves don't touch the filesystem. Pressing Save without any edit on a first-run machine (no existing config file) previously created a zero-byte file that fired `error.FileIsEmpty` warnings on every subsequent load; the short-circuit prevents that and also avoids needless mtime bumps on existing files.
- 2026-04-17: `settingsSaveAndReload` uses `@import("../config/key.zig").Key` to access the Config key enum — `configpkg` does not re-export `Key` at module root. The inline-for field walker in the save path is the single consumer of this import; if that helper moves to another module, relocate the import with it.
- 2026-04-17: `settingsSaveAndReload` writes `FileFormatter{ .changed = true }` — only fields differing from `Config.default()` land in `ghostty.conf`. This is load-bearing for two reasons: (1) prevents bloating the primary file to hundreds of default lines on the first click of Save; (2) future upstream default changes still take effect on fields the user didn't explicitly edit. The save-path baseline (`file_cfg` built from `default() + loadDefaultFiles`) + copy-only-edited-fields patch still applies; the formatter's `changed` flag is the second line of defence.
- 2026-04-17: `settingsSaveAndReload` calls `makePath(dirname(target_path))` before creating the sibling temp file. `config_edit.openPath` guarantees the default-path parent exists; CLI overrides to arbitrary paths do not, so the first Save to `D:\new-project\custom.conf` would otherwise fail with `TempCreateFailed` even though the user expectation is that Save creates whatever it needs.
- 2026-04-17: `settingsNotifySuccessThunk` has two visible channels: (1) always tries `showHostBanner(.app, .info, "title: body")` — local chrome feedback for a user-initiated Save action, NOT gated on notification config because users expect confirmation of their own clicks; (2) conditionally fires `showDesktopNotification` gated on `app-notifications.config-reload`, or when no host banner rendered. Without channel 1, disabling config-reload notifications made settings saves completely silent.
- 2026-04-17: `settingsNotifySuccessThunk` falls through to the non-modal `showDesktopNotification` fallback when `showHostBanner(.app, …)` returns false (no host surface — settings window is the only UI). Without the fallback, combining `app-notifications.config-reload = false` with a settings-only state produced a Save that succeeded silently in every observable channel.
