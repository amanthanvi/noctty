- 2026-10-15: A typed key no longer presents a frame ahead of its echo (LAT-02). `keyCallback` queued a render for every key that typed, though only a dropped selection or a jump back to the bottom changes the screen; the echo arrives as output, which wakes the renderer itself. On a vsynced display the keypress frame takes the next refresh and the echo shows a refresh later. `dropSelectionAndScrollForTyping` and `scrollToBottom` (also behind the text/csi/esc/cursor_key bindings and paste) now redraw only for what they changed. Measured with LAT-01's harness under its emulated 60 Hz present (a model, not a display): local echo 25.85 ms median / 33.17 p95 on main, 8.80 / 16.66 after; presents while typing fell from 2-3 per key to 1. Four traps. (1) That frame masked an older gap. termio wakes the renderer after output only for dirty state (#8), and moving the cursor within its row marks nothing dirty: BS, CUB, CUF, CHA, and CUP to the same row, which `Terminal.setCursorPos` sends through `cursorLeft`/`cursorRight` (a move to another row goes through `cursorChangePin`, which marks rows). DECSCUSR, DECTCEM and OSC 10/11/12 mark nothing either. Such an echo (Left at a prompt echoes a BS) was drawn by whatever frame came next: on main an arrow's echo 30 ms late reached the display at a median 113 ms, carried by the next key's keypress frame; with that frame gone it waited for the blink timer (median 243-326 ms), and with a steady cursor it would wait for unrelated output (inferred). The renderer now records `render_dirty.Undirtied` (the cursor's place and look, the default colors) at each frame update in `renderer.State.drawn_undirtied`, and termio's output wake and the render follow-up count a mismatch as work (`needsFrame`), so it stays pending across reads, synchronized output included, until drawn. A frame woken by OSC 10/11 still redraws only dirty rows' cells, an older renderer gap (inferred from the code, not run). (2) Every change of the binding mods set `dirty.clear` and redrew the whole screen, a frame for each Shift and Ctrl press. Mods only decide link highlighting, which needs `renderer_state.mouse.point` (set by `mouseRefreshLinks` only while a link is under the pointer, and now cleared when it finds none) or an `always_mods` link, so `modsChanged` checks that first. `keyCallback` compared the raw event mods with the binding-reduced mouse mods, #134's trap again: with Num Lock on, every key ran the link refresh ahead of its pty write and, in a mouse-reporting app, queued a frame. (3) libxev's IOCP loop runs a due timer before the async wakes of the same pass, so output reached the 8 ms render follow-up before its own wake: the follow-up drew it, the wake found the paint slot reserved, and its retry presented the same frame again (every other key or so; about 285 of 930 presents in 10 s of a 60 fps animation). The follow-up now leaves dirt to a recorded wake (`wakePending`), and termio records `io_output` under the lock, before the renderer can see the state. (4) Under pacing (power saver), a frame update put off that was not dirt (a scroll, a blink) was dropped by the follow-up, which only looked at dirt. It now carries one, except while the custom-shader draw timer runs: that timer carries it (#297), and a follow-up that also tried would re-defer at every slot the timer took and keep it doing full frame updates. Harness traps: `lat-echo` writes each byte separately and wraps after 60 echoed bytes counting escape bytes, so an `ESC[D` echo can arrive in three reads with CR LF inside the CSI; that, and the 500 ms blink-reset wake riding on a lone ESC, is the tail of the arrow-key numbers. From Git Bash, `cmd //c "start \"\" /belownormal /wait /b cmd /d /c \"\"x.cmd\" ...\""` reached cmd with broken quoting and sat idle with no child and no log; put the `start` in a `.cmd` wrapper called by full path. And stopping the agent's background `bash script.sh` task reported success while the script kept running its remaining steps (their logs were stamped minutes later, alongside the next run); check by PID that every process of a stopped run is gone before starting another.

- 2026-10-10: A synchronous (`update_now`) renderer paint inside `App.drainMailbox` can starve the UI thread for seconds. The drain pops until the mailbox is empty, and an `update_now` paint blocks in SwapBuffers until vblank before it releases the surface's repaint reservation. Whenever a present takes longer than the renderer's frame interval (a 60 Hz monitor against the 8 ms animation timer or the output follow-up burst, or heavy output at any refresh rate), the renderer usually queues the next frame before the drain looks again. Drains then run back to back. Every mailbox push also posts a `WM_WINHOSTTY_WAKE`, and posted messages outrank input and WM_TIMER in `GetMessage`, so the WAKE backlog grew faster than the pump retired it. Sent messages still got through whenever a drain lost the race (WM_NULL probes were answered every 50-300 ms), but posted keys, WM_CLOSE and WM_TIMER waited behind the backlog for seconds. Settle mode (`resize_settle_*`) is the only state that makes renderer frames `update_now`, and it ended only on its timer's last WM_TIMER, so it sustained itself. Measured: 1-22 s stalls after a resize, maximize or drag under heavy output on a 240 Hz panel. A local reproduction of the startup freeze described in #297, with no user resize: an animated custom shader on a 60 Hz display never drew typed input, because a WM_SIZE during window creation starts settle mode (about 40 synchronous paints at launch on a 240 Hz panel). The reporter's battery hardware and nu shell case remain unverified. Two bounds now hold it. The hard one: settle mode also ends at a deadline (`resize_settle_until_ms`), so a starved WM_TIMER cannot extend it. The practical one: a core-app tick spends at most one synchronous renderer paint (`rendererTickRepaintMode`), and later frames in that tick queue an invalidate, whose WM_PAINT ranks below input, so the WAKE backlog cannot grow. Bounding the drain to the messages present at entry would not have been enough on its own, because the WAKEs from the renderer's pushes still outrank input. This corrects the 2026-04-29 entry below that says renderer `.render` actions must paint `update_now` outside live resize: since #8 they queue except during settle. Measured generation-advancing presents for 30 and 60 fps TUIs were comparable before and after: their count was near the emitted-frame count at 240 Hz, and the count/emitted-frame ratio was 0.87-0.98 for 60 fps at 60 Hz. This is a proxy, not a unique-frame survival measurement: the observation window includes command and prompt output, and multiple presents can accompany one emitted frame. The run-to-run spread was measured; a refresh-phase explanation remains inference. Two harness traps. A surface on a `CreateDesktop` desktop does get keyboard focus (render trace `surface_focused=true`), so it takes the focused 8 ms cadence even though `GetForegroundWindow` never returns it there. And `pwsh -File` does not treat single quotes as quoting: a config line with spaces passed through a hidden-desktop driver arrives split (`'unfocused-render-fps`) and is silently ignored, so pass `key=value` without spaces.
