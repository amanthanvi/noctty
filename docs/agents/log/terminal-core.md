- 2026-10-20: Kitty graphics placements follow a scroll through `ImageStorage.scrollMarginsBegin` and `ScrollMargins.end` around the row operation, not through pin tracking alone (KITTY2 part 2, ports of upstream `90bce0d2dd3b`, `b8222f4a8403` and part of `6760c6482be2`). Measured on main with new tests (16 failing, upstream's included): with DECSTBM margins `eraseRowBounded` moved a pin on the region's top row onto the row above the region, `deleteLines` and `insertLines` (SU with a top margin, SD, RI at the top) move no pins at all, and placements straddling or outside the region were dragged; on a screen without scrollback (the alternate screen, `scrollback-limit = 0`) `cursorDownScroll`'s `eraseRow` left the pins of the discarded top row on row 0, so every image that reached the top stayed drawn there; and ED 3, a shrinking resize of a screen without scrollback, or a shrink that cannot pull scrollback (every Windows session) moved the pins of erased rows onto rows that remain without marking them garbage (`PageList.eraseRows`, `erasePage`, `eraseTrailingRows`), drawing those images there. Rules. (1) Upstream's `kittyScrollMarginsBegin` returns null for every full-screen scroll because "placements follow their anchored rows via pin tracking"; that holds only for a scroll up on a screen with scrollback (still upstream main's code on 2026-10-20). The fork returns null only there. Elsewhere every image moves with the text, as kitty's marginless `scroll_filter_func` moves it, the part above row 0 is clipped because a pin cannot sit above the screen, and an image whose anchor row leaves the screen is deleted, where kitty keeps it off screen. A scroll can therefore delete a placement and free its pin: read what you need from a placement before anything that scrolls (`display()` read `pin.x` after its cursor-movement `index()` calls, a use after free on a one-row screen without scrollback, found by Greptile). (2) `clipTop` and `clipBottom` compute the crop from the drawn height (`calculatedSize`), so a y offset is blank space, not image rows: upstream's crop of a whole cell row, run against the same test, cropped 10 px where 5 is right. They change only the source top and height, which `prepKittyPlacement` in `renderer/image.zig` reads (`sourceRows` mirrors it). Without a row count the drawn height follows the source height, so `clipTop` crops at least one source row when the clip covers image pixels: an enlarged image's crop rounds down to zero, and it then stayed drawn whole at the top through every scroll. (3) A row operation that moves rows must sit between begin and end with the matching `ScrollOp`: `window_shift` when it can move pins outside the region rows (`cursorScrollAbove`, which reaches `grow` or `eraseRow`), `in_place` otherwise. Kitty scrolls images for IND, RI, SU and SD and never for IL or DL, so wrap `scrollUp` and `scrollDown`, not `deleteLines` and `insertLines`. (4) Rows are erased on three paths, and the placements anchored in them must go: before `Screen.eraseHistory` (ED 3) and the no-scrollback branch of `Screen.resize` erase the history, they call `ImageStorage.deleteInErasedRows` beside `semantic_command.invalidateRange`; and `PageList.eraseTrailingRows` (from `keepRowActive`, fork-only, when `resize_pull_scrollback` is off) marks the pins it moves garbage, after which `Screen.resize` calls `removeGarbagePlacements`. A test of a placement deletion must also check `countTrackedPins()`: dropping the release in the scroll path failed no test until those checks were added. `SemanticCommand.invalidateActiveTopRow` handles the same `eraseRow` trap for prompts. Trap, read from the code: `pointFromPin(.history, pin)` does not stop at the end of the history and returns a point for an active pin too, so test "is in the history" with `pointFromPin(.active, pin) == null` or `Pin.isBetween`. (5) Retransmitting an image ID deletes all of its placements (`addImage` through `deleteById`), as the protocol's note requires. `addImage` counts the replaced image's bytes as freed and excludes that image from eviction: crediting without excluding would evict the image being replaced as well and leave the total over the limit. `evictImage` stops at `>=`. This qualifies traps (2) and (3) of the 2026-10-19 KITTYPIN entry ("A Kitty graphics placement's tracked pin is released only by...", proposed in #500) in this file, and a sentence of the 2026-10-11 PKG-14 entry in `conpty.md`; see the corrections below.
- 2026-10-20: Kitty graphics placement geometry is program input (KITTY2 part 1, ports of upstream `e5840bb9bacd`, `d866fa455385` and `bcbc93a6b9cc`). `ImageStorage.Placement` columns, rows, source width and height, and pixel offsets are u32 values taken straight from the APC command, and main used them unchecked. Inferred from the loop, not run: with the default cursor movement (`C=0`) `display()` called `terminal.index()` once per placement row, so `c=1,r=4294967295` meant about 4.3 billion calls on the IO thread under the renderer state mutex (a 1000-row placement on a 5-row screen measured 1001 rows in total). - 2026-10-06: The typeahead inference for cmd (#269, #273, `SemanticCommand.markPromptStart`) was gated on `output_mark_seen`, set by any C mark and never cleared, so a cmd tab that had ever run WSL bash, pwsh or Clink lost the inference for good and a shell started there from a typed-ahead line kept cmd's `redraw=0`. Four review rounds, three of which overturned the previous fix; the rules they left. (1) The handoff case, a line typed ahead while bash or PowerShell runs `exit` back to cmd, is fixed by no longer gating `new_prompt` on the flag; nothing else touches a line typed after the C. Every variant that instead dropped the count at the next prompt after a C (a per-cycle flag) failed it, and the first tests for it ran `ping -t x` in cmd before the typed-ahead line, so they exercised cmd's second prompt and passed on such a version; a test named for a handoff has to put the line in the handoff window (and `exit` typed, not Ctrl+D: bash writes no C for that, and the typed line closes its still-open prompt). Zeroing the count at the C itself only cost the lines submitted before it, `exit` and `nu` pasted at a nested pwsh prompt, so that zeroing is gone too. (2) "A D outside a prompt drops the count" on its own is a regression: noctty's PowerShell integration without PSReadLine (PowerShell drops it under a screen reader) writes D and `A;redraw=0` for every prompt and never a C, so that rule switched the inference off for a shell that needs it.
