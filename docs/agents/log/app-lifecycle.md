- 2026-10-23: Action Center clicks reach noctty through a COM toast activator (#528, NOTIFY-3). An unpackaged app's toast keeps its in-process `Activated` handler only while the popup is up; a click on its Action Center entry is delivered by COM to the class named by `CustomActivator` under `HKCU\Software\Classes\AppUserModelId\<aumid>` (or the shortcut's ToastActivatorCLSID), whose `INotificationActivationCallback::Activate` gets the launch string. `src/apprt/win32_toast_activator.zig` implements it with static objects (COM may hold a proxy past revoke) and only copies the string into the same channel the popup handler posts to; an installed, non-elevated, non-handoff, non-safe-mode copy registers it (`toastActivatorWanted`, `shouldRegister`) and `registerAumidDisplayName` writes `CustomActivator` for the same copy, inside that function so the measurement patch's early return skips it; `dist/windows/noctty.iss` registers the CLSID's `LocalServer32` and the shortcut property, and uninstall removes the user's value. Six traps. (1) COM appends ` -Embedding` to every `LocalServer32` command (LocalServer32 docs), so a cold click starts `noctty.exe -ToastActivated -Embedding`, which `isEmbeddingProcess` alone reads as a default-terminal handoff server: decide with `ComStart.ofArgs`, and every argv scanner that stops at `-Embedding` (`Config.parseManuallyHook`, `cliConfigFileOverrideArgs`) must stop at `-ToastActivated` too. (2) The cold start learns the launch string only from `Activate`, after it registers the class, so `run` pumps for it (`awaitColdToastActivation`, a `MsgWaitForMultipleObjectsEx` deadline of its own, never a timer whose failure would make the wait endless) before it decides to forward; it then forwards that string alone (`coldToastForwardArgument`), because its own argv would open a plain window in the running instance, and first calls `AllowSetForegroundWindow` for the pipe server's pid: COM's foreground right belongs to the forwarding process, which exits. (3) A toast's window, tab and surface ids mean something only in the process that showed it, and COM hands a click to whichever process registered the class or starts a new one, so launch strings carry `pid=` and `resolveToastActivationSurface` presents the primary window for a foreign or absent pid. (4) One popup click can arrive through both routes: `RepeatFilter` (2 s from the first arrival, the last 8 targets, so a click on another toast in between does not reset it) guards the message-window arm and the forwarded-IPC arm. (5) A running App may have no surface (`initial-window = false`, `quit-after-last-window-closed = false`): parking the activation in `pending_toast_activation` alone waits for an unrelated window, so `receiveToastActivation` also pushes `new_window` to the core mailbox once `startup_windows_opened`. (6) `Activate` runs only when the STA dispatches messages, so a call COM queues while `run` does pipe I/O waits for the next pump; keep the stretch between the cold wait and `startToastActivator` free of message pumps. Testing: drive `Activate` through `win32_toast_activator.testCallback()` with `toastActivatorSink(app.delivery.?)` bound to a TestSession App's real message window; never call `register` in a test; `noctty.iss` is readable in tests as `@embedFile("noctty_iss")` (test-only anonymous import in build.zig); and a Pascal `{ }` comment line in `[Code]` that starts with `[Section]` is a section tag to ISCC ("Invalid section tag"). - 2026-10-11: `session-state.json` has one owner per user profile: the process that was eligible to restore it (`sessionRestoreEligible`), took `session-state.json.lock` (an exclusive byte-range lock held for the process lifetime, so a crash frees it) and then got its first window. `sessionStateEnabled`, the gate every save goes through, is `session_owner != null` plus the restore policy. Before this, every process that ran `terminate` saved, and with no hosts `saveSessionState` deleted the file (since the 2026-10-19 #497 entry no save deletes it). Measured on 88fef4f3f with portable copies on a hidden desktop: a second plain launch that forwarded to the running primary deleted the file while the primary ran; an idle `-Embedding` handoff server deleted it on its 5 s idle exit; a `--single-instance=false --working-directory=C:\Windows` window (the installer's "Open noctty here" verb) overwrote a 2-window session with its one `C:\Windows` window; and a second `single-instance = false` launch restored the same 2 windows again. Sign-out, shutdown and reboot never saved, because Windows may end the process after WM_ENDSESSION(TRUE) without `GetMessage` returning, so `terminate` never runs. `hostWindowProc` now saves on WM_ENDSESSION(TRUE), as Windows Terminal's `WindowEmperor` does (a sign-out's WM_QUERYENDSESSION answers TRUE; a Restart Manager close is answered as the 2026-10-23 RMCLOSE-1 entry says), and checkpoints on WM_DISPLAYCHANGE through a posted `WM_WINHOSTTY_SESSION_CHECKPOINT`, at most once a second. Six rules. (1) Ownership is set only after the first window exists (`run`), so an error out of restore or the first window leaves the file alone and no save runs while a restore is half done. A restore that returns false (unreadable, oversized, every window skipped) still makes the process the owner, which overwrites the file at its exit, as before. (2) A `.checkpoint` skips once the session's last window has saved as it went (a committed `Surface.init` outside the quick terminal clears that flag again, never `createHost`: a window whose init fails leaves that snapshot standing). No save deletes the file; see the 2026-10-19 #497 entry. (3) A real end of session latches `session_ending`, after which nothing saves: the sign-out ends the shells too, their panes close, and those closes would otherwise shrink the snapshot or move aside a restore nobody used. `App.init` raises the process to shutdown level 0x2FF so it is asked before its shells (default 0x280; one level is ended in no set order). That ordering is from the `SetProcessShutdownParameters` documentation, not measured with a real sign-out. A Restart Manager close (`ENDSESSION_CLOSEAPP`) that noctty agrees to saves every window and latches too, then quits from the message loop (the 2026-10-23 RMCLOSE-1 entry). (4) The WM_ENDSESSION save runs inside a sent message, which can arrive while the UI thread waits inside a call made under a surface's renderer mutex (the core's copy path holds it across `EmptyClipboard`, which sends to the previous clipboard owner), so `captureSessionScrollback` only `tryLock`s it and skips a surface without a live core. (5) An explicit-directory, `-e`, profile-picker, `--launch-layout` or `initial-window = false` process is not the owner, so it neither restores nor saves: what it ran was never loaded from the file, and writing it back replaced the session the next plain launch restores. The cost: when such a process is the first one running (a jump-list recent folder, `noctty --working-directory=X`), it becomes the IPC primary and nothing forwarded into it that day is saved; a reload from `window-save-state = never` does not start saving either. This reverses the 2026-09-01 test line "Startup-only restore bypasses must not disable later session saves". (6) A plain launch that starts while the previous owner is between `stopIpcServer` and the lock release in `terminate` becomes a non-owner primary; a bounded wait was tried and dropped, because the lock spans the profile while the IPC namespace is per class and elevation, so it would also stall launches that sit beside an unrelated owner. To exercise the end-session and display-change saves without signing out, send WM_QUERYENDSESSION, WM_ENDSESSION(1, lParam) and WM_DISPLAYCHANGE to the host windows with `SendMessageTimeoutW`. A unit test cannot reach `saveSessionState` itself: `localAppDataPathAlloc` returns null under `builtin.is_test`, so test the gate (`sessionStateEnabled`), `writeSessionStateAt` and the lock with explicit temporary paths.
