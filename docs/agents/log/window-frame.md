  - The rules.
    1. After the frame write. `App.reconfigureTheme` showed the opacity before its frame-mode `SWP_FRAMECHANGED` (the stock/integrated flip a change of `window-show-tab-bar` makes on Windows 11); it now shows it after, as fullscreen and the decorations toggle do (the OPACITY-640 entry's refresh sites). Not every frame write does: four older ones, not changed here, are open item (d). On the base a reload's `applyConfig` asserted blur-behind again after the flip anyway, so only `reconfigureTheme`'s own order was wrong: the frame mode flips only with a config change (`use_integrated_titlebar` follows `window-show-tab-bar`), whose callers now leave the opacity to `applyConfig` (rule 2).
    2. Once, at the value it will show.
       - Never at the value it leaves. `reconfigureTheme(opacity)` takes `retry` (`reconfigureSystemTheme` rebuilding with the system inputs changed, rule 3), `refresh` (`reconfigureSystemTheme` rebuilding with the system inputs unchanged, including its missing-resources pass; Settings' theme preview, `refreshSettingsPreview(.theme)`; `App.endSettingsPreview` when a theme preview ends alone) or `caller_applies` (the `.app` `config_change` arm; `Host.swapRuntimeConfigFromPalette`, palette code; `endSettingsPreview` when an opacity preview ends with the theme one, whose `.opacity` arm then applies it for every window, after the theme), which leaves the opacity to the `window_state.applyConfig` that follows. The trap: #678 commented the double apply as harmless. On the palette path, at the end of a Settings preview of a theme and an opacity (a save that leaves the overlay: without a reload in safe mode, or a `Saved*` save error; the Settings window closing with a preview left), and on a reload for a window kept empty for undo, the refresh showed the opacity the window was leaving (a translucent window going opaque asserted blur-behind at its old alpha, then `applyConfig` ended it). `endSettingsPreview` ends the theme first because its `std.EnumSet` of `win32_settings.PreviewEffect` iterates in tag order, which is `PreviewEffect`'s declaration order (`none`, `theme`, `opacity`); a comptime check there fails the build, naming the rule, if `opacity` ever comes first.
       - Never twice. A reload goes through core `App.updateConfig`, which sends every pane its `change_config` before the app its `config_change`: each pane's `.surface` arm applied its window's half for the pane the window shows, and the `.app` arm then applied every window again, so a window with panes applied its opacity twice at the new value and asserted blur-behind twice where it ended translucent; the palette path did the same (each pane's core `updateConfig`, then its host loop). `App.app_wide_config_change` now marks an app-wide change, and while it is set a pane's `.surface` arm leaves the window half to the app-wide step (the rest of the arm, `takeRuntimeConfig`, `setTabBackground` and the scrollbar refresh, is unchanged). Every apprt call into core `App.updateConfig` goes through `App.updateCoreConfig`, which sets it (the soft and hard reloads, the settings save's reload and its disk re-check, `settingsCheckDisk`, and the app.zig tests that update the config that way), and the palette sets it around its per-pane loop, whose core update is `App.updatePaneCoreConfig`. It is saved and restored, so a palette swap inside an app-wide change leaves it set for the rest of that change. A reload no longer runs one: it ends a live palette theme preview without showing the preview's original (`Host.supersedePaletteThemePreview`, open item (a) below, fixed). A pane's own config change outside an app-wide one (the `.reload_config` arm's soft `.surface` target) still gives its window the config from the pane it shows. A pane's step that fails (its scrollbar refresh, the one fallible step the `.surface` arm still runs, or anything earlier in core's `Surface.updateConfig`) ends core's update before the `.app` arm, and with the panes leaving the window half to that arm no window took any of the reload (CodeRabbit on #682; before these follow-ups the windows of the panes it had reached took it). `updateCoreConfig` now notes whether the `.app` arm reached its window pass (`App.app_wide_windows_applied`); when the update failed before it, the update ends as a soft reload of the config the app keeps (`App.reloadKeptConfig`), in core's order, past a step that fails (logged): every pane's update with `app.config` (`updatePaneCoreConfig`, each in its own light/dark state, still inside the app-wide change, so each pane leaves its window to the app's step), then the `.app` arm itself with `app.config` replayed in core's light/dark state (`changeConditionalState`; null when that changes nothing, and the arm clones what it is given before it frees `app.config`).     - `window_start.TopLevel.shows(panes_draw_alpha, high_contrast, blur_behind_failed)` decides.     - With `alpha-blending = linear-corrected`, the default, `load_color` premultiplies linear color, and the sRGB target and `GL_FRAMEBUFFER_SRGB` encode the result.
