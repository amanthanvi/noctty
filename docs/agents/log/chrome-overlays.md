- 2026-10-30: palette-mru.txt lines are escaped (`writePaletteMruLine` and `paletteMruKeyFromLine` in `win32/palette_controller.zig`), which qualifies "one action per line" in the 2026-04-16 `App.palette_mru` entry below in this file (chrome-overlays.md). The MRU key is the formatted action (`Command.cval`). Since upstream #13609 (ported in the 2026-10 merge window's input slice, #618), `Binding.Action.format` writes a string parameter raw instead of through `std.zig.stringEscape`, so a quoted `command-palette-entry` such as `action:"text:make\r"` puts a real CR, LF or tab in the key. Written raw, `loadPaletteMru` (which tokenizes on CR and LF and trims spaces and tabs) read `text:make` back, so the entry never matched after a restart, and the text after an LF could read back as another command's key. Lines are now written through `std.zig.fmtString` and decoded on load only when escaping the decoded key gives the line back; `std.zig.string_literal.parseAlloc` stops at the first unescaped quote without failing, so a line with a bare quote or a bad escape is kept as it is. This is the escaping `Action.format` applied to string parameters before #13609, so lines written by earlier builds still match, and earlier builds can read these. Evidence: "win32 palette MRU lines keep keys with line breaks and tabs, and read earlier builds' lines" failed on the raw form (expected `text:make\r`, found `text:make`). Two later #618 fixes, both from review, each with a failing test first: (1) `readPaletteMru` (shared by `loadPaletteMru` and the round-trip test) takes a line as a whole key and no longer trims it, because `fmtString` writes a space as itself and `text:hello ` came back as `text:hello`. (2) A line that ends in an odd run of backslashes (`text:C:\`, from an older build or a hand edit) is kept as it is before parsing: the synthetic closing quote becomes `\"`, which Zig 0.15.2's `string_literal.parseWrite` accepts and then reads `bytes[index]` one past the end (Debug: 'index out of bounds: index 10, len 10'; release reads past the buffer, at startup). Rule: anything that stores `Command.cval` or `Action.format` output in a line-based file escapes it, reads each line back untrimmed, and never hands `parseAlloc` a quoted string whose closing quote can be escaped.

- 2026-09-14: Moving GDI-painted chrome text into a real child window on this host is a five-trap operation, all measured on the confirm overlay's title and body. (1) The host carries `WS_CLIPCHILDREN`, so the parent's band paint is clipped out of every visible child rect: the child must fill its own background with `themeSurface(theme, .overlay_panel_bg)` -- `overlay_brush` is the BAND colour and is 4-6 levels off the panel, which cut two visible rectangles out of the rounded panel -- and it must not cover the panel outline, which `gdi.drawRoundedRect` draws two device-pixel rows deep at every DPI (it insets its `RoundRect` by one pixel and strokes it with the 1px stock pen), so a child starting on the painted rect's first row erased the outline across its whole span with no way for the parent to draw it back. - 2026-09-14: A Win32 multiline EDIT breaks a line only on CRLF. If a Host isn't available (shouldn't happen in practice, but pre-init close paths exist), `Surface.close` falls through to direct `DestroyWindow` and logs — preserves the "config silently ignored" fix even if the overlay path is unreachable. `MessageBoxW` is now banned in the Win32 apprt except for the pre-init fatal-error dialog.
- 2026-04-17: `Host.invokeConfirmAccept` / `invokeConfirmCancel` MUST snapshot the callback + userdata locally, call `hideOverlay` + `layout` (which frees the payload), and only THEN dispatch the callback. A destructive accept (e.g. confirm-close-surface) synchronously destroys the Host via `DestroyWindow`, so any `self.*` access after the callback is a use-after-free. Compare with `invokePaletteRow` which has the same "do not access `self` after dispatch" constraint. **Call sites** (host wndproc button 2003/2004, overlayEditProc VK_ESCAPE, submitOverlay `.confirm`) must also return immediately — NO `refocusActiveSurface(v)` / `layout()` after the call, the Host pointer may already be freed. `invokeConfirmAccept` handles focus restoration itself where safe (via the callback's own teardown path); the overlay-close path does not need to call `refocusActiveSurface`.
- 2026-04-17: `HostOverlayMode.confirm` is a message-only overlay: `showOverlay` hides the EDIT for this mode (there's no query to type) and focuses the Accept button on show. The payload `body` is routed to the hint HWND via `syncOverlayHint`'s `.confirm` early-branch — the generic `buildOverlayHintText` returns `""` for `.confirm` so the hint stays unused in the fallback path. Default-focus on the Accept button is safe because Enter = Accept and Esc = Cancel are already wired; initial focus is one explicit press away from either gesture. Never default-focus the EDIT in this mode — the edit is hidden, and directing keyboard input to an invisible control is a UX trap.
- 2026-04-17: `Host.rebuildPaletteList` logs breadcrumb lines (`text_len`, `cmds`, `cvals`, `ranked`) at `.debug` around the `rankedForQuery` call so palette-crash diagnostics have repro-time state.
- 2026-04-17: `Host.completeCommandPalette` dupes `text` AND `seed` into owned buffers BEFORE calling `setOverlayEditText(candidate)`. That call path frees `cached_overlay_edit` via `syncWindowTextUtf8CachedAfterSet → appendOwnedString`, so any read of `text` / `seed` after it is a use-after-free — `text` is a slice into `cached_overlay_edit` (from `overlayEditText`), and `seed` either aliases `text` or borrows from the same cache. This is the task-#44 root cause: "palette crashes after a few keystrokes" fired on type → Tab because `appendOwnedString(seed)` at the end of the function read the just-freed memory. NEVER retain a slice returned by `overlayEditText` across a call that might update the overlay EDIT — always dupe.
- 2026-04-17: Palette paint + dispatch paths defensively bounds-check `palette_list_ranked[i]` against the fixed stack buffer length (`256`), NOT just against `palette_list_ranked_count`. `rankedForQuery` is contracted to respect the buffer length, but a regression in that contract would turn every paint / scroll / invoke into OOB UB. Also bounds-check `cmd_index` against BOTH `snap.commands.len` AND `snap.cvals.len` — the two arrays are parallel but a user-added `command-palette-entry` could desync them if parsing was partial.
- 2026-04-17: `Host.rebuildPaletteList` must NOT free the slice `overlayEditText` returns. `overlayEditText` returns either a `""` literal or a borrowed view of `Host.cached_overlay_edit` — the Host owns the cache and frees it in `Host.deinit`. A prior defer-free both (a) freed a string literal (UB) and (b) left `cached_overlay_edit` pointing at freed memory, so every subsequent palette read returned a dangling pointer. Callers read, never own.
- 2026-04-17: `hostButtonProc` handles keyboard events for the overlay accept/cancel pair: `VK_ESCAPE` cancels (confirm mode) / dismisses (generic overlay); `VK_TAB` / `VK_LEFT` / `VK_RIGHT` cycle focus between the two buttons; `VK_RETURN` / `VK_SPACE` invoke the focused button's action. Without this path, confirm-mode Esc was inert because focus sits on accept_hwnd (the EDIT control is hidden) and the only Esc handler lived on `overlayEditProc`. Keyboard cancellation is non-negotiable for modal-ish overlays — mouse-only dismiss is an accessibility regression.
- 2026-04-17: Palette EN_CHANGE re-entry guard. Programmatic `SetWindowTextW` on the overlay EDIT HWND synchronously fires `EN_CHANGE` on the same thread, which previously (a) nulled `cached_overlay_edit`, (b) re-ran `syncCommandPaletteBanner` / `syncOverlay*` mid-write, and (c) raced borrows of the cache across the outer caller's follow-up sync. `Host.suppress_edit_events: bool` is the guard flag; `Host.setOverlayEditText(value)` is the sole wrapper around `syncWindowTextUtf8CachedAfterSet` for the edit HWND — it sets the flag before `SetWindowTextW`, clears it after, and the EN_CHANGE handler early-returns when the flag is true. Mirrors the precedent in `win32_settings.zig` (AGENTS.md:75). All four programmatic edit writes (`stepProfileSelection`, `showOverlay`, `completeCommandPalette`, `stepTabOverviewSelection`) route through the wrapper. Adding a fifth programmatic write must use `setOverlayEditText`, not raw `syncWindowTextUtf8CachedAfterSet` against `&cached_overlay_edit`, or the crash returns. Locked by `test "win32 palette EN_CHANGE re-entry guard"`.
- 2026-04-16: Command palette matching uses `zf.rank` against the human title AND the action string (best of both). Tokens are whitespace-separated; extra tokens past `palette_max_tokens` are ignored. The ranker is called per-keystroke from up to 5 helpers; cost is O(N) per call at ~90 entries so no caching is necessary today. `commandPaletteUniqueMatch` now returns the top-ranked entry (not strictly unique) — this powers Enter-to-run semantics without forcing the user to type a full action name.
- 2026-04-16: `win32_palette.rankedForQuery` is a true top-K selection: it scans the full snapshot and replaces the current worst slot when a better rank arrives. Do NOT short-circuit on `count >= buf.len` — that would hide later commands (including user-added `command-palette-entry` items) from Enter-to-run, completion cycling, and banner suggestions once the palette grows past `max_ranked` (256).
- 2026-04-16: `App.palette_mru` owns up to 5 most-recently-invoked command palette actions (newest first). `pushPaletteMru` dupes the action string into `core_app.alloc` and frees the oldest slot on insertion; `App.terminate` frees remaining slots. The MRU push must happen BEFORE `Surface.performBindingAction` on the submit path — actions such as `close_window` may synchronously free `self`, and post-dispatch access to `self.app.pushPaletteMru` is undefined. App-scoped (not Host-scoped) so recent picks survive window close. Persisted to `%LOCALAPPDATA%\noctty\palette-mru.txt` (one action per line, newest first) via `loadPaletteMru` in `App.init` and `savePaletteMru` in `App.terminate`. Load / save failures (missing LOCALAPPDATA, permission denied, corrupted file) degrade silently to "start empty" — MRU is a UX nicety, not a correctness invariant.
- 2026-04-16: Command palette list lives in a custom `noctty.win32.palette_list` WNDCLASS (registered in `App.createHost` via `ensurePaletteListClass`). The list child HWND is stamped with a `*Host` via `GWLP_USERDATA`; `paletteListProc` recovers it via `getPaletteListHost` to dispatch WM_PAINT / WM_LBUTTONDOWN / WM_MOUSEWHEEL / WM_GETOBJECT back to Host methods. Ranked matches are cached in `Host.palette_list_ranked` (stack array of `RankedIndex`) rebuilt on every keystroke via `rebuildPaletteList` — do NOT re-rank from within WM_PAINT; that's a per-frame cost paid for no reason. The child HWND is destroyed as part of the parent's destroy cascade, so `GWLP_USERDATA`'s pointer is only dangling briefly between child teardown and host.deinit; the wndproc handles WM_PAINT/mouse only and never touches `self` in that window. `invokePaletteRow` must `pushPaletteMru` BEFORE `performBindingAction` (same lifetime rule as `submitOverlay`). Arrow-key navigation (↑/↓) drives `Host.moveListSelection` on the EDIT subclass — Tab stays on `completeCommandPalette` for EDIT-text completion. `palette_list_selected` tracks the Enter target; the highlighted row repaints with `button_active_bg`. Keybind hints are rendered from `config.keybind.set.reverse.get(cmd.action)` into a 96-byte stack buffer via `std.fmt.bufPrint` — no per-frame heap allocation.
