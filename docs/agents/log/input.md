- 2026-10-30: The ConPTY-path encoder (`key_encode.legacy` with `windows_legacy`, used while mode 9001 and the Kitty flags are off) writes for ConPTY's VT input parser, not for the program, so two upstream v1.4.0 changes that are right for a program were wrong there as ported in the 2026-10 merge window (input slice, #618); review caught both. (1) DECBKM (mode 67, upstream #12226): the port made windows_legacy Backspace send BS when exactly one of Ctrl and DECBKM was set. ConPTY's `InputStateMachineEngine::_DoControlCharacter` decodes BS (0x08) as Ctrl+Backspace ("Process Ctrl+Bksp to delete whole words") and DEL as Backspace, and conhost encodes VK_BACK for a VT-input program under that program's own DECBKM (`terminalInput.cpp`: `ctrl == back ? DEL : BS`; `adaptDispatch.cpp` sets `Mode::BackarrowKey` on DECBKM). With noctty's mode 67 set, a plain Backspace would have reached PSReadLine as Ctrl+Backspace (BackwardKillWord), and a VT-input program that set DECBKM would have had it applied twice and got DEL. Read in microsoft/terminal's main-branch source, not measured; whether ConPTY forwards a program's `CSI ?67h` to noctty was not measured either. Rule: windows_legacy Backspace is BS with Ctrl and DEL without, whatever `backarrow_key_mode` says ("legacy: Windows console Backspace ignores DECBKM", which failed on the port with 0x08 for a plain Backspace); the table's `sequence_decbkm` rows serve libghostty-vt and the other callers. (2) The normal keypad row (upstream #14145, `function_keys.kpKeys`) matches any modifiers in normal keypad mode and holds the US character, so it replaced the layout's text: a numpad decimal (`VK_DECIMAL`, `.numpad_decimal`) that types ',' on a German layout sent '.'. Found by reading `pcStyleFunctionKey`, not on a live German layout (the test gives the encoder the event). Rule: a numpad key with text other than a control character sends its text when the row it matched is the normal keypad row (the `pc_style` block of `legacy`). On windows_legacy that text takes the text path, so Alt keeps its ESC prefix (Ctrl+Alt+numpad decimal on German is `ESC ,`). On every other encoder (modifyOtherKeys 2, libghostty-vt) it is written in the row's place and encoding, so Ctrl+numpad 1 with text `1` under MOK2 stays a bare `1`, as upstream's 'legacy: keypad 1 with modify other state 2' expects; routing it through the text path there gives a CSI 27 form instead. A numpad key without text (Ctrl, an Alt-code digit) still takes the row, and application keypad rows are unchanged. The first port fixed only windows_legacy; bot review and sol-loop review on #618 found the MOK2 and Alt cases (tests 'modify other keys 2: a numpad key sends the layout's text' and the Ctrl+Alt case in 'legacy: Windows console modified numpad keys and the Menu key use the shared table').
- 2026-10-30: The mouse back and forward buttons (XBUTTON1/2) reached programs as the wheel (fixed in the 2026-10 merge window's input slice, #618). `handleXMouseButton` mapped them to buttons four and five, which `mouse_encode` writes as 64 and 65, the codes the core sends for a wheel tick (`Surface.scrollCallback`), so with mouse reporting on, Back scrolled the program up and Forward down. Measured on a private desktop with portable copies under the bundled ConPTY 1.24 (a scratch adaptation of `interactive-win11-mouse-input.ps1` that sends `WM_XBUTTONDOWN`/`WM_XBUTTONUP` to the surface): a program reading VT input received `ESC[<64;11;5M` and `ESC[<64;11;5m` for Back (65 for Forward), and a program reading console records in mode 0x98 received a `MOUSE_WHEELED` record (button state 0x800000; 0xff800000 for Forward) for each press and each release. Rule: X buttons are buttons 8 and 9 (`win32/input.zig` `xMouseButton`, codes 128 and 129), as in xterm and upstream's GTK and macOS runtimes; never give a pointer button four to seven, the wheel's 64 to 67. With 128 and 129 the VT reader receives `ESC[<128;11;5M`/`m` (129 for Forward), and ConPTY 1.24 gives a record reader nothing for them (no record, and a wheel notch sent after them still arrives as wheel records). That qualifies item (10) of the 2026-10-11 PKG-72 entry in this file, "decodes noctty's SGR replies": it decodes the codes conhost knows and drops the others. UTF-8 mouse mode (1005) needs the button UTF-8 encoded from 128 up (`mouse_encode`, upstream #14532). Not measured: in-box conhost, and a physical mouse (posted messages only).
- 2026-10-23: The IME conversion target clause (#527 part 2) comes from `GCS_COMPATTR`, one attribute byte per UTF-16 unit of `GCS_COMPSTR` (Chromium's IMM path, removed since, indexed it the same way: `GetCompositionTargetRange` in `ui/base/ime/win/imm32_manager.cc` at tag 90.0.4430.0, lines 37-60, takes the byte indices as UTF-16 positions), not per codepoint, so a surrogate pair carries two bytes and takes its first. `win32_input.imeTargetCodepointRange` keeps only the first run of `ATTR_TARGET_CONVERTED` (1) or `ATTR_TARGET_NOTCONVERTED` (3), and drops the attributes whenever their count differs from the unit count. Read them under the same `ImmGetContext` as the string and `GCS_CURSORPOS`. The core maps the range onto kept codepoints like the caret, `Preedit.layout` reports its drawn cells as `target_x`, and the renderer double-underlines exactly those. IMM attributes carry no colours; Windows Terminal's TSF path does apply an IME's colours (`_textAttributeFromAtom`), so only the double underline is parity with it. Three traps. (1) `ImmGetCompositionStringW` was bound with a `?[*]u16` buffer, which cannot take the attribute bytes, and `readImeUnits` passed IMM the full byte count while its buffer held `count / 2` units, one byte short for an odd count. The binding now takes `?*anyopaque`, and `readImeBuffer(T, ...)` passes `count * @sizeOf(T)`. (2) `imePoint` anchored the composition and candidate forms at the cursor even when the preedit is drawn left of it (a wide character or an end caret in the last column); take the start from `layout`, through the pure `Surface.imePosAt`. (3) A diff box between two captures that differ only in the attributes (`RendererNative.DiffBox`) says where an underline changed, not into what: a curly or a thicker single underline can fill the same box. Count the shape as well (`RendererNative.LitBands`): over two adjacent glyphs, no stroke crosses the gap between them, so the rows on which every pixel is lit are underline rows. Measured on OpenGL, D3D11 hardware and WARP in a 459-493 row: a single underline is rows 490-491, the double 488-489 and 492-493. A stub with single underlines everywhere gave 1 band under the target, and a curly stub 0. The `-WarpOnly` CI runs reach only the WARP case.

- 2026-10-10: Do not read a key's text from a `ToUnicode` probe in the `WM_KEYDOWN` handler. The `dead_key` branch was unreachable live and the tests that set `dead_key = true` by hand could not see the two bugs that followed: each composition left one `WM_CHAR` unit authorized, which let the next Enter, Backspace, Tab, Esc or Ctrl chord through a second time, and under Kitty `report_all` the accent went out as a quote key and `é` was dropped. (3) `WM_SYSCHAR` stays queued: Alt+Space has to reach `DefWindowProc` for the window menu.
