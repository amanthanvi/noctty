- 2026-11-08: CHAIN-CLOSE-UAF: a key binding chain's actions and the surface that runs them outlive a closing action only until it runs. (Notation: `a>b` below is shorthand for a chain, written in a config as `keybind = <trigger>=a` followed by `keybind = chain=b` (`src/input/Binding.zig`, the `chain` prefix), and `x:a>b` puts the `x:` flags on the first line. In a keybind itself `>` separates the keys of a sequence, so a binding written `f5=a>b` is not a chain; council round 6's first live run made that mistake.) `Surface.maybeHandleBinding` took `leaf.actionsSlice()`, which for a chain (`leaf_chained`) is a slice into the binding set that the surface's own `DerivedConfig` owns (`config.keybind`, cloned at init), ran every action through `performBindingAction`, and then read the slice again to decide `.closed`. On Win32 `close_window` frees the surface and that config before `performBindingAction` returns when nothing needs a confirmation (`Host.close`, `closeConfirmed`, `destroyPaneOf`, then `WM_DESTROY` runs `Surface.destroy`), so `ignore` then `close_window` read freed binding storage after the loop, and `close_window` then anything ran the later actions on a freed surface. A council reviewer measured 0xC0000005 on main for `ignore>close_window` on a private desktop; which read faulted was inferred from the code, not traced in a dump. Upstream v1.4.0 has the same loop (`src/Surface.zig`, about lines 3122-3165). Two more of the same class, read from the code and not run: a reload in a chain (`reload_config`, then anything) replaces the surface's `DerivedConfig` synchronously (`core_surface.updateConfig` runs `self.config.deinit()`), so the rest of the chain read freed storage, and `App.keyEvent` did the same against `rt_app.config`, which the `.app` `config_change` arm frees; and `App.performAllAction` walked `self.surfaces.items` while a fanned-out `close_window` swap-removed a window's panes from it (an `all:` or `global:` chain), so the walk could reach a freed surface. Evidence (the first version, c6485cc7a): six `performChain` tests in `src/Surface.zig` ("a binding chain ...") ran a chain through a stand-in surface, `TestChainTarget`, which on a closing action or a reload overwrites the binding storage with another action (a free that leaves valid values, as the 2026-10-19 "`Surface.DerivedConfig` must own every byte" entry in config.md does, so a stale read fails an assertion rather than ending the test binary) and counts every call made after the close. With main's loop and main's borrowed slice put back behind the same seam, five of the six failed, by assertion, not by a crash: `expected .closed, found .performed` for `ignore>close_window`, `expected 0, found 2` calls after the free for `close_window>ignore>scroll_to_top`, and the reload chain performed the overwritten action. The Win32 fixtures cannot drive a key binding: a `TestSession` core is zeroed (trap (2) of the 2026-10-19 #497 entry in app-lifecycle.md). Rules. (1) A running chain reads a copy, never the binding set: `GenericLeaf.cloneActions` (or `Action.cloneSlice`, a deep copy: "cloneSlice copies the bytes an action carries" overwrites a `text` and both `cursor_key` slices after the copy and failed against a shallow one) into a per-call arena, in `dispatchLeaf` (the dispatch half of `maybeHandleBinding`, so the Surface tests reach the production copy; without it the two reload chain tests failed), in `App.keyEvent`'s app-scoped loop, and inside `App.performAllChainedAction` itself (`performChainOnAll`), because its callers pass borrowed storage: Win32's `handleGlobalHotkey` passes the registered binding's actions from `self.config`, which `reload_config` frees (`global:...=reload_config>new_window` read freed memory at the second action; Greptile found it on #692 after the first copies, which missed that caller). Its tests, "an app-wide chain ..." in `src/App.zig`, run a stand-in app (`TestChainApp`); without the copy the reload test failed with `slices differ` at index 1. A new caller that runs a binding's actions passes them to `performAllChainedAction` or copies them first. The arena holds only the app's allocator, so its `defer` is safe after the surface is gone. Nothing may keep a pointer into that arena past the call: the inspector's record of a binding keeps only the action tags (`bindingTags`, `inspector/widgets/key.zig` `Event.binding`), where a shallow copy kept payloads the arena then freed (council round 1). (2) On one surface a chain ends at its first action that can close that surface (`closesCaller`: `close_surface`, `close_window`, `close_tab:this`), and the actions after it are dropped. `close_tab:other` and `close_tab:right` close only the tabs beside it (`App.closeTab` on Win32), so the chain goes on after them; the first version stopped at every `close_tab` (`closingAction`, now only the test stand-ins' model of an app-wide close) and returned `.closed` for a surface that was still there (council round 1 on #692; "a binding chain goes on after closing the tabs beside it" failed with `closingAction` back in `performChain`). An app-wide chain (`all:`, `global:`) runs every action: with the copy nothing in `App.performAllChainedAction` reads what a close frees, so the stop the first version had there was a behaviour choice, not safety, and is gone; `global:close_window>new_window` crashed on main in both orders (council round 2 measured 0xC0000005 for both on f7ae840e9), and on 5f16d084f the window opened and the process quit 0.3-0.8 s later, because the last close had already posted WM_QUIT (`startQuitTimer` with no delay); with `quit-after-last-window-closed = false` the window stayed. Rule (5) holds that quit until the chain ends; and the calling surface returns `.closed` only if it is gone once the chain is done, from a `closeToken` taken before the fan-out (another surface's `close_tab:other` can close it, and `all:close_tab:right` in a one-tab window closes nothing). What a closing action returns does not say whether the surface is gone: one that performed may only have opened a confirmation (a cancelled `close_surface` leaves the surface), one that returns false had nothing to close, and one that fails is usually still there too, since a failed `close_tab:this` is rolled back, but not always: `closeTabUndoable`'s `errdefer` disposes the detached tab, panes and all, when the rollback fails as well. So `performChain` takes a `closeToken` (the app, the runtime surface and its core `id`) before the close, whatever it returns, and asks `App.hasSurfaceInstance` afterwards, which reads the surface only once it is found in the list: gone is `.closed`, and nothing reads the surface or the actions again; still there keeps the key's usual release bookkeeping (CodeRabbit on #692, twice: returning `.closed` for a rolled-back close, and then for a performed close that left the surface, skipped the consumed-press bookkeeping, so a release-reporting program saw a key-up it never saw pressed). An app-wide chain asks the same way, with a token taken before the fan-out (`all:close_tab:right` in a one-tab window closes nothing). Only the actions that ran count afterwards (`Dispatch.reached`, and the decision `bindingOutcome` that `dispatchLeaf` makes from them): with `unconsumed:a=scroll_to_top>close_window>ignore` where the close finds nothing to close, the dropped `ignore` made `a` ignored where it should reach the program (CodeRabbit; "a binding chain whose closing action closes nothing keeps what came before it" expects `.encode` and failed with every action counted). The same check follows an action that can take the surface out of every live tab without closing it (`mayDetachCaller`: `undo` and `redo`, whose replay detaches a pane for the other direction): if the surface is gone, or still there but in no live tab (`CloseToken.attached`, through `receivesAppWideActions`), the chain ends there, because the next action could free it: `undo>reset` on the pane a split made detached it and then cleared redo, which disposed it under the chain (CodeRabbit on #692, measured by council round 4 (Opus) on a private desktop: `undo>reset>scroll_to_top` on a split-created pane crashed main with 0xC0000005 3 of 3 times and left 4a364ff4a running 3 of 3; "a binding chain ends where an undo detaches its surface" failed without the check, with a call after the free). Nothing else detaches the pane its key ran on: tab moves only reorder, and the quick terminal toggle hides its window with the pane in its tab. And a key that reaches a pane already detached (queued before an `undo` took it out of its tab) runs no action at all: `dispatchLeaf` refuses the binding when `closeToken().attached()` is false and swallows the key as consumed, since a `reset`, even alone, would clear redo and dispose the pane while it runs (CodeRabbit; "a binding on a pane an undo detached runs nothing" failed without the refusal, the pane freed under the chain; council round 5 (Opus) measured it live on a private desktop, 3 runs a case: F7 bound to `undo` and then F8 to `reset>scroll_to_top`, or to `reset` alone, crashed 4a364ff4a with 0xC0000005 6 of 6 times and left 722d4221b running 6 of 6). The dispatch tests go through the stand-in's `attached`; the real `CloseToken.attached` (`App.hasSurfaceInstance`, then `receivesAppWideActions`) is tested on Win32 fixtures, "win32 the core close token sees a pane retained for undo out of its tab": a `TestSession` has a real core App, so the test registers its panes there and points their inert cores at it (`app`, `rt_surface`, `id`), which is all the token reads (CodeRabbit on #692; with `attached` reduced to `survived` the test failed). Council round 4 also verified it live. (3) A fan-out over `App.surfaces` reaches only surfaces in a live tab (`receivesAppWideActions` on the runtime surface; on Win32, `Host.findTabForSurface`): a pane detached for undo is still one of the app's surfaces, hidden with its program running, and main sent it every `all:` action, so `global:...=close_tab:this>text:...` typed into the tab just closed (CodeRabbit on #692; `goto_attention`'s fallback skips such panes too). - 2026-10-30: The ConPTY-path encoder (`key_encode.legacy` with `windows_legacy`, used while mode 9001 and the Kitty flags are off) writes for ConPTY's VT input parser, not for the program, so two upstream v1.4.0 changes that are right for a program were wrong there as ported in the 2026-10 merge window (input slice, #618); review caught both. (1) DECBKM (mode 67, upstream #12226): the port made windows_legacy Backspace send BS when exactly one of Ctrl and DECBKM was set. ConPTY's `InputStateMachineEngine::_DoControlCharacter` decodes BS (0x08) as Ctrl+Backspace ("Process Ctrl+Bksp to delete whole words") and DEL as Backspace, and conhost encodes VK_BACK for a VT-input program under that program's own DECBKM (`terminalInput.cpp`: `ctrl == back ? DEL : BS`; `adaptDispatch.cpp` sets `Mode::BackarrowKey` on DECBKM). With noctty's mode 67 set, a plain Backspace would have reached PSReadLine as Ctrl+Backspace (BackwardKillWord), and a VT-input program that set DECBKM would have had it applied twice and got DEL. Read in microsoft/terminal's main-branch source, not measured; whether ConPTY forwards a program's `CSI ?67h` to noctty was not measured either. Rule: windows_legacy Backspace is BS with Ctrl and DEL without, whatever `backarrow_key_mode` says ("legacy: Windows console Backspace ignores DECBKM", which failed on the port with 0x08 for a plain Backspace); the table's `sequence_decbkm` rows serve libghostty-vt and the other callers. (2) The normal keypad row (upstream #14145, `function_keys.kpKeys`) matches any modifiers in normal keypad mode and holds the US character, so it replaced the layout's text: a numpad decimal (`VK_DECIMAL`, `.numpad_decimal`) that types ',' on a German layout sent '.'. Found by reading `pcStyleFunctionKey`, not on a live German layout (the test gives the encoder the event). Rule: a numpad key with text other than a control character sends its text when the row it matched is the normal keypad row (the `pc_style` block of `legacy`). On windows_legacy that text takes the text path, so Alt keeps its ESC prefix (Ctrl+Alt+numpad decimal on German is `ESC ,`). On every other encoder (modifyOtherKeys 2, libghostty-vt) it is written in the row's place and encoding, so Ctrl+numpad 1 with text `1` under MOK2 stays a bare `1`, as upstream's 'legacy: keypad 1 with modify other state 2' expects; routing it through the text path there gives a CSI 27 form instead. A numpad key without text (Ctrl, an Alt-code digit) still takes the row, and application keypad rows are unchanged. The first port fixed only windows_legacy; bot review and sol-loop review on #618 found the MOK2 and Alt cases (tests 'modify other keys 2: a numpad key sends the layout's text' and the Ctrl+Alt case in 'legacy: Windows console modified numpad keys and the Menu key use the shared table').

The chrome controls (tab buttons, search field) and every Settings control are not subclassed for `WM_SYSCHAR`, so the top-level window under them -- the host, and separately the Settings window, which is its own top-level with no owner -- answers the phantom loop's `WM_MENUCHAR` (high word of wParam `MF_SYSMENU` without `MF_POPUP`, measured 0x2000) with `MNC_CLOSE`; a real popup (`MF_POPUP` set, measured 0x2010 for a key typed into the open window menu) keeps the default reply, and measured on Windows 11 that default neither closes the menu nor beeps for an unmatched key, so do not write "beeps like every Win32 menu" -- I did, and the measurement said otherwise. Fixing the host alone leaves Settings beeping: it is not a child of the host, so a host-side reply never sees its loop.
