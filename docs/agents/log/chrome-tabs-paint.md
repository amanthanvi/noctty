- 2026-10-01: The tab strip is the first consumer of the Windows accent (#278), behind `accent-follow-system` (default on). `resolveTheme` hands the accent `resolveSystemAccentColor` read to `withSystemTabAccent`, which keeps it as read in `ThemeColors.system_accent` and a readable version in `tab_accent`; the active tab's border, the underline and the strip above a separate tab row read the latter through `tabAccent`. `readableTabAccent` keeps the accent as chosen when the underline and `tabAccentBorder`, which every layout paints, reach 3:1 against `chrome_bg` (DESIGN.md's floor for essential non-text indicators), and otherwise blends it toward white (dark) or black (light) in 5% steps until they do. The strip does not take part in that decision: only a separate tab row paints it, never the integrated titlebar, so it would let a color nobody sees on default Windows 11 alter the accent. Where its shift would fall below 3:1, `tabAccentStrip` paints the followed accent itself instead. A custom `window-titlebar-background` band re-derives `tab_accent` from `system_accent` against the band's background and polarity, never from the already adjusted `tab_accent`: with `window-theme = ghostty` the base strip is always dark, so a dark accent such as `#0063B1` was lifted toward white for that strip and then stayed lifted on a light band, where the accent as read was already readable. High Contrast, a missing or zero accent and `accent-follow-system = false` leave `tab_accent` null and the strip as before. Everything else that reads `accent` (buttons, overlays, the scrollbar thumb, profile chrome, the Settings window) still uses the theme's fixed palette. This supersedes two statements in the 2026-04-16 `blendSemanticAccent` entry: `reconfigureTheme` on `WM_DWMCOLORIZATIONCOLORCHANGED` now has a visible effect (the tab strip), and the `accent-follow-system` knob now exists because it has a consumer; it also supersedes the 2026-04-16 "Do not add user-facing config knobs for planned-but-unimplemented features" entry's listing of `accent-follow-system` among the advisory fields that were silent no-ops and got removed — it is no longer a no-op and is not removed.

- 2026-04-17: `src/apprt/win32_icons.zig` is the single source of truth for the 18 geometric icons used across palette rows, settings, search bar, toast severity glyphs, and titlebar fallback glyphs. `drawIcon(kind, hdc, rect, color, is_hc)` paints via `CreatePen` / `SelectObject` / `Ellipse` / `Rectangle` / `Polygon` / `MoveToEx` / `LineTo`. UnderlineState.positioned distinguishes first layout from an already positioned snap; the production retarget policy snaps on the first layout and under reduced motion, then slides only on active-tab changes when motion is enabled; geometry-only resize/DPI changes snap. slide_started_ms == 0 means no slide is running, not that no position has ever been assigned. `closeHitRect` expands in lockstep with alpha so pointer hit-testing matches the visually rendered button.

- 2026-04-17: `win32_icons.drawMaximize` + `drawRestore` select the stock NULL brush before `Rectangle(hdc, ...)`. `setupGdi` installs a SOLID brush matching the glyph colour, so the bare `Rectangle` call FILLS the rect (producing a coloured block the user saw as a "blank button"). - 2026-04-17: Tab close-fade uses TWO `CloseState` slots on `Host` — `tab_close_hover_*` drives the incoming-target fade-in (0 → 1); `tab_close_prev_*` drives the departing tab's fade-out (1 → 0) on adjacent-tab transitions. Without the second slot, rapidly moving the mouse from tab A to tab B would snap A's X to 0 the moment the mouse enters B instead of cross-fading them. Both slots are tick-ed + invalidated independently in `tickTweens`. A single extra slot is enough — at 120 ms per fade the user can't queue a third parallel animation within the heartbeat.
- 2026-04-17: Tab close-button hover fade is the first visible consumer of `win32_tab_visual.CloseState`. Wired through `Host.setHoveredButton` → `addTween(dummy, close_fade_ms)` → `tickTweens` explicitly invalidates the fading tab button HWND (parent-HWND `InvalidateRect` with flag 0 does NOT cascade to child buttons). `drawButton` reads `CloseState.alphaAt(GetTickCount64())` and alpha-pre-composites the close-glyph colour against the tab bg via `blendColorRGB` — GDI `DrawTextW` has no alpha channel, so the blend must happen on the colour before SetTextColor. Active tabs always paint the X at full alpha (permanent affordance); non-hovered + non-active tabs skip the glyph entirely when alpha ≤ 0.01. When effectiveTweenDuration is zero, setHoveredWithMotion snaps alpha/start_alpha to target and clears the timestamp instead of scheduling the dummy heartbeat; both the incoming and departing slots must snap.
- 2026-04-17: `blendColorRGB(a, b, alpha)` linearly interpolates two Windows COLORREFs (`0x00BBGGRR`) by `alpha` ∈ [0, 1]. Clamps alpha, extracts channels, lerps, reassembles. Used for fade effects on GDI paint paths that can't use alpha blending directly (DrawTextW, FillRect). Do NOT pass hex literals that include the high byte — Windows COLORREF is 24-bit, the high byte is reserved and must be zero.
- 2026-04-17: `appendOwnedString` allocates the replacement BEFORE freeing the old slot. Reversed from the prior order so (a) an OOM leaves `*target` holding a still-valid previous allocation instead of a dangling freed pointer, and (b) a caller passing a `value` that aliases the current slot is copied to fresh storage before the free, closing a latent UAF class. All live callers are null-safe re: the old order; the new order is strictly more robust. Locked by `test "win32 appendOwnedString leaves target untouched on OOM"`.
- 2026-04-17: Focused-tab underline is painted as a single parent-HWND rect animated via `Host.tab_underline: win32_tab_visual.UnderlineState`. `retargetTabUnderline(left, width)` is called from `layoutChromeForRect` once per layout, snapping on the first retarget (!positioned, no slide-in-from-origin on window open) and under reduced-motion / HC, otherwise sliding over `underline_slide_ms` (160 ms). The slide runs on the existing 16 ms tween heartbeat via a dummy `addTween`; no second timer. `paintChrome` draws the interpolated rect in the 2 px gap between the child tab buttons (`button_y = scaled(3)`, `button_height = tab_h - scaled(6)`, so buttons occupy y∈[3, tab_h-3)) and the 1 px chrome bottom border. Painting on the parent (not each child button) is load-bearing: only a single-rect paint can slide smoothly across child-HWND boundaries; per-button underline is a hard cut. The per-button underline in `drawButton` is removed. Insets 3 px on each horizontal edge per WT reference (docs/wt-chrome-reference.md §1, MUX `TabViewItemBorderThickness: 1,1,1,0` equivalent at our scale).
