- 2026-10-30: `Termio.resize` resizes the pty while it holds the renderer state lock (port of upstream `f2571a3ec1ee`, #14706, in the 2026-10 merge window, #620), so output the console host or the shell writes in answer to the resize cannot be parsed against the old grid; a refused pty resize is still logged and the grid resized anyway (PKG-14). That makes a pty resize that blocks a deadlock, since the reader then waits for the lock instead of draining the output, so it was measured first. A probe (C# P/Invoke, a `cmd.exe` flooding a pseudo console whose output nobody reads, sizes 100x30 and 80x24 alternately): with the output pipe full (4,128 to 4,164 bytes unread), every `ResizePseudoConsole` (in-box) and `ConptyResizePseudoConsole` (bundled 1.24) call returned within 0.18 ms and 600 in a row completed, but the 684th blocked on both, because the 6-byte resize packets fill the 4 KiB signal pipe once the host stops reading it while its own output write waits. So a resize of a pseudo console this process created never waits for output to be read, and the lock is safe while the reader drains between resizes; the IO thread coalesces them to one per 25 ms (`Thread.zig` `Coalesce.min_ms`), so filling the signal pipe takes more than 17 s of resizes during which no output is read. Not measured, inferred: a default-terminal handoff session resizes through `Pty.setSize` -> `HandoffControl.writeSignal`, a synchronous `WriteFile` of the same 6-byte packet to the signal pipe the console host handed over, under `signal_write_mutex`. It probably behaves the same (a pipe that the host's signal thread reads), but no probe reached it, and that pipe is created on the host's side, so its buffer size, and with it the ~683-packet bound, is not known there. `setAdoptedVisibility` (4-byte packets, from `Exec.ptyVisibility` on the IO thread) and `closeAdoptedSignal` take the same mutex and write or close the same pipe, so their packets count toward the same bound. `interactive-win11-conpty-sync.ps1` (Debug build, hidden desktop) passed 18 of 18 scenarios in sync after the change, with `clink-typed-narrow-widen` skipped for want of a portable Clink; a second run with `-Clink` (the official portable Clink 1.9.34, Authenticode-signed by Christopher Antos, the version CLINK-RESIZE-01 measured) passed 19 of 19 in sync, the Clink scenario included (0 rows apart before, after the narrow and after the widen). Two probe traps: a child needs `STARTF_USESTDHANDLES` with null handles (the 2026-09-15 entry), and the bundled OpenConsole writes only its 23-byte prologue and then holds all output until its startup DA1 query is answered, so a probe that never answers fills nothing; write a DA1 reply (`ESC[?62;22c`) to the input pipe first. Rule: nothing the IO thread calls with the renderer lock held may wait on the console host's progress; a new pty signal there needs the same measurement.
- 2026-10-25: A resize at a Clink prompt (CLINK-RESIZE-01) drew Clink's line twice, and the cause was noctty's column reflow, not the Lua's `redraw=0`. Measured on a hidden desktop with portable Clink 1.9.34 under the bundled ConPTY (80x20 at 150%): noctty's rows were compared with ConPTY's buffer at every step of narrow, widen, rows down and up, and both at once. - 2026-10-11: PKG-14 makes noctty agree with ConPTY across resizes. Every Windows pty is a pseudo console, so `Exec.initTerminal` turns off `Terminal.flags.resize_pull_scrollback` (a backport of upstream c55f213aa, C API option 40 included): growing rows appends blank rows below instead of pulling history back into the active area, and a column reflow keeps the old top of the active area. On Windows, a maximize at a prompt therefore shows blank rows under the prompt rather than more history, as Windows Terminal does. With the flag off, a shrink that would push the cursor's row into history also drops what does not fit below the cursor instead (`PageList.keepRowActive`, rows and reflow alike), which is what conhost does; before, the cursor snapped to an unrelated row. - 2026-10-10: Closing a pane, tab or window, or quitting, could freeze noctty for good (robustness audit F1): `Exec.threadExit` stopped the Windows pty reader with one `CancelIoEx`, which cancels only a read that is already pending. Whenever the reader was processing a chunk or about to call `ReadFile`, the cancel was lost (the audit measured this on 29% of busy-pane closes on the in-box conhost and 38% on the bundled ConPTY), and the next synchronous read never ended. This process holds the output pipe's write end until `Pty.deinit`, after the join, so no EOF came either. The IO thread then joined the reader forever, and the UI thread, inside `DestroyWindow`, joined the IO thread. `Surface.deinit` now sets `Termio.stopping` first thing (`threadExit` sets it too, for an IO thread that ends on its own), the reader checks it before every read (`ReadThread.readUntilStopped`), and `cancelReadUntilExit` repeats the cancel every 10 ms until the reader thread exits, as Windows Terminal does (microsoft/terminal#14544). The reader can stop before the child is killed: with nothing draining the full output pipe, `TerminateProcess` plus the wait still returned in 2 ms (in-box conhost, measured). Both halves are needed. The check alone misses a reader that passed it just before the flag was set and reaches `ReadFile` after the first cancel. The retry alone keeps a reader running for as long as output (for example from a descendant of the killed shell) keeps its reads completing at once, so no cancel finds one pending. The same deadlock had a second entry: the reader's `.forever` pushes into the app mailbox (titles, pwd, clipboard; drained by the app thread) and the termio mailbox (replies; drained by the IO thread) waited for threads that are both joining during a close. A stopped reader now drops those messages at the source, and a push already waiting gives up through `BlockingQueue.Timeout.forever_unless`, which waits like `forever` until the flag is set. Nothing is lost: `Surface.destroy` removes the surface from the app (`deleteSurface`) before `core_surface.deinit`, so the app would drop its messages anyway. The IO thread's own `child_exited` push (`processExitCommon`) gives up the same way, and `killCommand` waits at most 2 s for the terminated child. Not changed here (read in the code, not measured): the search thread's quit pushes still wait `forever` while `Surface.deinit` joins that thread (G059); `frameCompleted`'s `renderer_health` push waits `forever` too, and on Win32 it runs on the app thread, which draws, so a health change while the app mailbox is full would wait on that thread's own queue; and the in-box `ClosePseudoConsole` before Windows 11 24H2 may wait for attached clients (all measurements here ran on build 26300, where it returns at once). Three traps. (1) A sink that blocks in its first chunk holds the real reader outside `ReadFile` deterministically, which proves the pre-read check. Nothing can hold the real reader between its check and its read, so the retry is tested with a stand-in reader released after a 100 ms sleep intended to let the first cancel run. There is no acknowledgement of that cancel: under heavy load a single-cancel mutation could occasionally pass, although the recorded mutation failed. Each new test was run against the old code (one cancel, no pre-read check, `.forever` pushes) and failed with its own error. (2) In the robustness harness, the fixture producer's 10-minute cap ends the original pane's shell, which closes the window. A long run that ends at about 600 s with a failed probe, Win32 error 1400 and a zero app exit is that cap, not a hang; pass `-ProducerMinutes`. (3) Every pane leaked its child's process handle: `Command.pid` was never closed, and libxev's process watcher closes only its own duplicate. The subprocess now closes it when it drops the command.
- 2026-09-23: Base64 typed into Neovim after an OSC 52 paste (#261) came from termio's pty write pool, which dropped whole 4 KiB chunks of large input. `SegmentedPool` handed out request+buffer slots by ring index and took them back by count, which only works while the ring never grows: growing when the oldest in-flight slot was not slot 0 made it later hand out a slot still queued in xev's intrusive `WriteQueue`, `queueWrite` re-initialized that request (resetting its `next`), and every chunk queued behind it was orphaned, the OSC's `ESC \` included. The rest of the chain is outside noctty. OpenConsole caches an unterminated OSC in its input parser and flushes it to the client as plain text as soon as an escape sequence it does not handle arrives, such as the kitty key-release `CSI 106;129:3u` that nvim 0.12's `CSI >3u` asks for. Neovim's TUI then sees `ESC ] 52 ; c ;` with no ST, and when 'ttimeoutlen' expires it types the whole thing as keys. The paste times out, the keys run as Normal-mode commands, and the first insert command in the base64 starts inserting the rest. Measured on 1.3.130 x64, bundled ConPTY, nvim 0.12.5 (`g:clipboard='osc52'`), default `clipboard-read = ask`, a 196,000-byte clipboard (a 64-chunk reply) and three key presses posted right behind the Allow click. nvim typed 16,373-16,425 keys and ended in Insert mode with base64 in the buffer, in all 3 runs. A console probe got exactly the first 28 chunks, then the keys, and no ST. Size decides it (CORRECTED by the OSC 52 matrix entry above: below about 96 KiB it still cannot trigger, but above that it is not a clean size threshold, and 199,956 bytes never leaked where 196,000 did). Clipboard text up to about 96 KiB fits the fresh 32-slot pool, so the pool never grows and it cannot trigger; 90 KB with 40 keys stayed intact. Above that, it takes 65-N writes queued behind an N-chunk reply before it drains: 120 KB (40 chunks) survived 3 keys and broke with 40, and by the model a 64-chunk reply breaks on the first write. Two OSC 52 queries in one burst for a 684,000-byte clipboard also broke it, 3 of 3 runs: they came back as ONE 842,375-byte reply with chunks 24-40 missing, and no second reply. The fix checks out a `std.heap.MemoryPool` entry per chunk, as upstream did in e0ef934f7, and every case above then arrives intact. Neovim's own half is real on its own: with 'nottimeout', a delivery gap of 60 ms or more, or WSL with 'ttimeoutlen=0', it types an intact reply too. But the bundled OpenConsole hands a terminated OSC to the client in one piece, and native nvim with default settings never did this up to 684 KB (0.10.4, 0.11.6, 0.12.5).
- 2026-09-23: "Input on the wrong row after minimize/restore" (#262) was not the renderer and not #257. A/B on the release ZIPs reproduces it identically on 1.3.125, 1.3.129 and 1.3.130. The cause: a minimized host reports a 0x0 client rect, every `WM_SIZE` (including `SIZE_MINIMIZED`) ran `Host.layout` against it, `splitSurfacePlacement` clamped the pane to 1x1 px, and the core turned that into a 1x1 grid and a 1x1 `ResizePseudoConsole`. ConPTY keeps no scrollback, so at 1x1 it drops its whole buffer and homes its cursor, and the bundled OpenConsole emits zero bytes after either resize. The terminal reflows its own copy to one column and back and keeps its cursor on the prompt row, though at column 0. After restore the two disagree, and the shell's next output arrives as absolute CUPs (`ESC[1;1H`...) to the top rows. 1.3.124 (in-box conhost) collapses the same way but repaints, so it loses the prompt row instead of desynchronizing. `chrome_layout.hostLayoutClientRect` now keeps the last client rect with an area, and `Host.layout`, `Host.contentRect` and `syncTabButtons` all go through it. Two measuring techniques worth reusing. (1) To read what the pseudo console itself believes, run a helper process that calls `FreeConsole`, then `AttachConsole(<shell pid>)`, then `CreateFileW("CONOUT$")`, then `GetConsoleScreenBufferInfo` / `ReadConsoleOutputCharacterW`. It returns ConPTY's buffer size, cursor and text, which you can diff against the terminal's UIA `TextPattern`. Use `GetSelection()` to get the terminal caret. Run the helper `-WindowStyle Hidden` and have it write to a file. (2) `ShowWindow(SW_SHOWMINNOACTIVE)` then `ShowWindow(SW_SHOWNOACTIVATE)` minimizes and restores a test window without touching the foreground. `WM_COMMAND` 1904 on a minimized host restores it. Two things turned up on the way. (a) Any real resize while cmd or pwsh sat at a prompt erased the prompt row and left the cursor block alone on a blank line. `Terminal.flags.shell_redraws_prompt` defaults to `.true`, so `Screen.resize` clears from the last OSC 133;A down and waits for the shell to redraw it. Plain cmd never redraws it. PowerShell with PSReadLine re-renders only the typed input. ConPTY sends nothing. `--shell-integration=none` is the control that keeps the prompt. Both integrations now send `redraw=0` on the mark, and any Windows shell integration that cannot repaint its prompt on a resize must do the same. Two gaps remain. Clink redraws its prompt after every resize, and its prompts keep `redraw=0`: measured on 2026-10-25 (CLINK-RESIZE-01, see that entry), clearing them made Clink's redraw overwrite the line above. The flag is also terminal-wide and sticky: a zsh, fish or elvish session nested inside a cmd/pwsh tab, which sends a bare 133;A, keeps `redraw=0` too. FIXED by #267: a bare A now resets the setting to the default unless a prompt is still open (`SemanticCommand.prompt_open`, closed only by a submitted line or a C mark), which keeps a theme's extra A inside a cmd or PowerShell prompt from switching clearing back on. - 2026-09-15: Triaging a "scrambled TUI" report against a ConPTY-hosted multiplexer (#243) needs a master-side recorder, and the recorder silently records nothing useful unless the child is created with `STARTF_USESTDHANDLES` and all three std handles NULL: when the driver's own std handles are redirected -- which they always are under an agent shell or a piped tool -- the child keeps the PARENT's handle values and writes past the pseudo console entirely, so the capture holds only conhost's attach/title/detach boilerplate (measured: 162 bytes, byte-identical for `cmd /k`, `cmd /d /c echo` and `powershell -Command`) and the run looks like "the child produced no output". Clearing `HANDLE_FLAG_INHERIT` on the parent's std handles and passing `bInheritHandles=FALSE` do NOT fix it; only the NULL-std-handle form does, and it works from a pipe-only parent, so it is the portable alternative to the `Start-Process -WindowStyle Hidden` workaround in the 2026-09-14 PowerShell entry below. Two findings that harness bought. (1) The in-box conhost (ConPTY v1) does not merely strip sequences, it reshapes repaints: for one scripted 30 s `herdr` scenario at 160x45 the bundled v2 stream carried 22803 CUP and zero CUF/ECH (the application's own absolute-CUP redraw, forwarded), while the in-box stream carried 6988 CUP plus 15138 CUF, 1933 ECH and 229 LF. Both shapes skip cells they believe are unchanged -- an application repaint skips the whitespace gaps between words -- so the difference is not "v1 skips and v2 does not" (I shipped that wrong once and review caught it); it is that every v2 run carries an absolute CUP that re-anchors the cursor, while v1's motion is relative and context-dependent (CUF clamps at the right margin, LF scrolls at the bottom row, ECH interacts with pending wrap), and that v1 skips at single-cell resolution INSIDE a word -- the capture literally contains `Modif` ESC[1C `ed` and `9/1` ESC[1C `/2026` -- so a divergence surfaces as one wrong letter, which is the shape "scrambled text" reports describe. A control child proves which stream is whose: its exact bytes come back verbatim under bundled v2 (only a `CSI 1t CSI c CSI ?1004h CSI ?9001h` prologue added) and come back as a synthesized top-to-bottom `ESC[K`+CR/LF redraw under v1, with overwritten text simply absent and the child's own CUF replaced by spaces -- so never read a bundled capture as conhost's output or an in-box capture as the application's. For any "stray leftover characters" report, diff `NOCTTY_CONPTY=inbox` against the default BEFORE suspecting the terminal -- but an inbox-only reproduction implicates the in-box path, not the transport as a whole, because the v1 shape reaches terminal code (CUF at the right margin, ECH against pending wrap, LF at the bottom row) that the bundled stream never exercises, so replay the capture through `libghostty-vt` to decide which side. Ask whether a resize preceded it: measured across three `ResizePseudoConsole` calls, the bundled path emitted no snapshot of its own (the next bytes were the application's own `CSI 2J`-led redraw) while the in-box path emitted its own `CSI ?25l CSI H` repaint from home with ECH for the blanks and NO ED -- overwrite-without-clear after an independent reflow is exactly where stale cells survive. Releases before 1.3.125 have no bundled pair and are always on the v1 shape. (2) `libghostty-vt` settles "is this the terminal core?" without a GUI repro: `zig build -Demit-lib-vt=true` produces `ghostty-vt.dll`, every portable release ZIP already ships one for its own version, and both can be driven from a few lines of `ctypes` -- replay the captured bytes through `ghostty_terminal_vt_write`, then diff `ghostty_formatter_format_buf` output and the `ghostty_render_state_*` per-row dirty flags across versions and chunk sizes. That exonerated both 1.3.124 and `main` on the real captured streams (identical screens, no chunk-boundary sensitivity, zero dirty-tracking violations) in minutes.
