- 2026-10-23: The profile syntax review (discussion #529, PROFILES part 1) left three traps in config loading. (1) `cli.args.LineIterator` returned null for a line longer than its 4094-byte entry buffer (`streamDelimiterEnding` fails with `WriteFailed` on the fixed writer), which silently ended the file: every line after a long `PATH` was lost (measured on main with a test that uses only main's keys: `expected 1, found 0`, the next line's `title` never read). It now skips to the next newline and returns `LineIterator.skipped_line`, a marker compared by pointer (a mutable global, so no string literal shares its address), which `parse` turns into a located problem and, for a destination with `_replay_steps`, a `.diagnostic` replay step, since a conditional replay never reads the file again. The CR of a CRLF line is read into the entry buffer before the trim, so that buffer needs one byte more than the documented limit, or a CRLF file's limit is one byte less (CodeRabbit). (2) An empty value (`key =`) calls the field type's `init` when it declares one (`args.zig` `parseIntoField`), instead of resetting to the default; `profile-command` uses that to remove every profile while keeping tombstones, and every `ProfileMap` declares `init` (the others clear), because a decl cannot be declared for one comptime instance only. (3) `ExpandEnvironmentStringsW` lets the closing `%` of an unset name open the next one (`%UNSET%SystemRoot%` gives `%UNSET` plus the expanded root), unlike Wine's implementation, which copies both `%`; measured by a parity table against the real API, which is how `windows_shell.expandProfileText` stays equal to it now that `%NAME%` reads global `env` entries first. (4) `Replay.Iterator` re-added a `.diagnostic` step's problem to the config it rebuilds but not the step itself, so a config rebuilt by replay (the one `finalize`'s `loadTheme` swaps in whenever a theme file exists) lost every such problem at the next `changeConditionalState`: the over-long line, and on main a missing or cyclic `config-file`. It now keeps the step, as the `.expand` arm does. A theme file's own problems are the exception: every `finalize` reads the current theme again, so `loadTheme` drops the theme's `.diagnostic` steps from the replay log (kept, a light theme's problem rode into every dark config rebuilt from a light one), and its replay skips the steps conditional on the theme, which only an earlier `loadTheme` left there (kept, a second `finalize`, as `+validate-config` does after `Config.load`, applied the theme's lines and reported their problems twice, on main too). A test of "survives a conditional replay" must use theme files that exist: with a missing theme `loadTheme` returns before its replay, and the test passes on the broken code. (5) A formatter that inserts canonical spacing can make a line the reader accepted too long to read back; profile lines fall back to `key=id:value` past 4094 bytes. Bash heredocs in this agent's shell turned `\\` into `\` in a Python script, and MSYS path conversion ate a leading `/` of a `/// ...` argument: write edit scripts with a file tool and set `MSYS_NO_PATHCONV=1`.

- 2026-04-17: `App.cli_config_override_path` caches the `--config-file <path>` override resolved once at `App.init` — BEFORE `run()` calls `sanitizeCurrentDirectory()`. Resolving a relative CLI path via `getCwdAlloc` at save time targets the sanitized cwd (typically `%USERPROFILE%`), which is NOT the cwd `Config.load()` used at launch. Result would be that saves land in a different file than the one CLI-masks the config at runtime. The Settings "Save" path and the Advanced "Open in editor" escape hatch both route through this cached absolute path, guaranteeing they edit the same file that `Config.load` used at launch.
- 2026-04-17: `App.startup_cwd` caches the launch-time cwd (captured in `App.init` before `sanitizeCurrentDirectory()` runs). Both `settingsSaveAndReload` AND the `.reload_config` action wrap `Config.load(alloc)` in a `chdir(startup_cwd) … chdir(cwd_before)` dance so `loadCliArgs` resolves relative `--config-file` argv entries against the SAME cwd the launch used. Without this, a reload after cwd-sanitization resolves `--config-file custom.conf` to `%USERPROFILE%\custom.conf` instead of the file Config.load originally loaded from `X\custom.conf`, silently swapping the runtime config source every time the user reloads. Always restore the sanitized cwd after the reload so downstream code (surface spawn, relative-path lookups) sees the environment it expects.
- 2026-04-17: The `.reload_config` action uses the same startup-cwd scope as `settingsSaveAndReload` (`App.enterStartupCwd` / `StartupCwd.restore`, deferred), so cwd restore runs on both the happy path AND the `Config.load` error path. Manual Ctrl+Shift+R reloads that fail on a broken include no longer pin the process to `startup_cwd`. `reload_config` restores at the end of its arm, after `updateConfig`; a Settings save restores right after the load.
