  - Rules. Everything that can fail runs first, in this order: the drop's preconditions; the hidden new window (`window_state.Origin.tear_off`: the source's decorations, opacity and topmost, never its maximize or fullscreen, placed by `window_start.placeTearOff` at the drop point or a cascade step off the source); the target's tab capacity; what handing the tab over runs first, all window code (`Host.prepareGiveTab`: the prompts it puts away, a rename it hides, the drag it ends, round 13); the `move_tab_to_window` prepare; the commit, retrying stale. After each step that runs window code, and once more right before the commit, `App.revalidateTabMove` finds both windows and the tab again by id, applies every entry check again and reserves the slot again (round 15). A move that fails after `prepareGiveTab` has already put the prompts away and ended the drag (its release swallowed): accepted, since the user asked for the move. Only then do both windows' structural histories go (as a reorder clears them: their entries keep tab indices and panes of their window, so an undo after a move restores nothing structural), so a failure at any step before keeps them (round 4 below). One rule for every failure (round 5): the model and the windows always agree, and no closed tab the model keeps for undo is left without its window. History a disposal cannot finish stays with its window, and a window the move emptied stays too, hidden, until the undo prune disposes it (`Host.destroy_after_structural_dispose`). History is given up only where the model needs it gone first: a transfer in it that names the tab, which the model refuses the move for (`InvalidTransfer`), so the history goes before a second prepare, which can still fail (round 4). `Host.giveTab` then cannot fail and pumps nothing between taking the tab out and putting it in (the 2026-11-01 NOTIFY-MODULE entry in app-lifecycle.md): it hides the panes first (no two GL children overlap in either window: the 2026-04-14 entries below), reparents, renumbers the tab in the target (tab ids are a window's own) and raises the source's UIA tab-list change; the target's button comes from its next chrome pass. The target is activated (a new window through `.before_show`, its first show and `.after_show`, then `applyDpiChangeToVisibleSurfaces`, since a hidden window's panes took its size before its DPI's font: the 2026-10-25 DPI-HIDDEN-TAB-BATCH-01 entry in window-frame.md) before an emptied source is destroyed, so the foreground never passes to another program in between. The quick terminal neither gives nor takes a tab, a window kept empty for undo takes none, and another process's window is never a target: a drop there opens a new window in the dragging process. A window's only tab hands the drag to the system's window move (`SC_MOVE | HTCAPTION`, posted), decided in the host's `WM_SYSCOMMAND` once `DefWindowProc` returns, so a move that never started leaves nothing armed; a move that ended over another window's strip, not maximized, merges.

Review on #689 (Greptile, CodeRabbit, the council's Opus, Sol, Muse and Kimi seats) found most of the traps below; each says which test pins it. (1) The gap `win32_layout.splitSurfacePlacement` leaves is 2 physical pixels at every DPI (1 px off each pane) and is the only part of a divider the host receives the mouse in. The grab zone (the gap plus `pane_divider.grab_margin_dip`, 3 DIP, into each pane) works because a pane answers `HTTRANSPARENT` from `WM_NCHITTEST` there (`Host.paneDividerAtScreen`), as it already did for the frame's resize edges (`Host.resizesFrom`), except over its own overlay scrollbar's band while it can scroll (`Surface.scrollbarBandAtScreen`). That band (10 DIP) covers the whole margin on its side, so beside a scrollable pane the target is 5 px at 100% and 6 at 150%, not 8 and 10. `HTTRANSPARENT` hands every button to the host, so in the strip the wheel, the right and the middle button do nothing. Where a nested divider meets its parent's line, the deepest split wins (`pane_divider.For.hitTest`). (2) The capture moves the mouse, not the keyboard: Esc reaches the focused pane, and `TranslateMessage` would already have queued its `WM_CHAR` 0x1B. So the App's loop takes key messages before `TranslateMessage` while a host holds a divider gesture: a drag, or the button of one that Esc or a double-click ended (`pane_divider_button_held`). Keys are owned by physical key, the scan code and extended bit (lParam bits 16-24; a message with no scan code by its virtual key): left and right Shift share `VK_SHIFT`, and keyed by virtual key the drag swallowed the left one's release and delivered the right one's (Sol, measured). A press is the gesture's only when it starts during it (lParam bit 30 clear); its repeats and release are swallowed with it, also after the gesture, so a held Esc never reaches the shell; a key already down at the press keeps its release. The held set is reconciled on `WM_ACTIVATEAPP(true)` (`App.reconcilePaneDividerHeldKeys`, through `hostWindowProc`): a key still down by `GetAsyncKeyState` of its own sided virtual key (`pane_divider_held_vks`: VK_RSHIFT, not VK_SHIFT; for a VK_PROCESSKEY message the key the IME took, `ImmGetVirtualKey` from the loop's `paneDividerDragKeyFrom`, else the scan code's, since VK_PROCESSKEY is never down) stays held, one that went up while another app had the keyboard is forgotten. A key released and pressed again while noctty was inactive is down either way and cannot be told apart: its repeats and release are still swallowed once. That is deliberate: `GetAsyncKeyState`'s pressed-since-last-call bit is shared with every process that calls it and documented as not to be relied on, the thread's keyboard state sees only its own messages, and raw input or a low-level hook would be out of proportion (CodeRabbit accepted it). The first fix forgot every key at deactivation, which let the release of a key held across the switch reach a terminal without its press (CodeRabbit, both ways). `WM_HOTKEY` is dropped during a drag (`App.takeGlobalHotkey`). A hotkey held past the release repeats as any held hotkey does (they are registered without `MOD_NOREPEAT`), and its repeats run. A latch that dropped them until the key was seen up was tried and removed (#702): `WM_HOTKEY` carries no repeat flag, and noctty cannot see a release while another app has the keyboard (only a low-level keyboard hook could), so no latch can tell a repeat from a fresh press. Sol measured the latch keeping fresh presses swallowed indefinitely when the key was released in another app and pressed again under its time gap, and FILTERKEYS allows repeat delays and intervals up to 20 s, so no gap bounds a repeat. Rule: drop a hotkey only while a divider gesture holds the mouse (`App.takeGlobalHotkey`); do not track hotkeys past it. With an IME composing, every key arrives as `VK_PROCESSKEY`; one whose original key is Esc cancels the drag, judged by the key the IME took (`ImmGetVirtualKey`), then by the layout's key for the scan code, and by Esc's scan code only when neither says, so a layout that puts Esc on another key still cancels (CodeRabbit). The loop routes a message before translation in `App.routeLoopMessage`, which hands the lookup the message's window (tested through a real posted message). (3) The keyboard `resize_split` (`App.resizeSplitFallback`) enforces no minimum and records no undo step: a changed resize clears structural undo and redo and the tab's terminal redo (the 2026-04-19 entries below). A drag is that resize, made at its press: when it ends changed it discards the history recorded before the press (`clearPaneDividerHistory`: structural entries with a smaller `sequence_id` than `PaneDividerDrag.press_sequence`, and the tab's terminal redo), and never what was recorded during it. Without that cut, automation that split the pane or closed the tab mid-drag had its new entry discarded by the drag's end, and a close's entry is what keeps the tab's sessions (CodeRabbit, Opus; test "drag discards only the history recorded before its press"). "Changed" is the divider's pixel, never its ratio: (a) a move is `start_ratio + (pointer - press) / extent`, so no movement gives the starting ratio exactly (the 801 px and 1/3 stationary clicks, where a round trip through the rounded pixel wrote f16(401/801) = 0.5005; test "stationary click on an odd width"); (b) at the end `paneDividerOnStartPixel` compares the divider's pixel with its pixel at `start_ratio` on the same layout code, which (a) cannot cover once the pointer moved: at 3840 px from 0.400390625 a 1 px move makes the ratio 0.40063 on the same pixel 1538 (Opus; test "release on its start pixel keeps the history where the ratio moved", which fails with the rule off; with it off every other test still passed). When the tree is replaced before the drag ends (a pane closed), the change cannot be put back and the pixel is read from `off_start`, the last step taken on the valid tree: a drag back on its start pixel changed nothing (Sol: out to 0.25 and back to 0.5, then a replacement, had cleared the history; test "drag back on its start pixel keeps the history when the tree is replaced"). The drag re-anchors at the divider under the pointer whenever the panes' rectangle changes (an overlay opening moved the content's top, and a 600 px vertical drag put the divider at 430 under a pointer at 401; Greptile). Tree validity (`paneDividerDragTab`: the tab by id, `SplitTree.generation`, the node still a split of its layout) is kept apart from whether the drag goes on (`paneDividerDragLive`: in front, unzoomed) and from whether a new drag may start (`paneDividerTab`: no overlay too): an overlay does not stop a drag; a zoom or a tab switch ends it as one change. `SplitTree.generation` is new on every tree value a constructor makes (`nextGeneration`), so a replacement at the address and length of the old tree is still a replacement (Opus); the first click of a double-click records it too, so a pane exiting between the clicks cannot make the second equalize another split at the same spot (CodeRabbit). A position lookup that fails (its slots cannot be allocated) confirms nothing and keeps the last reading, logged (`Host.paneDividerOffStart`): counting it as a move would discard history and the sessions it keeps (CodeRabbit). `off_start` is read on every step and on every layout while the drag's tree is valid (`refreshPaneDividerOffStart`, first in `Host.layout`), not only when the ratio moves: the same ratio lands on another pixel once the panes' width changes, also by a WM_SIZE between steps (CodeRabbit; at 3840 px from 0.400390625 a 1 px move stayed on pixel 1538, and the same ratio at 3841 px is pixel 1539). Undo and redo cannot run mid-drag (keys are intercepted; `isSafeAutomationAction` refuses both), and an entry `moveNewest` carries between the stacks keeps its old sequence, so one moved during a drag would go (Opus, Sol).
