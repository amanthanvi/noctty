  - That a surface keeps the window it opened in.   - That `Prepared.created` names what a commit made. `commitRetryingStale` swaps in the retry's reduction and previous state, not its `created`, and a retry reserves its own new window id, so the torn-off window's shell id is read from the model after the commit (`tabConst(tab).window`).
  - That the model can end with an empty window. `ShellState.validate` rejects a window with no tab and none retained (`EmptyWindow`), so `move_tab_to_window` removes the window it empties in the same reduction (the native side then destroys it, with `Host.shell_id` cleared first so the audit does not look for it), and refuses a tab a transfer names (`InvalidTransfer`): a transfer's undo would cross windows.
  - That Esc reaches the drag. Capture redirects the mouse only; the keys go to the focused terminal, so `App.cancelTabDragForKey` takes Esc in the pump, once the drag passed its threshold, and its key-up too.   - Rules. Everything that can fail runs first, in this order: the drop's preconditions; the hidden new window (`window_state.Origin.tear_off`: the source's decorations, opacity and topmost, never its maximize or fullscreen, placed by `window_start.placeTearOff` at the drop point or a cascade step off the source); the target's tab capacity; the `move_tab_to_window` prepare; the commit, retrying stale. Only then do both windows' structural histories go (as a reorder clears them: their entries keep tab indices and panes of their window, so an undo after a move restores nothing structural), so a failure at any step before keeps them (round 4 below). One rule for every failure (round 5): the model and the windows always agree, and no closed tab the model keeps for undo is left without its window. History a disposal cannot finish stays with its window, and a window the move emptied stays too, hidden, until the undo prune disposes it (`Host.destroy_after_structural_dispose`). History is given up only where the model needs it gone first: a transfer in it that names the tab, which the model refuses the move for (`InvalidTransfer`), so the history goes before a second prepare, which can still fail (round 4). `Host.giveTab` then cannot fail and pumps nothing between taking the tab out and putting it in (the 2026-11-01 NOTIFY-MODULE entry in app-lifecycle.md): it hides the panes first (no two GL children overlap in either window: the 2026-04-14 entries below), reparents, renumbers the tab in the target (tab ids are a window's own) and raises the source's UIA tab-list change; the target's button comes from its next chrome pass. The target is activated (a new window through `.before_show`, its first show and `.after_show`, then `applyDpiChangeToVisibleSurfaces`, since a hidden window's panes took its size before its DPI's font: the 2026-10-25 DPI-HIDDEN-TAB-BATCH-01 entry in window-frame.md) before an emptied source is destroyed, so the foreground never passes to another program in between. The quick terminal neither gives nor takes a tab, a window kept empty for undo takes none, and another process's window is never a target: a drop there opens a new window in the dragging process. A window's only tab hands the drag to the system's window move (`SC_MOVE | HTCAPTION`, posted), decided in the host's `WM_SYSCOMMAND` once `DefWindowProc` returns, so a move that never started leaves nothing armed; a move that ended over another window's strip, not maximized, merges.

Rules: arm a hand-off to a window message (WM_DESTROY freeing its owner) only once nothing after it can fail; do not leave an errdefer armed past the point where what it frees has a new owner (`restoreSessionTab` kept `errdefer restored_tree.deinit()` after giving the tree to the tab, so a failed `layout` freed it twice); and since `destroy` and `windowDestroyed` never run for a failed init, its errdefers must release what they would have: the title and other strings the core sets as it starts, the new tab's button and UIA provider (`Tab.deinit` asserts the provider is gone), the quit timer `addSurface` stopped, and a new host's provisional shell id, which the Debug shell audit otherwise reports while the host window is destroyed. (Labels the core's `set_title` gave the other tabs of an existing host stay until the next chrome sync.) The core has the same trap one level down: its `Surface.init` starts the renderer and IO threads and then ran a fallible initial `set_title`, while its errdefers free state those threads use and nothing stopped them. Once a failed init no longer ends the process, that is a live-thread use-after-free (access violation 0xC0000005 after a forwarded `+new-window --title=x` whose title action fails, measured on a fault-injected portable build). Nothing may fail after both threads start, and an errdefer stops the renderer thread if the IO thread's spawn fails (and hands the older errdefers what the thread allocated, since they free copies taken before it started). The same function kept `errdefer env.deinit()` armed after handing `env` to `termio.Exec.init`, whose `deinit` frees it, so any later failure freed it twice; `Subprocess.init` now owns `env` from the call on, also when it fails, because its puts can grow the map and leave the caller's copy stale; and its font grid reference had no errdefer, which Debug reports at exit through `App.deinit`'s no-grid-left assertion. Its renderer errdefer deleted GL objects on whatever context was current, which after `finalizeSurfaceInit` or the renderer thread is no longer this surface's; it now rebinds the context first and abandons the objects if that fails, as `deinit` does. Also, one failing core-app mailbox message used to end `App.run` and close every window; `drainMailbox` now drops it with a warning, and a failed `new_window` shows a banner because a forwarded request was already acknowledged. `App.test_surface_init_stage` stands in for the GL context and core surface so the rest of `Surface.init` runs for real in a unit test; `destroy` then leaves the core-app registration, because it unregisters only a surface whose core it stopped.
