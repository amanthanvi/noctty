- 2026-10-15: Docked search (PKG-41, G052 G063 F079). (1) `ScreenSearch.select(.prev)` with nothing selected picks the OLDEST match, and Enter, F3 and Down all reach it as core `.previous` (visible Down), so the first press after typing scrolled to the top of the scrollback. #346 had already made F3 follow Enter, so the audit's "opposite directions" half was stale on main (harness on main: Enter `60/60`, `59/60`, F3 `57/60`). The fix is in `Thread.select` (`selected == null` means `.next`, the newest match), not in `ScreenSearch.select`, whose `.prev` is also what `reloadActive` and the core tests mean. With a selection nothing changed, so the second Enter wraps from the newest to the oldest (`1/60`, `60/60`, `59/60`): Enter is the visible Down and the first match is the bottom-most, as in Windows Terminal. Making Enter keep walking away from the prompt means flipping Enter and F3 together (`dockedSearchEnterDirection`, the default `f3` binds, `PKG32 default F3...`, the `+list-keybinds` snapshot): a product decision. (2) A pattern that does not compile used to publish `total_matches = 0`, the "No matches" event. `Event.invalid_query` replaces that zero total in the clear (`Thread.notifySearchCleared(invalid)`), and `changeQuery` now compiles the new query BEFORE it stops the old search (an out-of-memory compile still stops it first, because `event_generation` already belongs to the new query and the old results would be published under it; Greptile caught that, a failing-allocator test pins it): clearing first and reporting after made the label read "No matches" and then "Invalid pattern" (two live-region events), and the first version of this change did exactly that (review caught it; `total_events` asserts it). It rides on `search_total` as `invalid: bool` (message and action; `SearchTotal.C` does not carry it) and `SearchBar.invalid` is cleared by `setQuery`, every toggle (`invalidateResults`) and `Surface.setSearchActive`, which every new query passes through before the core can answer it, so no core event can clear or leave a stale mark. (3) The results chip is a STATIC (`SS_RIGHT | SS_CENTERIMAGE`) that clips on the LEFT: 72 DIP was too narrow for "No matches" (82 px at 100% in the 14 px chrome font, so the N was already cut on main) and for "Invalid pattern" (98 px; it drew "alid pattern"). It is 104 DIP. Measure chip text, not the 9 pt default: `System.Windows.Forms.TextRenderer.MeasureText` with `Segoe UI` at 14 px `GraphicsUnit.Pixel` agreed with the pixels; the same call at 9 pt read 71 px for "No matches" and hid the problem. (4) Narrow panes: the fixed controls are 232 px at 96 DPI and the edit wants 120 more. `chrome_layout.searchBarFit` hides the toggles below 352 px and previous/next below 248 px (the same numbers at every DPI, scaled with the truncating `scaled`); close and the edit stay. The chip is placed after the buttons and needs `results_w + section_gap + min_edit_w` of what is left, so it disappears below about 466 DIP (434 before); the rule predates this change and the toggles keep priority over it on purpose. Hide a button with `Surface.hideSearchBarButton`, which hands the focus to the edit when the button had it. `SearchBarChromeLayout` now lives in `chrome_layout.zig`. (5) Harness (`test/windows/hidden-win11-docked-search.ps1`) traps: `WM_GETTEXT` on the chip returns its text whether or not the chip is shown, so visibility needs `IsWindowVisible`; in PowerShell `@(1100, $a-1)` is `(1100, $a) - 1` because the comma binds tighter, so parenthesize every computed element; a `.cmd` wrapper splits `-Dtest-filter=x` at the `=` when forwarded through `%1`, use `%*` and an environment variable for the log; `PrintWindow(PW_RENDERFULLCONTENT)` of the host on a hidden desktop renders the GDI search bar (crop it to the `2100` frame) although the GL pane is blank; `AttachThreadInput` + `SetFocus` moves a noctty control's focus without injecting input, and `GetGUIThreadInfo` reads it back; `Child(host, id)` by control ID returns the first pane's search bar, so use one pane per case. Measured at 150% on build 26300 only.
- 2026-10-01: Since #282 the search bar's six buttons draw VS Code's Codicons (`arrow-up`, `arrow-down`, `regex`, `case-sensitive`, `whole-word`, `close`) from the embedded Symbols Nerd Font with `DrawTextW`. This supersedes the 2026-04-17 entry for the search bar: there `win32_icons` is now only the fallback, and the `regex` / `case_sens` / `whole_word` shapes are no longer what users see. GDI cannot select font bytes held in memory, so `registerSearchIconFont` adds them once per process with `AddFontMemResourceEx` (private to the process, released at exit). The font is kept only when `fontHasSearchCodicons` finds every button's glyph with `GetGlyphIndicesW` on a memory DC, never by face name: `CreateFontIndirectW` does not fail on a missing face but returns a substitute (per the PR, an earlier draft drew the arrows from the titlebar's "Segoe Fluent Icons"; Windows 10 ships only Segoe MDL2 Assets, so it came back as Arial and the arrows drew nothing), and an older installed "Symbols Nerd Font" can shadow the registered one. Any GDI failure counts as missing; a failed registration or a rejected font is logged once at warn. Glyphs are drawn with `DT_NOCLIP` because whole-word's bracket spans its full advance, 16 px at 100%, while a 30x28 button's padded content box is 12x14: the overflow is horizontal (measured with `GetGlyphOutlineW`; every other glyph's ink fits the box). The font is created at the first search-button paint (`Host.searchIconFont`), not in `createHost`, since registering the 2.4 MB font costs milliseconds of cold start and most sessions never open the search bar; a DPI or theme change (`recreateTitlebarIconFonts`) drops it, and a failed creation is not retried until then.
- 2026-04-19: `Host.refreshChrome()` must not walk every visible docked search bar and re-run `syncSearchBarResultsText()` on generic chrome refreshes. Search results text is already synchronized on control creation and every actual search state change; the host refresh loop just re-formats and re-compares strings for no visible change.
- 2026-04-19: `setScrollbar(...)` runs on every scrollback update. PKG-56 removed the dormant status-percentage text and its invalidation path; keep scrollbar state updates independent of host chrome.
- 2026-04-19: Core search can replay identical total/selected callbacks during docked-search debounce and steady state; `setSearchTotal` / `setSearchSelected` / `setSearchSelectedDisplay` must early-return on unchanged visible state or every duplicate callback still rebuilds results text.
- 2026-04-19: `syncScrollbarWindowNow()` must not call `Host.refreshScrollbarTimerState()` on every scrollbar sync. That path tree-walks the active tab; only refresh the host timer when this surface's heartbeat eligibility actually changes, and let `Host.tickScrollbars()` own the once-per-tick refresh.
- 2026-04-19: `syncScrollbarWindowNow()` must not `InvalidateRect` the layered scrollbar child on every hover/timer sync. Most ticks only change layered alpha, and alpha comes from `SetLayeredWindowAttributes`; repaint only when actual scrollbar paint inputs change (rect, scroll position, hover/drag visuals, or marker revision).
- 2026-04-19: Dynamic Win32 scrollbars do not need the 16 ms heartbeat once they are fully hidden and idle. Keeping `scrollbarNeedsHeartbeat()` true just because a pane is scrollable leaves the timer running forever; hover wake still comes from `WM_SETCURSOR` / mouse paths, so the heartbeat should stop at stable `.hidden` and restart on the next real activity.
- 2026-04-19: `Host.layout()` calls `setVisible(...)` on every pane during ordinary layout churn; `Surface.setVisible` must not unconditionally `refreshScrollbarWindow()` or same-state passes hammer the layered scrollbar sync/timer path for no visual change. Layout-side runtime sync should key off actual pane-rect or visibility deltas.
- 2026-04-19: Win32 docked-search `Enter` / `Shift+Enter` must derive from the same visible Up/Down helper as the search edit arrow keys; separate mappings drift silently the next time the visible button contract changes.
- 2026-04-19: Win32 docked-search result counts should stay newest-first even though the visible navigation moves older/up from the bottom prompt; converting the label to top-down order makes Enter/Up feel backward. If the results chip only appears for non-empty queries, edit changes must also trigger a host relayout or the chip stays hidden after the first typed character.
- 2026-04-19: Scrollback search core indexes matches newest-first (`idx = 0` is most recent), so Win32 docked-search UI must map visible up/prev to core `.next` and down/next to core `.previous`; forwarding the enum names literally inverts the user-visible direction.
- 2026-04-19: In Win32 docked search chrome, do not parent-paint grouped trays behind owner-draw child buttons. Hidden or resized child placements can keep stale rects and leave ghost boxes on resize; group with spacing, not background trays.
- 2026-04-19: Win32 docked-search edit changes must not call `host.layout()` on every `EN_CHANGE`; the only query-driven geometry toggle is the empty/non-empty results chip, so unconditional relayout just churns `invalidateHostedChildPaint` and synchronous child repaints on each keystroke.
- 2026-04-19: `invalidateHostedChildPaint` only needs to queue child `WM_PAINT` after repaint-suppressed `SetWindowPos`; forcing `UpdateWindow` there turns every layout/search resize into synchronous owner-draw churn with no correctness benefit.
- 2026-04-19: If Win32 docked-search stops clearing core search on every non-empty edit, pending debounce state must ignore incoming core `search_total` / `search_selected` / `search_match_rows` updates or stale results from the previous query overwrite the bar's `"Searching"` state and scrollbar markers before the rerun starts.
- 2026-04-19: `buildHostAwareBaseTitle` only depends on effective surface title + host tab status. Search state (`search_needle`, totals, selection, markers) is not part of the host title contract, so search callbacks must not route through `refreshWindowTitle()` unless the title builder changes too.
- 2026-04-18: Win32 overlay scrollbars that use a layered child HWND must never auto-hide to global alpha `0` if hover wake-up depends on real mouse input. An alpha-zero layered child stops receiving hover hit-tests, so the scrollbar can strand itself hidden; keep a non-zero alpha floor for the hidden-but-hoverable state.
- 2026-04-18: Overlay scrollbar child HWNDs must use `WS_EX_LAYERED` with BOTH `LWA_ALPHA` and `LWA_COLORKEY`; global alpha alone tints the entire hover strip over the GL child instead of leaving only the painted track/thumb visible.
- 2026-04-17: `src/apprt/win32_scrollbar_geometry.zig` owns the graphical scrollbar's visibility state machine (`hidden → fading_in → visible → fading_out → hidden`) + track / thumb rect math. Fade-cancel preserves alpha: a scroll during fading-out switches to fading-in and back-computes `fade_started_ms` so the fade-in continues from the current alpha (no pop). `pointOverTrack` always uses the hover-expanded width for hit-testing regardless of the current `hovered` flag — prevents edge-flicker at the 1 px boundary between skinny and hovered widths. GL renderer wire-up consumes `trackRect` / `thumbRect` / `alpha` per frame.
- 2026-04-17: `src/apprt/win32_search_bar.zig` owns per-pane search state: query (allocator-owned, freed + re-duped on `setQuery`), toggles (regex / case / word / wrap), match counts (`total` + `selected`), and a 40-ms debounce (`last_edit_ms` + `searched` flag). `shouldRunSearch(now)` returns true exactly once per debounce window after the query stabilises — the `searched` flag prevents re-firing on subsequent ticks until the next `setQuery` or `forceSearch`. `setResults(n)` primes `selected = 1` so the "1 of N" label is immediately meaningful; `setResults(0)` nulls `selected` to avoid a stale ghost. Toggles PERSIST across `close` / `open` by design — users iterating on case/word shouldn't lose progress. `downsampleMarkers` buckets matches into `max_markers` equal-height bins and emits the midpoint of each occupied bin as a normalised `[0, 1]` f32; N ≤ max returns all matches unchanged.
- 2026-04-17: `start_search` action opens the search overlay BEFORE `setSearchText`. Reversed order let the search thread compute viewport matches against the pre-resize viewport; after the overlay shrunk the surface by ~40 px, those stale pins painted 2-3 rows below the actual match. The rendered dims_changed guard in `generic.zig:1229` clears the stale matches post-resize, but re-order ensures the first compute happens post-resize instead of relying on the guard.
