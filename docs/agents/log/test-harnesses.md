- 2026-10-31: STALL-LOAD-AB-01. A UI stall seen on one build and not the other is a difference between builds only once both have met the same load. (1) Across four batches, every multi-second UI stall (1.9 s to about 530 s) was on the renderer pacing build (the 2026-10-30 renderer pacing entry in renderer.md), and main's worst was under 400 ms, which read as a pacing defect. Each stall coincided with heavy outside load. A quiet gate before each run does not keep a burst out of the run: the only two outside bursts of 20 or more cores in the last three batches both landed on pacing runs (about a 25% chance). Evidence: `lat02` ABBA runs on private desktops, trace builds of 829bfd98c (pacing) and cec863455 (main). Quiet set: 19 main and 20 pacing runs; runs with a key over 500 ms 0 and 1, the one being an outside burst at about 20 cores (Fisher p 1.0). Then the same scheduled load on both builds, 20 ABBA pairs: one spinning thread per logical processor at BelowNormal, busy 2 s and idle 4 s, with noctty's job at `IDLE_PRIORITY_CLASS` (the job's priority-class limit, 0x40) so the maintainer's Normal apps kept the CPU, and the driver's key thread and the watchdog above the load. Results: worst key per burst 1959 ms on both (Hodges-Lehmann shift -0.7 ms, 95% CI -16 to +16 ms); recovery after a burst 36.8 against 35.1 ms; keys over 500 ms inside bursts 1303 against 1295 (p 0.77). Rule: to compare stall rates, inject the same load into both builds' runs, ABBA, at a priority above noctty's and below the user's apps. Log outside processes over a few cores by name and PID. Run positive controls first: an Idle-class counter must stall during bursts while a Normal window's `SendMessageTimeoutW` stays fast. One spinning thread per logical processor starved an Idle-class thread only partly (46% of its rate); two per processor starved it completely. (2) A control thread at the same base priority answering the watchdog's pings within 16 ms, while noctty's UI thread missed them, read as noctty blocking in its own code. That control is not like for like. A thread woken by a message gets a +2 priority boost and loses one level per quantum it uses up. An idle control thread keeps the boost. A UI thread inside one `WM_PAINT` draw (GL draw and `SwapBuffers`: Win32 draws on the app thread) falls to its base, and a load two levels above starves it until the load stops; Windows' anti-starvation boost after about 4 s never arrives for a 2 s burst. Evidence: in the quiet 1946 ms stall, the UI thread was Ready at p7 and then p6 (base 6) in all six missed pings, inside one 2000 ms paint draw (`render.json`), while the outside process ran at 19-21 cores. Under the injected load, the UI thread was Ready in 224 of 248 missed-ping samples on main and 224 of 241 on pacing, and no UI or renderer stack in 78 `cdb` dumps held a lock frame. Rule: at each missed ping, read the UI thread's state and its current and base priority. Ready means starvation, not a wait. For a like-for-like control, use a thread that does a draw-sized CPU burst per ping. (3) A `cdb -pv` attach suspends the target for 0.6-2.4 s. Mark a stall that starts with the UI thread in Wait/Suspended as caused by the attach. (4) The trace builds had no `noctty.pdb`, so the stacks name no noctty frame. ReleaseFast strips by default and then writes no PDB (item (1) of the 2026-10-16 release symbols entry in build-release-ci.md). Build a trace build with `-Dstrip=false` and keep its `noctty.pdb` beside the exe. The harness (watchdog, load program, runner and probe copies) and the result tables are on origin as a measurement-only commit, `96f7c5db4` on `stall-load-measurement-harness` (`test/windows/stall-load-harness/`), as the MEASUREMENT-HARNESS-RERUN-01 entry below describes for the others. This qualifies trap (1) of the VISIBLE-PACING-CERT-01 entry below: the bench stall's cause stays inferred, but pacing is not a candidate. It complements trap (7) of the 2026-10-19 SETSTALL2 part A entry in settings.md: a busy load also starves the harness's own worker.
