# Deep dive: Wintty (deblasis/wintty)

Executive summary (5 lines):
Wintty is the other "Ghostty for Windows": a solo, MIT-licensed **soft fork** rebased on upstream daily, wrapping `libghostty.dll` in a **C# WinUI 3** shell with a **DirectX 12 + DXGI + DirectComposition** renderer — deliberately mirroring the macOS Swift-wraps-libghostty architecture ([README](https://github.com/deblasis/wintty)). In ~5 months it shipped an impressive feature surface — tabs (vertical strip + overview), splits, quake terminal, frecency command palette, native settings UI, session restore, Mica/Acrylic/Crystal backdrops, toasts, jump lists, taskbar progress, Kitty images — and self-describes as a "usable daily-driver" still "polishing renderer throughput" ([README status](https://github.com/deblasis/wintty)). Its deepest asset is empirical Windows-VT engineering: a measured esctest/vttest baseline, a documented ConPTY-mangling catalog, and a **bundled newer OpenConsole `conpty.dll`** that restores Kitty/Sixel passthrough the in-box conhost strips ([conpty-reference.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/vt-compliance/conpty-reference.md)). Its fatal weaknesses are distribution and trust: **zero releases**, signed installer + auto-update **gated behind GitHub Sponsors**, free users must build a Zig+.NET toolchain, GitHub Actions disabled, Discussions disabled, bus factor 1, ~45 stars ([releases](https://github.com/deblasis/wintty/releases), [wintty.io/download](https://wintty.io/download), [tooling.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/tooling.md)). The maintainer himself spiked a pure Win32 + no-.NET escape hatch citing "<200 ms to first frame, no CLR, no GC" — effectively validating noctty's architecture from inside the rival camp ([#82](https://github.com/deblasis/wintty/issues/82)).

---

## 1. Identity & strategy

- **What it is:** "Wintty is a fast, sleek, smooth, feature-rich terminal emulator based on the awesome Ghostty that uses Windows native UI and GPU acceleration" — repo description ([github.com/deblasis/wintty](https://github.com/deblasis/wintty)). Positioned at [wintty.io](https://wintty.io/) as "a fast, GPU-accelerated Windows terminal — built on the Ghostty core," with headline differentiators: deep theming, custom GPU shaders, **vertical side-docked tabs**, and Quake mode.
- **Relationship to upstream:** explicit **soft fork**: `main` mirrors `ghostty-org/ghostty` "synced daily, if it's a good day"; the default `windows` branch carries all Windows work **rebased on upstream** ([README branching model](https://github.com/deblasis/wintty)). History: the maintainer (Alessandro De Blasis) got **17 PRs merged upstream** (Windows build/CI/DLL infrastructure) before continuing independently because "upstream doesn't have capacity to maintain Windows-specific changes right now" ([README history](https://github.com/deblasis/wintty)). Upstream maintainers publicly credited his PRs (#11803, #11782, #11839) as the model for incremental Windows contribution ([ghostty discussion #2563](https://github.com/ghostty-org/ghostty/discussions/2563)).
- **Architecture bet:** "same architecture as macOS where Swift wraps libghostty. All terminal emulation stays in Zig. The C# layer handles windowing, input, and platform integration via P/Invoke" ([README](https://github.com/deblasis/wintty)). This is the sharpest possible head-to-head contrast with noctty's hard fork + native Zig/Win32 apprt: wintty keeps upstream mergeability and inherits every upstream core improvement within a day; noctty owns its whole runtime but must cherry-pick upstream.
- **Roadmap communication:** public progress bars in the README — "MVWT (Minimum Viewable Windows Terminal) ~100%", "MVT (Moonshot Viable Terminal) ~70%" — with a tracking north-star issue ([#26 "Console-stellation aka North Stars"](https://github.com/deblasis/wintty/issues/26)).
- **Governance/bus factor:** solo project. 565 fork commits are De Blasis; other authors in history are upstream Ghostty authors carried by the rebase (local git analysis of the `windows` branch, 2026-08-17). No co-maintainers, CODEOWNERS is upstream's, Discussions disabled (404), GitHub Actions disabled. Bus factor = 1.
- **License / branding:** MIT (upstream's license). Notably still uses "Ghostty" naming internally (`windows/Ghostty/`, `ghostty.dll`); upstream discourages Ghostty branding in unofficial builds ([discussion #2563](https://github.com/ghostty-org/ghostty/discussions/2563)) and a Ghostty collaborator flagged **noctty's own name** for trademark concerns in the forks thread ([discussion #12371](https://github.com/ghostty-org/ghostty/discussions/12371)) — a live risk for both projects.
- **Monetization:** sponsorware. "Sponsor perks like auto-updates and signed binaries" ([README note](https://github.com/deblasis/wintty)); the download page's recommended path is "Become a sponsor, then come back here and sign in with GitHub" for "a signed installer for Windows 10/11 (x64), automatic in-app updates, both stable and tip channels" ([wintty.io/download](https://wintty.io/download)).

## 2. Performance & fluidity

- **Rendering architecture:** DirectX 12 with DXGI swap chains and DirectComposition; 5 HLSL pipelines compiled to SM 6.0 DXIL via dxc.exe; DirectWrite font backend ([README](https://github.com/deblasis/wintty), [#26](https://github.com/deblasis/wintty/issues/26)). The DX12 backend lives in the shared Zig renderer layer (`src/renderer/DirectX12.zig`, ~1,100 lines, alongside Metal/OpenGL), so it inherits upstream's multi-threaded model (dedicated IO/render threads per surface). Rebuilt from DX11 to DX12 in April 2026; the project's stated rationale is that "DX11 is frozen at Microsoft following Windows 10 EOL" ([#26](https://github.com/deblasis/wintty/issues/26)) — wintty's characterization, not a Microsoft position (Microsoft still documents D3D11 support on Windows 11).
- **Three surface modes** at the library level — HWND (`CreateSwapChainForHwnd`), SwapChainPanel composition (WinUI 3/XAML), and shared `ID3D12Resource` texture for game engines/embedders; "the device picks the path based on what the caller provides. No compile-time flags" ([README architecture](https://github.com/deblasis/wintty)).
- **Damage model is currently weak and admitted as such:** open issues track "scroll optimization — avoid full rebuild on viewport scroll" (row versioning / GPU buffer rotation, [#94](https://github.com/deblasis/wintty/issues/94)) and "progressive adaptive presentation" (waitable swap chain, `ALLOW_TEARING`/VRR, skip-present when idle, [#93](https://github.com/deblasis/wintty/issues/93)). README status: "polishing renderer throughput."
- **No published product-level benchmarks.** There is an unusually disciplined _benchmark plan_ — issues for startup-to-first-frame ([#35](https://github.com/deblasis/wintty/issues/35)), K2P software input latency ([#39](https://github.com/deblasis/wintty/issues/39)), ConPTY round-trip latency ([#40](https://github.com/deblasis/wintty/issues/40)), scroll MB/s ([#38](https://github.com/deblasis/wintty/issues/38)), frame-time p95 ([#36](https://github.com/deblasis/wintty/issues/36)), memory-per-pane ([#32](https://github.com/deblasis/wintty/issues/32)), idle power ([#34](https://github.com/deblasis/wintty/issues/34)), GC frame-jitter stress ([#41](https://github.com/deblasis/wintty/issues/41)) — plus a zero-cost cross-language tracing framework (Zig comptime + C# conditional primitives, Chrome-tracing/Perfetto output, [#53](https://github.com/deblasis/wintty/issues/53)–[#59](https://github.com/deblasis/wintty/issues/59)). A `Ghostty.Bench` harness with round-trip/throughput probes exists in-tree, but **no product-level benchmark numbers are published** (all bench issues open as of 2026-08-17; the esctest baseline's ~0.8–0.9 ms latency probes below are the sole published measurements).
- **The .NET/WinUI 3 startup & memory tax is unquantified by the project itself:** [#51](https://github.com/deblasis/wintty/issues/51) ("measure .NET runtime tax," pass thresholds <30 MB / <150 ms, "hard numbers, not vibes") remains open with no measured results. The pure-Win32 spike issue [#82](https://github.com/deblasis/wintty/issues/82) lists as motivations "no .NET runtime," "faster startup" without CLR JIT warmup, "no GC," and a success bar of "startup under 200 ms to first frame" — and cites the InsipidPoint/ghostty-windows Zig+Win32 fork (noctty's lineage) as proof the approach works. **Uncertainty:** no third-party latency/throughput measurements of wintty exist anywhere I could find.

## 3. Native Windows integration

Shipped ([README "What is done"](https://github.com/deblasis/wintty)):

- **Mica / Acrylic / Crystal backdrops** with a tint resolver ("Crystal" is a wintty-specific third backdrop flavor); Dark/Light theme sync plus High-Contrast support for the terminal surface.
- **Toast notifications** (bell + long-running command completion) **with rate-limiting**, via Windows App SDK AppNotification.
- **Jump lists** — recent directories and pinned profiles via `ICustomDestinationList`.
- **Taskbar progress + attention overlay** — OSC 9;4 through `ITaskbarList3`.
- **Power/energy awareness** — power-saver mode detection and adaptive behavior.
- **Quick (Quake) terminal** — position, size, screen, animation, autohide, global hotkey.
- Single-instance; branded icon + icon picker; per-monitor DPI; IME (listed under MVWT input work in [#26](https://github.com/deblasis/wintty/issues/26)).
- **UIA accessibility provider** for the terminal grid (README status line); deeper coverage (output announcements, high-contrast auditing) still tracked open in [#77](https://github.com/deblasis/wintty/issues/77) and automated contrast verification in [#327](https://github.com/deblasis/wintty/issues/327).

Not shipped (admitted gaps, [README "What is next"](https://github.com/deblasis/wintty) / [#81](https://github.com/deblasis/wintty/issues/81)):

- System tray / background mode; "Open Terminal Here" Explorer context menu (classic registry + Win11 `IExplorerCommand`); **default-terminal registration** (`ITerminalHandoff`, rated High complexity with stability concerns); first-class automation surface (control CLI / COM server); **multi-window**.
- **ARM64:** no evidence of ARM64 support; the sponsor installer is explicitly "Windows 10/11 (x64)" ([wintty.io/download](https://wintty.io/download)). noctty ships x64 + ARM64.

**ConPTY story (the deepest part of the whole project):** ConPTY is the sole transport (a raw-pipe bypass was removed in #474). `WindowsPty` drives `CreatePseudoConsole` over a named input pipe (overlapped I/O for libxev IOCP) + anonymous output pipe, `dwFlags = 0` to sidestep the documented `INHERIT_CURSOR` close-deadlock. Crucially, wintty **ships a newer OpenConsole as `conpty.dll`** next to the exe and prefers it over the OS conhost, because "the in-box Windows conhost only dispatches the VT sequences it recognizes and silently drops the rest," which "strips … Kitty graphics (APC) and Sixel (DCS)." Fallback to kernel32 is treated as **degraded mode and logged**: "…using OS conhost (Kitty graphics and Sixel will not work)" ([conpty-reference.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/vt-compliance/conpty-reference.md)). The same doc catalogs every known ConPTY mangling with mitigation status (mid-DCS SGR-reset injection: unmitigated; OSC 10/11/12 color-query interception: unmitigated since the bypass removal; resize reflow desync: inherent).

- **UTF-8 code page handling:** injects a one-time preamble for code-page-observing shells — `chcp 65001` for cmd, `chcp` **plus** `[Console]::OutputEncoding`/`InputEncoding` for PowerShell 5.1/7 (chcp required even on pwsh7) — gated by a `utf8-console = auto|always|never` config with a guard that refuses auto-forcing on legacy CJK ANSI code pages (932/936/949/950/1361) to avoid mojibaking legacy `.bat` files ([conpty-reference.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/vt-compliance/conpty-reference.md)).
- **WSL story:** first-class — profiles auto-discover WSL distros; the whole VT-compliance harness runs `wsl.exe → ConPTY → libghostty`.
- Elevation/UAC: no specific handling found (uncertain — nothing documented).

## 4. Terminal capability

- **Core parity by construction:** daily rebase means the full upstream Ghostty 2026 core — VT/xterm conformance, Kitty graphics + keyboard protocols, synchronized output, OSC 8 hyperlinks, OSC 52, light/dark notifications, grapheme clustering — is inherited within a day of upstream landing it ([README](https://github.com/deblasis/wintty)). This is the structural advantage of the soft fork: upstream's 1.3.0 scrollback-search-era improvements arrive "for free."
- **Kitty images on Windows actually work end-to-end:** "Kitty image protocol transport (ConPTY bypass) with DX12 atlas upload" ([README](https://github.com/deblasis/wintty)) — today implemented via the bundled `conpty.dll` passthrough above. Sixel DCS likewise forwarded by the bundled host.
- **Measured, honest VT conformance:** an esctest baseline run through the real WSL→ConPTY path: of 568 tests — 141 pass, 42 xterm-known-bug, 1 fail-other, 307 "timeouts" _measured and proven to be unanswered-query failures, not transport_ (dominated by DECRQCRA screen-readback which libghostty deliberately doesn't answer), 77 mismatch-review. A latency probe shows ConPTY+WSL query replies round-trip in **~0.8–0.9 ms with zero loss** ([esctest-baseline.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/vt-compliance/esctest-baseline.md)). The doc even publishes a correction of its own earlier wrong conclusion. vttest visual runs are documented with a WSL build harness ([vttest-results.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/vt-compliance/vttest-results.md)). Automated esctest + visual regression in CI is an open aspiration blocked on Actions billing ([#508](https://github.com/deblasis/wintty/issues/508)).
- **Known VT holes on Windows:** OSC 10/11/12 color queries are intercepted/swallowed by ConPTY and currently have **no workaround** ("an unanswered color query on Windows is a ConPTY interception, not a Wintty gap") — apps that query background color for theme detection fail ([conpty-reference.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/vt-compliance/conpty-reference.md)).
- **Shell integration:** upstream's bash/zsh/fish/elvish/nushell scripts, plus a **PowerShell** integration (`src/shell-integration/powershell/ghostty.ps1`) and — unique among the Windows forks — a **cmd.exe integration**: the `PROMPT` env var emits OSC 133;A/B and OSC 9;9 (cwd), and an auto-loaded Clink `ghostty.lua` (via `CLINK_PATH` prepend) adds OSC 133;C and 133;D;<exit-code> when Clink is present, degrading gracefully without it (`src/shell-integration/cmd/README.md` in-tree, windows branch).
- Scrollback search, resize overlay, inspector window, bell, clipboard with **paste confirmation** (MIME + format marshalling) are shipped in the C# shell ([README](https://github.com/deblasis/wintty)). Yazi-integration OSC handlers are a tracked wishlist item ([#347](https://github.com/deblasis/wintty/issues/347)).

## 5. Workflow features

- **Tabs:** vertical side-docked tab strip, tab overview, snap zones, color palettes, per-tab icons, rename ([README](https://github.com/deblasis/wintty)). The vertical layout is marketed as a differentiator "for wide, multi-pane workflows" ([wintty.io](https://wintty.io/)).
- **Splits:** split tree, pane context menus, directional navigation.
- **Quick terminal:** full quake-mode implementation (position/size/screen/animation/autohide/global hotkey) — upstream's `quick-terminal-*` config surface realized on Windows.
- **Command palette:** "frecency autocomplete" with multiple sources — built-in actions, config keybinds, jump (recent directories), profiles, version, demo (`windows/Ghostty/Commands/*.cs` in-tree).
- **Profiles:** auto-discovery of installed shells (pwsh, cmd, WSL distros, MSYS2) with Win32/SVG icon resolution.
- **Session restore:** window/tab/split state save/restore (`SessionManager`/`SessionRestorer`/`SessionStore`) — same scope as noctty (layout, not contents).
- **Keybindings:** Ghostty's `keybind` config grammar plus a native Keybindings settings page and a cheat-sheet ([README settings list](https://github.com/deblasis/wintty)).
- **Missing:** multi-window (open roadmap item), broadcast input (never mentioned), cross-window tab drag (n/a without multi-window).

## 6. Reliability & quality signals

- **Tests:** upstream Zig suite passes on Windows (2,604 tests, 53 skipped — [README](https://github.com/deblasis/wintty)); C# side has `Ghostty.Tests`, `Ghostty.Tests.Windows` (incl. QuickTerminal smoke tests), interop tests against the real DLL.
- **But no CI at all:** "There is no automated CI pipeline. GitHub Actions is disabled." Rationale: free-tier Windows runners burn minutes at 2x; testing happens manually on a homelab over SSH; "Upstream keeps Linux and macOS CI healthy" ([tooling.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/tooling.md)). README jokes it's "DisContinuous Integration." Regression protection is therefore human-discipline-only.
- **Daily-rebase fragility:** the default branch is force-pushed daily with rewritten SHAs (~17.6k commits total); "synced daily, if it's a good day" concedes sync slippage. Any contributor branch goes stale every 24 h.
- **Issue tracker is a solo lab notebook, not a user-bug stream:** of ~53 open issues, nearly all are the maintainer's own planning/bench/instrumentation/spike issues; recent ones are self-filed correctness findings, some tagged "candidate to send" upstream (e.g. errdefer double-free [#596](https://github.com/deblasis/wintty/issues/596), Surface.init thread teardown [#624](https://github.com/deblasis/wintty/issues/624), single-instance connect-budget race [#629](https://github.com/deblasis/wintty/issues/629)). Essentially zero externally-filed bugs → tiny real-world exposure.
- **Release stability reputation: none exists** — there have never been releases ([releases page](https://github.com/deblasis/wintty/releases)). NativeAOT packaging is known-broken (.xbf/.pri missing from publish output, [#184](https://github.com/deblasis/wintty/issues/184), tagged upstream/WindowsAppSDK).

## 7. Configuration & extensibility

- **Config model: both file and GUI.** Ghostty's config grammar underneath; native settings UI with Appearance, Keybindings, General, Profiles, Terminal, Colors (including a gradient-points editor and color picker), **Raw editor**, Advanced, cheat-sheet ([README](https://github.com/deblasis/wintty)); a `ConfigWriteScheduler`/`SettingsConfigWriter` layer writes back to the config file (in-tree `windows/Ghostty.Core/Config/`). Windows-only keys exist (`WindowsOnlyKeys.cs`) but documenting a `windows-*` key surface mirroring `macos-*` is still open ([#214](https://github.com/deblasis/wintty/issues/214)).
- **Custom shaders:** upstream's shadertoy-style custom-shader pipeline is wired to HLSL for DX12 (`custom_shader_target: .hlsl`, `src/renderer/DirectX12.zig`) and marketed on wintty.io ("Custom GPU shaders for backgrounds and visual effects"). noctty has the GLSL equivalent behind a build flag — parity, not a gap.
- **Extensibility/API:** the real play is **embeddability**: three surface modes at the libghostty level, a planned NuGet package for libghostty Windows artifacts ([#65](https://github.com/deblasis/wintty/issues/65)), a separate [libghostty-dotnet](https://github.com/deblasis/libghostty-dotnet) examples repo, and an "embedder experience pain points" meta-issue ([#98](https://github.com/deblasis/wintty/issues/98)). No scripting/plugin system; automation CLI/COM server is roadmap ([README](https://github.com/deblasis/wintty)).

## 8. Packaging & adoption

- **Install channels: effectively none for the general public.** Zero GitHub releases; no winget, no Scoop, no MSIX/MSI (all "What is next" items, with auto-update "ships via the sponsor tier (Velopack)" — [README](https://github.com/deblasis/wintty)). The free path is building from source with Zig + Just + the .NET/WinUI toolchain; the paid path is sponsor sign-in for a signed x64 installer with stable+tip channels and in-app auto-update ([wintty.io/download](https://wintty.io/download)).
- **Code signing:** sponsor builds only. Antivirus false positives were encountered and remain an open research item ([#249](https://github.com/deblasis/wintty/issues/249)).
- **Docs:** good-to-excellent for developers (HACKING, tooling.md, the vt-compliance trio are genuinely best-in-class Windows-terminal engineering docs); thin for end users (wintty.io has marketing + download + docs stub; user docs mostly defer to ghostty.org).
- **Momentum signals:** ~45 stars, 2 forks, no contributors besides the maintainer; but extremely high solo velocity — ~637 issues+PRs and 565 fork commits since late March 2026, with PR #637 merged the day of this survey (local git log; [repo](https://github.com/deblasis/wintty)). Near-zero third-party coverage: no HN/Reddit threads found for "wintty" (searches 2026-08-17); it isn't even prominent in Ghostty's own Windows-forks showcase thread ([discussion #12371](https://github.com/ghostty-org/ghostty/discussions/12371)).

## 9. What users complain about

There is almost no external user voice to mine — Discussions are disabled, issues are ~all self-filed, and no Reddit/HN/blog coverage was found. What can be said:

- The absence of complaints **is** the signal: with no binaries, there are practically no users to complain. The only "user-shaped" friction on record is the sponsor gate itself (download page requires sponsorship + GitHub sign-in for any prebuilt binary — [wintty.io/download](https://wintty.io/download)) and AV false positives on locally-built artifacts ([#249](https://github.com/deblasis/wintty/issues/249)).
- Self-acknowledged product gaps that would be complaints under load: renderer throughput ("polishing"), full-rebuild scrolling ([#94](https://github.com/deblasis/wintty/issues/94)), no multi-window, no default-terminal registration, no tray, OSC 10/11/12 queries dead ([conpty-reference.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/vt-compliance/conpty-reference.md)).
- In the broader Ghostty-on-Windows community, recurring themes that shape expectations for both forks: ConPTY bugs pushing projects to embed newer ConPTY builds (ghostinthewsl author, [discussion #12371](https://github.com/ghostty-org/ghostty/discussions/12371)), demand for tiny/fast binaries (mite's <2 MB pitch, same thread), and upstream's trademark policing of "Ghostty"-branded forks (pluiedev flagged noctty by name, same thread).

## 10. Lessons for noctty

Ground truth caveat: noctty's [docs/status.md](../../../docs/status.md) undersells the codebase — code inspection shows quick terminal (`src/apprt/win32_quick_terminal.zig`), WinRT toasts, taskbar progress (OSC 9;4), and bell already exist even though status.md omits them. The lists below are checked against the code, not just status.md.

### Does well (adopt-candidates)

1. **Bundle a newer OpenConsole as `conpty.dll` with logged degraded-mode fallback.** noctty calls in-box `kernel32.CreatePseudoConsole` directly (`src/pty.zig:430`); per wintty's measurements the in-box conhost silently strips Kitty APC and Sixel DCS, so noctty's Kitty-graphics claim is at the mercy of the user's OS conhost version. Wintty's pattern — prefer adjacent `conpty.dll`, fall back with a loud "Kitty graphics and Sixel will not work" warning — is directly adoptable ([conpty-reference.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/vt-compliance/conpty-reference.md)).
2. **UTF-8 console preamble with a CJK-code-page guard.** noctty has no `chcp 65001`/`[Console]::OutputEncoding` handling anywhere (grep-verified), so cmd/PowerShell Nerd-Font/oh-my-posh output can mojibake. Wintty's `utf8-console = auto|always|never` policy plus the legacy-CJK-ANSI guard is a complete, tested design to copy.
3. **cmd.exe shell integration via `PROMPT` + optional Clink lua.** OSC 133;A/B and OSC 9;9 cwd from `PROMPT` cost nothing and work everywhere; Clink adds C/D marks with exit codes. noctty explicitly leaves cmd a "plain fallback" ([status.md](../../../docs/status.md)) — this closes it cheaply.
4. **Jump lists** (recent directories + pinned profiles via `ICustomDestinationList`) — no `ICustomDestinationList` usage exists in noctty (grep-verified). High native-feel value for the benchmark user; taskbar-driven re-entry into a cwd.
5. **A ConPTY-mangling catalog + measured esctest/vttest baseline as living docs.** noctty's [windows-vt-conformance.md](../../../docs/windows-vt-conformance.md) is a capability inventory; wintty adds the _why-it-fails_ layer (latency probes, unanswered-query taxonomy, per-mangling mitigation table, published self-corrections). Adopting that empirical format would harden noctty's "deep terminal capability" claim — and pre-answers OSC 10/11/12-style interception questions noctty hasn't documented.
6. **Vertical/side-docked tabs + tab overview.** Absent in noctty (grep-verified); wintty and wide-monitor users treat it as a first-class layout ([wintty.io](https://wintty.io/)). Cheap differentiation for multi-pane workflows.
7. **Frecency ranking in the palette + toast rate-limiting + long-running-command completion toasts.** noctty has recents and OSC 9 toasts; wintty's refinements (frecency, rate-limited bell toasts, "command finished" notifications keyed off shell-integration marks) are small deltas with daily-workflow payoff.
8. **Power/energy awareness** — power-saver detection with adaptive rendering behavior; nothing comparable exists in noctty (grep-verified).
9. **Public benchmark definitions.** Even unexecuted, wintty's metric set (startup-to-first-frame, K2P input latency, ConPTY round-trip, scroll MB/s, frame-time p95, memory/pane, idle power, [#26](https://github.com/deblasis/wintty/issues/26)) is the right scoreboard for a product whose PRODUCT.md promises "fastest, most fluid." Publishing noctty numbers against these metrics before wintty does would convert an empty rival plan into noctty marketing.

### Does badly (avoid / exploit)

1. **No releases, sponsor-gated binaries.** The rival's entire distribution funnel requires payment or a Zig+.NET build. noctty already ships signed installers via winget/Scoop — **exploit loudly**: noctty is today the only installable "Ghostty on Windows" with releases ([wintty releases](https://github.com/deblasis/wintty/releases), [wintty.io/download](https://wintty.io/download)).
2. **No CI.** "GitHub Actions is disabled … There is no automated CI pipeline" ([tooling.md](https://github.com/deblasis/wintty/blob/windows/windows/docs/tooling.md)). Avoid: keep noctty CI healthy and visible; it is a trust differentiator against a homelab-tested rival.
3. **WinUI 3/.NET runtime tax, unmeasured and internally doubted.** The maintainer's own issues quantify the fear (<30 MB/<150 ms pass thresholds unvalidated, [#51](https://github.com/deblasis/wintty/issues/51)) and his pure-Win32 spike ([#82](https://github.com/deblasis/wintty/issues/82)) reads like a brief for noctty's architecture ("no .NET runtime… startup under 200 ms… direct C calls, no P/Invoke marshaling"). Exploit: publish noctty's cold-start and memory numbers head-to-head.
4. **Daily-rebase soft fork operational fragility:** force-pushed default branch, rewritten SHAs, "synced daily, if it's a good day," NativeAOT packaging broken by upstream WinAppSDK behavior ([#184](https://github.com/deblasis/wintty/issues/184)). The flip side is real (they inherit upstream features in a day; noctty must budget for deliberate upstream syncs), but the contributor experience and reproducibility costs are a genuine hard-fork advantage to articulate.
5. **Bus factor 1 with zero community surface** (Discussions disabled, no external contributors, ~45 stars). noctty's Discussions-open posture and reproducible builds are the counter-position.
6. **x64-only.** No ARM64 anywhere in wintty's offering; noctty ships ARM64 — increasingly relevant with Snapdragon-X laptops.
7. **Trademark exposure.** wintty renamed away from "Ghostty" branding externally but still ships `ghostty.dll`/`windows/Ghostty` internals; upstream actively polices the name and has already flagged "noctty" ([discussion #12371](https://github.com/ghostty-org/ghostty/discussions/12371)). Lesson for noctty: treat naming/branding risk as a product issue before an upstream takedown makes it one.
8. **Feature breadth ahead of renderer soundness** — quake mode, backdrops, and palettes shipped while viewport scrolling still rebuilds the full frame ([#94](https://github.com/deblasis/wintty/issues/94)). This is PRODUCT.md's anti-reference ("feature-count competition that weakens performance") observed in the wild; keep noctty's ordering inverted.

### Blind-spot candidates (no category in PRODUCT.md)

1. **Embeddability as a product surface.** wintty treats `libghostty.dll` consumers as first-class: three surface modes (HWND/SwapChainPanel/shared texture), a NuGet artifact plan ([#65](https://github.com/deblasis/wintty/issues/65)), a .NET examples repo ([libghostty-dotnet](https://github.com/deblasis/libghostty-dotnet)), and an embedder-pain-points backlog ([#98](https://github.com/deblasis/wintty/issues/98)). PRODUCT.md has no category for noctty-as-a-component (it keeps only `libghostty-vt` buildable).
2. **Sustainability/monetization model.** Sponsorware perks (signed builds, stable+tip auto-update channels via Velopack) are an explicit product mechanic for wintty. PRODUCT.md is silent on how noctty funds signing certificates, infra, and maintainer time.
3. **Energy/battery as a performance axis.** Idle power draw benchmarks and power-saver adaptive behavior appear nowhere in PRODUCT.md's definition of "fastest, most fluid" — laptops are the dominant dev hardware.
4. **A quantified performance scoreboard.** PRODUCT.md asserts speed but defines no metrics, thresholds, or measurement harness; wintty's bench/instrumentation issue tree ([#26](https://github.com/deblasis/wintty/issues/26), [#53](https://github.com/deblasis/wintty/issues/53)) shows what a falsifiable performance contract looks like (including cross-language tracing for a mixed Zig/host architecture — directly applicable to noctty's Zig core + chrome pipeline split).
5. **Explorer/OS entry points as a category:** "Open Terminal Here" context menu, `ITerminalHandoff` default-terminal registration, system tray/background mode ([#81](https://github.com/deblasis/wintty/issues/81)). The rubric asks about these, but PRODUCT.md itself has no "how users _enter_ the terminal from Windows" category; wintty's P1/P2/P3 native-integration matrix is a ready-made checklist.
6. **Upstream-relations strategy.** wintty maintains a merged-17-PRs-upstream relationship and files fork-found bugs as "candidates to send" upstream ([#596](https://github.com/deblasis/wintty/issues/596)); upstream publicly credits it ([discussion #2563](https://github.com/ghostty-org/ghostty/discussions/2563)). PRODUCT.md declares upstream governance out of scope but has no posture for contributing fixes back or for coexisting with upstream's eventual official Windows effort — the single biggest strategic risk both forks share.
