# PowerShell history harness inventory

Source-only inventory for the PWSHHIST follow-up, checked against each entrypoint's argument arrays, generated configuration, input destinations, and guard calls. One row identifies one runnable launcher file, including its variants and delegated children. Shell means the process started in a noctty terminal (or the direct shell/fixture process when there is no product terminal). The input column distinguishes shell command lines, raw fixture input, and UI controls. History guard owners are source paths and call sites, not runtime acceptance claims.

`scripts/interactive-win11-lib.ps1:Get-InteractiveWin11LaunchArguments` adds `--command=cmd.exe` unless passed `-UseConfiguredCommand`; `test/windows/interactive-win11-stateful-lib.ps1:Start-StatefulApp` forwards that switch. Only the conpty-sync and issue149 launcher call sites opt out of this composer default. Calling `Get-InteractiveWin11ExePath` or `Get-InteractiveWin11ContainmentArguments` does not select a shell. In product configuration, `-e` sets **initial-command**, not **command** (`src/config/Config.zig:parseManuallyHook`): a PowerShell `-e ... -File` initial pane and cmd later tabs/splits can coexist. Rows identify that distinction where relevant.

Shared history guards are implemented by `scripts/windows-harness-history.ps1:Start-WindowsHarnessHistoryGuard` / `Assert-WindowsHarnessHistoryGuard`. They compare absence/existence, length, and UTC last-write ticks for three known-folder candidates: ApplicationData `Microsoft/Windows/PowerShell/PSReadLine/ConsoleHost_history.txt`, ApplicationData `Microsoft/PowerShell/PSReadLine/ConsoleHost_history.txt`, and MyDocuments `PowerShell/PSReadLine/ConsoleHost_history.txt`. They never read or hash real history. “Via shared helper” below means these functions; the owner supplies the harness label and brackets its run. The guard detects metadata changes; it does not itself disable saving or identify the writer.

`-NoProfile` alone is not history isolation. The noninteractive `-File` fixtures below do not return to a PSReadLine prompt unless explicitly paired with `-NoExit`; some read raw fixture keys through `Console.ReadKey`, which is distinct from a PSReadLine command reader. APPDATA/LOCALAPPDATA redirection alone does not redirect PSReadLine's known-folder history. The governing log entries are test-harnesses.md's 2026-10-11 PKG-13 and 2026-10-17 PKG-76.

- Launch libraries are traced through callers: `test/windows/hidden-win11-lib.ps1`, `test/windows/hidden-win11-local-lib.ps1`, `test/windows/interactive-win11-hidden-desktop-lib.ps1`, `test/windows/interactive-win11-stateful-lib.ps1`, `test/windows/renderer/Native.ps1`, and `scripts/interactive-win11-lib.ps1`. - Payload/native support is covered by the launching row: `test/windows/issue149-color-payload.ps1`, renderer `Fixture.ps1`, generated `-File` payloads, `history-guard-native.cs`, `cli-com-native.cs`, `cli-com-fixture.zig`, `console-input-records.c`, `console-attach-info.c`, and `cmd-clink.lua`. - `test/windows/settings-generated-form.ps1` and `settings-uia-patterns.ps1` are client-only HWND probes with their own metadata guards; parent launchers are listed. Nonlaunching source/AST/PE/provenance checks are `settings-open-readiness-tests.ps1`, `interactive-win11-measure-contract.ps1`, `Test-InteractiveWin11HintsContracts.ps1`, `cli-import-contract.ps1`, and `assert-interactive-runner.ps1`.

It supplies scratch known-folder roots and an injected clipboard-sequence reader to `scripts/interactive-win11-state-guard.ps1`; its assertions do not establish runtime acceptance of the composite.
- `test/windows/interactive-win11-job.ps1` sets `NOCTTY_INTERACTIVE_MEASURE_AUMID=1` and starts the same state guard around the whole job, so a product jump-list, startup-attempts or clipboard-sequence change during any leaf fails the job; its receipts land in `test/windows/flagship/artifacts/interactive-win11/job-state`.
- In the current composite source, `test/windows/interactive-win11-validate.ps1` calls `scripts/interactive-win11-state-guard.ps1:Start-InteractiveWin11StateGuard` before the batch and `Assert-InteractiveWin11StateGuard` in `finally`, alongside its separate history guard. Startup/product existence, length, and last-write changes or a clipboard-sequence change fail the guard. Cleanup targets only the exact measure filename when absent before, created and written within the batch interval, and unchanged on metadata recheck; preexisting or uncertain files are preserved. These are inspected source behaviors, not a runtime result or additional PSReadLine isolation.
- Flagship contract fragments that actually start PowerShell children have their own rows, even though loaded by `flagship/Test-VerificationContracts.ps1`. Source snapshot strings and mocked launch calls are not classified as launches. Other fragments and `ContractHelpers.ps1` run in that runner's scope; compiler/native Zig test processes are not classified as interactive PowerShell shells.
- The workflow mapping covers all eight current `.github/workflows/*.yml` files and follows the local release-preflight action plus the packaging and test-wrapper call chains. It does not claim an exhaustive transitive audit of external publishing tools, generated installer/uninstall hooks, or third-party actions. The composite, flagship wrapper, and leaves retain separate history-guard ownership; direct release packaging has no composite guard.
- This audit is source-only: no harness, PSReadLine acceptance control, build, or GUI ran, and no real history/profile/clipboard contents were inspected. Runtime proof belongs to the lead's acceptance evidence. Known-folder metadata guards do not cover arbitrary customized history paths or detect a rewrite preserving both length and timestamp; a changed file alone does not identify which concurrent writer changed it.
